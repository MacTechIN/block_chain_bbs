# 학습계획서 — 내 손으로 하는 법

> **이 문서의 역할: HOW.**
> 무엇을 만들지는 [개발계획서](01-개발계획서.md)가 정한다. 이 문서는 **그걸 어떻게 내 손으로 익히는가**를 정한다.
>
> **중복 방지 규칙**
> - Phase 범위 · DoD · 아키텍처 결정 → 이 문서에 다시 쓰지 않는다. [개발계획서](01-개발계획서.md) 링크.
> - 외부 URL · 저장소 · 라이브러리 비교 · 긴 개념 해설 → [기술리서치](02-기술리서치.md)에만. 여기선 `#앵커` 링크만.
> - 체크박스 · 회고 · 막힌 기록 → [PROGRESS.md](PROGRESS.md)에만.
> - **이 문서에만 있는 것**: 랩 템플릿, 힌트 단계 규칙, 에스컬레이션 규칙, 랩 인덱스.
>
> **랩 본문은 `docs/labs/`에 분리한다.** 이 문서는 인덱스와 규칙만 갖는다.
> Phase 0·1은 이미 작성돼 있고, **Phase 2부터의 랩 본문은 해당 Phase에 진입할 때 `docs/labs/phase-N-*.md`로 작성한다.**
> 앞 Phase에서 실제로 무엇에 막혔는지를 보고 난이도를 조정하기 위해서다.

## 1. 이 학습법의 전제

**Break-First.** 방어를 먼저 배우지 않는다. 취약한 것을 먼저 만들고, 내 손으로 깨뜨리고, 그 다음에 고친다.

이유는 단순하다. "prev_hash가 있어서 변조에 강하다"를 **읽어서** 아는 것과,
내 게시판 파일을 에디터로 고쳤는데 앱이 아무것도 눈치 못 채는 걸 **보고 나서** 아는 것은 다른 기억이다.
전자는 3일이면 흐려지고 후자는 남는다.

그래서 이 문서의 모든 랩은 **1절이 "먼저 깨져보기"**다. 개념 설명은 그 뒤에 온다.

**정답 코드는 어디에도 없다.** 랩 문서는 시그니처와 불변식과 힌트(의사코드까지)만 준다.
대신 **테스트는 미리 주어진다.** 통과시키는 구현은 사용자가 쓴다.

## 2. 학습 맵

Phase → 랩 → 개념의 의존 관계. **화살표는 "없으면 못 한다"는 뜻이다.**

```
Phase 0  기반 세팅
 ├─ Lab 0.1  실패하는 테스트부터 보기 ......... [pytest 루프]
 ├─ Lab 0.2  uv 프로젝트와 src 레이아웃 ....... [패키지 구조]
 └─ Lab 0.3  CI를 초록으로 .................... [자동 검증]
        │
        │  (테스트 루프가 없으면 이후 모든 DoD를 검증할 수 없다)
        ▼
Phase 1  단일 노드 체인 + 게시판 코어
 ├─ Lab 1.1  해시 감각 잡기 ................... [결정성, 눈사태 효과]
 │      ▼
 ├─ Lab 1.2  취약한 게시판과 변조 ⚔ .......... [무결성이 없다는 것]
 │      ▼
 ├─ Lab 1.3  블록과 체인 ...................... [canonical_bytes, prev_hash, 파손 전파]
 │      │                                          └→ ADR-0001 고정
 │      ▼
 ├─ Lab 1.4  머클 루트 ........................ [머클 트리] ──────┐
 │      ▼                                                          │
 ├─ Lab 1.5  영속화와 검증 CLI ................ [Storage 프로토콜] │
 └─ SQ 1.6   Sepolia 맛보기 🌐 ................ [실제 체인 기준선] │
        │                                                          │
        ▼                                                          │
Phase 2  탐색기 v1 + SQLite ................... [조회 API, 저장 추상화]
        │        ⚔ DB 직접 UPDATE                                  │
        ▼                                                          │
Phase 3  지갑 · 서명 · tx ..................... [공개키 암호, nonce]│
        │        ⚔ 사칭 · 리플레이                                 │
        ▼                                                          │
Phase 4  PoW · 채굴 ........................... [난이도, 해시레이트]│
        │        ⚔ 무한 블록 생성                                  │
        │                                                          │
        ├──────────────┐                                           │
        ▼              ▼                                           │
Phase 5  P2P · 합의                                                │
 ├─ 5a 피어/전파 ............................... [gossip]           │
 ├─ 5b 동기화 .................................. [IBD, 고아 블록]   │
 └─ 5c 포크/reorg .............................. [누적 난이도 선택] │
        │        ⚔ 영구 분기                                       │
        ▼                                                          │
Phase 6  공격 실습 ⚔⚔⚔ ...................... [확률적 완결성]     │
        │                                                          │
        ▼                                                          │
Phase 7  배포 + 앵커링 ........................ [노드 운영] ◄───────┘
                                              (앵커 대상은 블록 해시 —
                                               머클 루트는 그 해시의 입력이다)

⚔ = 공격 실습이 들어가는 지점    🌐 = 실제 공개 체인을 만지는 지점
```

**읽는 법**: 세로 화살표는 순서 제약이다([개발계획서 7절](01-개발계획서.md#7-순서-제약)).
가로 점선(Lab 1.4 → Phase 7)은 "여기서 만든 게 저기서 쓰인다"는 뜻이다.
머클 루트는 Phase 1에서 만들고 Phase 7 앵커링까지 안 쓰이는 것처럼 보이지만, **그때 쓰려고 지금 만든다.**
단 **온체인에 올라가는 값은 머클 루트가 아니라 블록 해시**다 — 머클 루트는 **블록 해시의 입력**으로 쓰인다.
(왜 머클 루트로는 안 되는지는 → [ADR-0003](decisions/ADR-0003-anchor-target.md))

## 3. 하루 루프

한 번 앉았을 때 이 순서로 돈다. **회고와 체크 없이 다음 랩으로 넘어가지 않는다.**

```
  ① 랩 열기          docs/labs/phase-N-*.md 의 다음 랩
        ▼
  ② 먼저 깨져보기    방어 없는 버전으로 공격 재현 → 화면/로그 확인
        ▼            (여기서 "왜 이게 가능했나"를 3줄로 메모)
  ③ 사전지식 체크    질문 3개. 못 답하면 → 기술리서치 #앵커
        ▼
  ④ 구현             과제 절의 시그니처와 불변식만 보고 직접 작성
        ▼            (막히면 → 5절 에스컬레이션 규칙)
  ⑤ 테스트           uv run pytest tests/... → 초록 확인
        ▼
  ⑥ 눈으로 확인      탐색기/CLI에서 "성공하면 보여야 할 것"을 실제로 봄
        ▼            ← 이 단계를 건너뛰면 이 프로젝트를 하는 의미가 없다
  ⑦ 회고 3줄         PROGRESS.md에 배운 것 / 헛짚은 것 / 다음에 확인할 것
        ▼
  ⑧ 커밋             랩 단위로 커밋. PROGRESS.md도 같이
        ▼
  ⑨ 체크박스         PROGRESS.md의 랩 체크박스 켜기
```

**⑥번이 이 프로젝트의 존재 이유다.** 테스트가 초록인 것과 체인이 깨지는 걸 눈으로 본 것은 다른 일이다.
시간이 없으면 ⑧을 미루고, ⑥과 ⑦은 미루지 않는다.

## 4. 랩 템플릿

모든 랩은 아래 9개 절을 **전부** 갖는다. 빈 절이 있으면 그 랩은 아직 완성이 아니다.

| 절 | 이름 | 무엇이 들어가나 | 금지 |
|---|---|---|---|
| 0 | **왜 이게 필요한가** | 한 문단. **아픔부터.** "이게 없으면 뭐가 곤란한가" | 원리 설명 금지 |
| 1 | **먼저 깨져보기** ⚔ | 방어 없는 버전으로 공격 재현 + **봐야 할 화면/로그를 예상 출력 그대로** + 질문 | 답을 미리 주기 금지 |
| 2 | **사전지식 체크** | 질문 3개. 못 답하면 리서치 문서 `#앵커`로 | 긴 해설 금지 |
| 3 | **과제** | **시그니처만**, 본문은 비움 + 만족해야 할 **불변식 목록** | 구현 본문 금지 |
| 4 | **힌트** | `<details>` 3단: L1 방향 / L2 구조 / L3 의사코드 | **L3도 의사코드까지만** |
| 5 | **흔한 실수** | 증상 → 원인 표 | |
| 6 | **검증** | 실행할 pytest 명령 + 통과해야 할 **테스트 이름 목록** + **눈으로 확인할 것** | |
| 7 | **실제 체인에서는** | 비트코인/이더리움의 대응 개념 + 리서치 문서 링크 | 링크만, 해설은 리서치에 |
| 8 | **더 파보기** | 선택 과제 2~3개 | |
| 9 | **회고 3줄** | PROGRESS.md에 기록 | |

### 힌트 3단 규칙

| 단계 | 언제 연다 | 무엇까지 |
|---|---|---|
| **L1 — 방향** | 30분 자력 시도 후 | "어디를 보라"만. 예: *"해시 입력을 만드는 부분을 다시 봐라"* |
| **L2 — 구조** | L1 후 1시간 | 함수를 몇 개로 쪼갤지, 어떤 자료구조를 쓸지. 로직은 없음 |
| **L3 — 의사코드** | L2 후 2시간 | 단계별 의사코드. **실제 파이썬 코드는 없다** |

**L3을 열어도 안 되면 정답을 찾지 말고 5절로 간다.**

### 테스트는 미리 주어진다

랩의 6절에 적힌 테스트 파일은 **에이전트가 미리 작성**한다. 사용자는 그것을 **통과시키는 구현**을 쓴다.
테스트를 고쳐서 통과시키는 것은 금지다 — 테스트가 틀린 것 같으면 그것도 리뷰 요청감이다.

## 5. 막혔을 때 에스컬레이션 규칙

```
 시작
  │
  ├─ 0~30분   자력. 검색도 금지는 아니지만 정답 코드 검색은 금지
  │              └ 그 전에: 에러 메시지를 끝까지 읽었나? 테스트 이름이 뭘 요구하나?
  ▼
  ├─ 30분     L1 힌트 열기 (방향)
  ▼
  ├─ 1시간    L2 힌트 열기 (구조)
  ▼
  ├─ 2시간    L3 힌트 열기 (의사코드)
  ▼
  └─ 그래도   code-reviewer 에이전트에 "내 구현을 리뷰해줘" 요청
              + PROGRESS.md 막힌 지점 로그에 기록
```

### 리뷰 요청할 때 지키는 것

**정답 요청 금지.** 이 원칙 하나가 이 프로젝트의 학습 효과 대부분을 결정한다.

| 이렇게 묻는다 ✅ | 이렇게 묻지 않는다 ❌ |
|---|---|
| "내 `canonical_bytes` 구현이다. 어떤 입력에서 깨질 것 같나?" | "`canonical_bytes` 구현해줘" |
| "이 테스트가 실패하는데, 내 가정 중 뭐가 틀렸나?" | "이 테스트 통과하는 코드 보여줘" |
| "이 두 설계 중 어느 쪽이 Phase 5에서 문제가 되나?" | "어떻게 짜는 게 정답이야?" |
| "내 머클 루트가 표준 구현과 다른 이유를 짚어줘" | "머클 트리 코드 붙여줘" |

**에이전트가 랩 대상 모듈을 대신 구현하지 않는 것은 프로젝트 규칙이다** ([CLAUDE.md](../CLAUDE.md)).
사용자가 명시적으로 "이건 대신 짜줘"라고 말한 경우만 예외이고, 그때는 그 사실을 PROGRESS.md에 기록한다.
나중에 그 모듈이 자기 것이 아니라는 걸 알아야 하기 때문이다.

## 6. Break-First 4박자

각 Phase의 랩은 **취약 → 공격 → 방어 → 재공격 실패 확인** 순서다.
**"왜 중요한지"는 ①②를 겪은 직후에만 서술한다.** 랩 0절은 문제 제기만 하고,
원리 설명은 ③ 직전 3~5문장으로 제한한다. 긴 개념 해설은 전부 [기술리서치](02-기술리서치.md)로 보낸다.

| Phase | ① 취약 버전 | ② 직접 공격 | ③ 방어 도입 | ④ 재공격 |
|---|---|---|---|---|
| **1** | 해시 없는 JSON 글 목록 | 파일 열어 3번 글 교체 — **앱은 눈치도 못 챔** | `prev_hash` 체인 + `validate_chain` | 같은 변조 → 파손 지점 보고 |
| **2** | 검증 배지 없는 탐색기 | DB를 SQL로 직접 UPDATE | 매 조회마다 검증 + 파손 하이라이트 | 화면이 빨강으로 |
| **3** | 작성자 필드가 그냥 문자열 | **남의 이름으로 글 작성 성공** | ECDSA 서명 + nonce | 사칭·리플레이 모두 거부 |
| **4** | 난이도 0, 무한 블록 생성 | 1초에 블록 5천 개로 체인 장악 | PoW + 난이도 + 타임스탬프 규칙 | 같은 스크립트가 몇 시간 걸림 |
| **5** | 포크 선택 없이 "먼저 온 것 채택" | 두 노드가 **영구히 다른 체인** | 누적 난이도 fork choice + reorg | 자동 수렴 |
| **6** | 레이트 리밋 없는 tx 엔드포인트 | 멤풀 플러딩으로 노드 다운 | **글 길이 제한 / 레이트 리밋 / 피어 점수** (이 체인의 tx에는 금액이 없어 **수수료로는 못 막는다** → [ADR-0002](decisions/ADR-0002-on-chain-post-body.md)) | 공격 차단 로그 |
| **7** | 앵커 없는 공개 노드 | **서버 관리자 권한으로 과거 블록 재작성** | Sepolia `(height, 블록 해시)` 앵커링 | 온체인 블록 해시 불일치로 탐지 |

이 표를 한 줄로 요약하면: **각 Phase의 방어 기능은 그 Phase의 공격을 겪은 사람에게만 의미가 있다.**

## 8. 용어 사전

한↔영 대조와 설명은 [기술리서치 #용어사전](02-기술리서치.md#용어사전)에 둔다. 여기서는 **이 프로젝트에서 뜻이 좁혀진 것만** 적는다.

| 이 문서에서 | 뜻 |
|---|---|
| **랩(Lab)** | 위 4절 템플릿을 따르는 실습 1단위. 한 번 앉아서 끝낼 수 있는 크기 |
| **사이드 퀘스트(SQ)** | 본선 DoD에 안 들어가지만 기준선을 만들어 주는 곁가지 (예: Sepolia 맛보기) |
| **깨져보기** | 방어 없는 버전으로 공격을 **재현**하는 것. 실패를 상상하는 게 아니라 화면에서 보는 것 |
| **불변식(invariant)** | 구현이 뭐가 됐든 항상 참이어야 하는 성질. 랩 3절에 목록으로 주어지고, property 테스트가 이걸 검사 |
| **파손 지점(first_bad_index)** | 체인 검증이 최초로 실패한 블록 인덱스. bool 대신 이걸 반환하는 이유는 [개발계획서 6절](01-개발계획서.md#phase-1에-고정할-핵심-계약) |
