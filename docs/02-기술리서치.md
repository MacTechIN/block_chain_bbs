### 1.2 채택 / 탈락 기준

후보마다 아래 6개를 실측하고, **굵은 3개 중 하나라도 걸리면 "참고 자료"로 강등하거나 탈락**시켰다.

| 기준 | 무엇을 봤나 | 왜 |
|---|---|---|
| **라이선스** | GitHub API `license.spdx_id` | **라이선스가 없으면 법적으로 복사·재배포가 불가능하다.** "공개돼 있으니 써도 된다"가 아니다. 읽고 직접 다시 쓰는 것만 가능 |
| **마지막 push** | `pushed_at` | 2년 넘게 정지면 의존성으로 넣지 않는다. 읽기 자료로는 여전히 유효할 수 있다 |
| **테스트 유무** | 저장소 트리에서 `test*` 직접 확인 | **테스트가 0개인 교육용 저장소는 "동작한다"는 근거가 없다.** 이 프로젝트가 테스트 주도로 가므로 특히 중요 |
| 스타 수 | `stargazers_count` | **참고 지표일 뿐 품질 근거가 아니다.** ⭐8,039인 `dvf/blockchain`이 그 반례다 |
| 범위 | PoW / P2P / 서명 / 머클 / 난이도 / 모델(UTXO vs 계정) 6칸 | 우리 Phase 지도에 어디가 매핑되는지 |
| 아카이브 여부 | `archived` | `archived: true`면 그대로 탈락 |

추가로, **"스타 수에 속지 마라"는 원칙을 이 문서의 기본값으로 둔다.**
이 프로젝트에서 가장 유용한 자료 중 하나인 `lsilva01/dissecting-bitcoin-core-test`는 ⭐0이고,
가장 위험한 자료인 `dvf/blockchain`은 ⭐8,039다.

#### ❗ 검색으로 확인한 중요한 부재 3건

1. **FastAPI + Jinja2 + HTMX로 된 쓸 만한 블록체인 탐색기는 존재하지 않는다.**
   GitHub 검색 API로 반복 확인했고 나온 건 전부 ⭐0~5 미완성 습작이었다.
   → 이 조합은 **직접 만드는 수밖에 없다.** 그래서 `btc-rpc-explorer`가 유일하게 직역 가능한 원본이 된다.
2. **쓸 만한 Python gossip 라이브러리는 사실상 없다.** 위 탈락 목록의 4개가 전부다.
   → `py-libp2p`의 `floodsub.py` / `gossipsub.py`를 **읽는 것**이 유일하게 값어치 있는 Python 소스다.
3. **Python으로 된 블록체인 코어 property-based test 공개 저장소를 찾지 못했다("존재 확인 실패").**
   스마트컨트랙트 레벨 PBT는 여럿 있으나 체인 코어 레벨과는 결이 다르다.
   → **이 프로젝트가 직접 만드는 게 오히려 가치 있는 이유**이기도 하다.

  같은 `k`·같은 `r`이어도 **약 절반의 입력에서 `s`가 `n-s`로 갈린다.**
  → `sign_deterministic(msg, hashfunc=..., sigencode=sigencode_der_canonize)` (`canonize`가 low-S 정규화다).
  이걸 모르면 "내 구현이 틀렸나"로 몇 시간을 태운다.

**libp2p/specs — gossipsub** — https://github.com/libp2p/specs/blob/master/pubsub/gossipsub/ (⭐1,778 · 2026-09 · 200 OK)

- **v1.0 명세에서 확인한 기본 파라미터**:
  `D=6`(목표 mesh 차수) · `D_low=4` · `D_high=12` · `heartbeat_interval=1s` · `fanout_ttl=60s` · `mcache_len=5`(윈도우 수) · `mcache_gossip=3`(IHAVE에 쓸 윈도우) · `seen_ttl=2분`
- **핵심 메커니즘**: **GRAFT/PRUNE**으로 mesh 멤버십 유지 → heartbeat마다 `D_low` 미만이면 추가, `D_high` 초과면 제거 →
  mesh **바깥** 피어에게 **IHAVE**(본 메시지 ID 목록)를 lazy push → 받은 쪽이 **IWANT**로 본문 요청.
- **v1.1 추가**: 피어 스코어링(gossip threshold 미만이면 gossip에서 제외), opportunistic grafting(mesh 중앙값 점수가 낮으면 고득점 피어로 교체),
  **IWANT 스팸 방어**(피어당 응답 횟수 제한 + 가짜 message ID 광고 시 graylist).
- **이 프로젝트에서 볼 것**: **P5는 floodsub(= 받은 걸 모든 피어에게)부터 시작하고, P6에서 스팸 시나리오를 만든 뒤에야** gossipsub의 mesh + IHAVE/IWANT로 올라가라.
  그래야 "왜 mesh가 필요한가"가 체감된다. `D=6`, heartbeat 1초는 이 체인에서도 좋은 출발값이다.

#### 구현할 때 반드시 넣을 릴레이 규칙 (Bitcoin 실측)

- **3단 릴레이**: `INV`(ID만 광고) → `GETDATA`(요청) → `TX`/`BLOCK`(본문).
  **본문을 바로 브로드캐스트하지 마라** — 중복 전송이 O(N×크기)로 터진다.
- **Poisson 지연 배치**: Bitcoin은 피어별로 tx 광고를 랜덤 간격에 모아 보낸다 — **아웃바운드 평균 2초, 인바운드 5초.**
  목적은 **출처 프라이버시 + 멤풀 프로빙 방어**, 부수 효과로 "최저 지연 피어에게만 요청이 몰리는" 현상 완화.
  **P6 시빌 시나리오에서 이걸 껐다 켜보면 효과가 보인다.**
- **orphan pool**: 부모가 없는 tx를 담는 별도 풀. **Bitcoin 기본 상한 100개.** P3에서 필요하다.
- **피어당 rolling bloom filter**: 그 피어에게 이미 광고한 것을 추적해 재전송·프로빙을 막는다.
- **피어 발견**: DNS seed → 실패 시 하드코딩 fixed seed → `addr` gossip으로 addrman 확장.
  addrman은 **New/Tried 두 테이블 + 암호학적으로 키잉된 해시 버킷**으로 구성돼, 공격자가 특정 버킷을 결정적으로 노리지 못하게 한다(Eclipse 방어).
  **block-relay-only 연결**(tx·addr을 릴레이하지 않는 연결)이 파티션 공격과 토폴로지 추론을 동시에 막는다.
  참고: `bitcoin-core/bitcoin-devwiki` wiki "Addrman and eclipse attacks".

> **P5 종합 권고**: **전송은 "asyncio 순수 소켓으로 한 번 직접 짜본 뒤 → FastAPI WebSocket + `websockets`로 정착",
> gossip 알고리즘은 libp2p gossipsub 명세(D=6 / heartbeat 1s / IHAVE-IWANT)를 읽되 코드는 py-libp2p `floodsub.py`→`gossipsub.py`만 참고,
> wire 포맷·핸드셰이크·테스트 하네스는 Bitcoin Core `test/functional/test_framework/{p2p,messages}.py`를 정답지로 삼아라.**
> py-libp2p는 되살아났지만 **trio 기반이라 FastAPI 스택에 의존성으로 넣지 마라.**

**Bitcoin Core `src/pow.cpp`** — https://github.com/bitcoin/bitcoin · `C++` · ⭐90,201 · 2026-09 · **MIT** (소스 직접 확인)

- `GetNextWorkRequired()` (**L14~**): `(nHeight+1) % DifficultyAdjustmentInterval() != 0` 이면 **그대로 이전 nBits 반환** — 2016블록 경계에서만 조정한다.
- **off-by-one 버그 (원문)**:
  ```cpp
  int nHeightFirst = pindexLast->nHeight - (params.DifficultyAdjustmentInterval()-1);
  ```
  → 2016블록 구간인데 **측정하는 간격은 2015개다.** 실제 목표 간격이 10분이 아니라 **10 × 2016/2015 ≈ 10.005분.**
  하드포크가 필요해 고치지 않고 방치 중이다.
- `CalculateNextWorkRequired()` (**L52~**) — **4배 clamp**:
  ```cpp
  if (nActualTimespan < params.nPowTargetTimespan/4) nActualTimespan = params.nPowTargetTimespan/4;
  if (nActualTimespan > params.nPowTargetTimespan*4) nActualTimespan = params.nPowTargetTimespan*4;
  ```

- **🔴 베끼지 말 것**: **10초 블록 체인에 2016블록 방식은 부적합하다.**

**ASERT (aserti3-2d) 공식 명세** — https://upgradespecs.bitcoincashnode.org/2020-11-15-asert/
(미러: `bitcoincashorg/bitcoincash.org` 의 `spec/2020-11-15-asert.md`)

```
next_target = anchor_target * 2 ** ((time_delta - ideal_block_time * (height_delta + 1)) / halflife)
```

- 고정 앵커 기준 **절대 스케줄**이다. rolling window 없이 상태가 `(anchor_height, anchor_time, anchor_target)` **3개뿐.**
- **이 프로젝트에서 볼 것**: **P4에서 실제로 채택할 1순위.**
  10초 블록에 halflife를 짧게(10~30분) 잡으면 **매 블록 부드럽게 반응하면서 진동이 없다.**
  상태가 작아 SQLite 스키마에 쉽고, **공식이 순수 함수라 hypothesis property 테스트에 최적이다**
  ("time_delta가 커지면 target 단조 증가", **"halflife만큼 늦으면 target이 정확히 2배"**).
- **베끼지 말 것**: 정수 근사(cubic approximation)는 합의 호환성 때문에 복잡하다.
  장난감 체인은 정수 시프트 + 고정소수점으로 단순화하되 **노드 간 완전 결정적**이어야 한다.

| `GetBlockProofEquivalentTime()` | `src/chain.cpp` **L135~** | 두 체인의 work 차이를 **"몇 초치 채굴"**로 환산 |
| `CBlockIndexWorkComparator` | `src/node/blockstorage.h` **L138~141** | `setBlockIndexCandidates`(std::set)를 이걸로 정렬 → **후보 tip이 항상 chainwork 순** |
| 최소 chainwork 게이트 | `src/chain.h` **L435** | — |

**핵심**: 공격자가 낮은 난이도 구간을 악용하면 **블록 수는 더 많지만 chainwork는 훨씬 작은** 체인을 만들 수 있다.
사토시의 초기 구현은 블록 개수를 썼고 **곧 chainwork로 교체됐다.**

- **이 프로젝트에서 볼 것**: **P5.** `blocks` 테이블에 `chain_work` 컬럼(256bit hex `TEXT` 또는 `BLOB`), tip 선택은 `ORDER BY chain_work DESC`.
  Python은 `int`가 임의정밀도라 `(1 << 256) // (target + 1)`로 끝난다 — **C++보다 쉬운 지점이다.**
- **읽을 글**: "The Longest Blockchain is not the Strongest Blockchain" https://cryptoservices.github.io/blockchain/consensus/2019/05/21/bitcoin-length-weight-confusion.html ·
  learnmeabitcoin "Target"(**nBits compact 인코딩 최고 해설**) https://learnmeabitcoin.com/technical/mining/target/
- **🔴 베끼지 말 것 — 동점 처리**: chainwork가 같을 때 Bitcoin Core는 **"먼저 받은 것"을 유지한다.**
  **해시 크기 비교 같은 tie-break를 쓰면 노드마다 결론이 갈린다.** **수신 순서(first-seen)를 명시적으로 기록해라.**

**disconnectpool의 핵심 아이디어**: 롤백한 블록의 tx를 **즉시 멤풀에 되돌리지 않는다.**
대부분은 곧 연결될 새 체인 블록에도 들어 있어 어차피 다시 지워지기 때문이다. 별도 버퍼에 모았다가 **reorg 완료 후 한 번에** 처리한다.
(근거 PR: https://github.com/bitcoin/bitcoin/pull/9208)

- **이 프로젝트에서 볼 것**: **P5 reorg 뼈대를 그대로.**
  ① 공통 조상 찾기 → ② 새 tip까지 블록 수집 → ③ 현재 tip부터 fork point까지 역순 disconnect(txn을 disconnectpool로) → ④ fork point부터 새 tip까지 connect → ⑤ 실패 시 전부 롤백 → ⑥ disconnectpool 정리 후 멤풀 복원.
  **SQLite면 ③~⑤를 하나의 트랜잭션으로 묶어 원자성을 공짜로** 얻는다 — Core가 손으로 하는 롤백을 `ROLLBACK`으로 대체할 수 있다.
- **베끼지 말 것**: `ActivateBestChainStep`의 부분 분할(cs_main 락 홀딩 시간 단축)은 단일 프로세스 장난감 체인엔 불필요한 복잡도다.
  그리고 멤풀 복원 시 **nonce/리플레이 검증을 다시 통과시켜야 한다** — 되돌린 tx가 새 체인에선 이미 무효일 수 있다.

**btcsuite/btcd** — https://github.com/btcsuite/btcd · `Go` · ⭐6,709 · 2026-09 · **ISC** — **같은 로직의 훨씬 읽기 쉬운 버전.**
- **먼저 볼 파일**: `blockchain/chain.go` — **`getReorganizeNodes()` L512**(detach/attach 목록을 두 `list.List`로 계산 — **이 함수 하나가 reorg의 본질이다**), `connectBlock()` L576, `disconnectBlock()` L727, `reorganizeChain()` L877, `connectBestChain()` L1161
  `blockchain/difficulty.go` — `CalcWork()` L67, `calcNextRequiredDifficulty()` L136, **`CompactToBig()` L45 / `BigToCompact()` L53** (nBits 인코딩 — **P4 Python 이식의 최고 원본**)
- **볼 것**: C++이 힘들면 **여기부터.** `getReorganizeNodes` → `reorganizeChain` 순으로 읽으면 P5가 한 시간에 이해된다.

#### 타임스탬프 검증

`ContextualCheckBlockHeader` — `src/validation.cpp` **L4088~** (소스 직접 확인):

```cpp
// L4100 하한: MTP
if (block.GetBlockTime() <= pindexPrev->GetMedianTimePast())
    return state.Invalid(..., "time-too-old", ...);
// L4105~4114 timewarp 방어 (BIP94, testnet4/regtest)

}
// L4116 상한: 2시간 미래

    return state.Invalid(..., "time-too-new", ...);
```

상수: `src/chain.h` **L29** `MAX_FUTURE_BLOCK_TIME = 2*60*60` · **L231** `nMedianTimeSpan = 11`(직전 11블록 중앙값) · `src/pow.h` **L35** `MAX_TIMEWARP = 600`

- **BIP113 (MTP)** — https://bips.dev/113/ — 2016-07에 BIP68/112와 함께 활성화.
  locktime 평가를 블록 timestamp → **MTP(median time past)**로 변경. **이유**: 블록 timestamp는 2시간 미래로 조작 가능해
  채굴자가 시간잠금 tx를 **의도보다 일찍** 유효화할 수 있었다. MTP는 11블록 중앙값이라 **단일 채굴자가 못 흔든다.**
  (`validation.cpp` **L4149**에서 locktime 컷오프로 사용되는 것 확인)
- **Timewarp 공격** — https://www.bitmex.com/blog/the-timewarp-attack · https://bitcoinops.org/en/topics/time-warp/
  - **원리**: 난이도 조정 구간의 **첫 블록 timestamp만 과거로 끌어내리고** 나머지는 정상 증가 → `nActualTimespan`이 부풀려져 **난이도가 계속 내려간다.**
    MTP 하한이 있어도 "MTP보다 크기만 하면 된다"는 제약뿐이라 **반복 가능하다.** Bitcoin의 off-by-one(2015 간격)이 구조적 원인이기도 하다.
  - **수정**: **BIP94**(testnet4, Core 28.0 / 2024-10) — 조정 구간 첫 블록 timestamp가 이전 블록보다 **600초 이상 과거일 수 없다.**
    메인넷은 "Great Consensus Cleanup"(BIP54) 논의 중. PR #29775(도입), #30647(7200s→600s), #30681.
- **이 프로젝트에서 볼 것**: **P4에 세 검사(MTP 하한 / 미래 상한 / 조정 블록 600초)를 전부 넣고, P6에 timewarp를 반드시 포함시켜라.**
  **검사를 끄고 공격이 성공하는 걸 보인 뒤 켜서 막히는 걸 보이면 가장 극적인 데모다.**
- **베끼지 말 것**: 10초 블록에 `MAX_FUTURE_BLOCK_TIME = 2시간`은 터무니없다. **블록 간격의 수십 배(60~120초)로 줄여라.**
  `nMedianTimeSpan = 11`도 재검토 대상 — 창을 늘리면 조작 내성은 오르지만 **체인 정지 후 재시작이 어려워진다.**
- 추가: Jameson Lopp, "Bitcoin Timestamp Security" https://blog.lopp.net/bitcoin-timestamp-security/

## 4. 주제별 정리

여기부터가 **랩 문서의 `→ [기술리서치 #앵커]` 링크가 도착하는 곳**이다.
각 절은 "이 주제에서 헷갈리는 것 + 원문 링크 + 함정" 세 가지만 담는다. **실습 절차는 [학습계획서](03-학습계획서.md)에 있다.**

### 해시함수

**SHA-256은 표준 라이브러리 `hashlib`로 충분하다.** 이 프로젝트에서 직접 구현할 대상이 아니다
(→ 직접 구현 경계는 [개발계획서 5절](01-개발계획서.md#5-기술-스택)).
대신 **해시의 성질 세 가지**가 이후 전부의 전제가 된다.

| 성질 | 뜻 | 어디서 걸리나 |
|---|---|---|
| **결정성** | 같은 입력 → 항상 같은 출력 | "같은 글인데 해시가 다르다"의 원인은 해시 함수가 아니라 **입력을 만드는 방식**이다 → [#직렬화](#직렬화) |
| **눈사태 효과** | 1비트만 바뀌어도 출력의 절반가량이 바뀐다 | 변조 감지의 전부. "조금 바꿨으니 조금 바뀌겠지"는 틀렸다 |
| **역상 저항 / 충돌 저항** | 출력에서 입력을 못 얻고, 같은 출력을 내는 두 입력을 못 찾는다 | 머클 트리의 **2차 역상 공격**과 CVE-2012-2459가 정확히 이 지점 → [#머클트리](#머클트리) |

- **SHA256d (이중 해시)**: 비트코인은 `SHA256(SHA256(x))`를 쓴다. 이유는 **길이 확장 공격(length-extension) 회피**다.
  우리 체인은 정규화 직렬화가 길이를 확정하므로 단일 SHA-256으로도 되지만, **비트코인과 같은 값을 비교하고 싶다면 SHA256d를 써야 한다.** 무엇을 쓰든 **ADR에 적고 끝까지 안 바꾼다.**
- **RIPEMD-160**: 주소 도출의 `HASH160 = RIPEMD160(SHA256(pubkey))`에 쓰인다.
  ⚠️ **OpenSSL 3.x에서 `ripemd160`이 legacy provider로 밀려나 `hashlib.new("ripemd160")`이 환경에 따라 실패한다.** P3에서 실제로 만나는 문제다.
- **직접 구현 참고**: `karpathy/cryptos`가 SHA-256과 RIPEMD-160을 **의존성 0으로 바닥부터** 구현해 뒀다 (→ [3.3](#33-암호--서명)). 읽기용.
- **눈으로 보는 교보재**: `anders94/blockchain-demo`의 `Hash` 탭 — 타이핑하는 대로 SHA-256이 갱신된다. https://andersbrownworth.com/blockchain/hash

### 직렬화

**이 프로젝트에서 가장 과소평가되기 쉬운 주제다.** 그리고 Phase 1에서 고정하지 않으면 뒤에서 되돌릴 수 없다.

**왜 중요한가**: 합의는 "같은 데이터 → 같은 해시"를 전제한다.
그런데 `json.dumps`는 **키 순서 · 공백 · 유니코드 이스케이프 · float 표현**이 환경마다 달라질 수 있다.
노드 A와 B가 같은 블록에 다른 해시를 내면 **체인이 즉시 갈라진다.**
→ **직렬화를 합의 규칙의 일부로 못박아야 한다.** (이 프로젝트의 결정은 [ADR-0001](decisions/ADR-0001-canonical-serialization.md))

#### RFC 8785 JCS (JSON Canonicalization Scheme)

- **RFC 본문**: https://www.rfc-editor.org/rfc/rfc8785
- **trailofbits/rfc8785.py** — https://github.com/trailofbits/rfc8785.py
  `Python` · ⭐13 · push **2026-09-16** · **Apache-2.0** · PyPI 0.1.4 (2024-09-27)
  - **RFC 8785의 순수 파이썬 구현이 실제로 존재함을 확인했다.** 의존성 없음.
  - **먼저 볼 파일**: `src/rfc8785/_impl.py` (**400줄 미만 — 직접 구현 연습용으로 이상적**), `test/assets/input/*.json`
  - **베끼지 말 것**: JCS의 ES6 number serialization(Ryū 기반)은 **까다롭다.**
    **🔴 애초에 float을 체인에 넣지 마라.** 금액은 정수(satoshi 단위), 타임스탬프도 정수.
- **cyberphone/json-canonicalization** — ⭐149 · 2024-12 — **JCS 공식 테스트 벡터의 원본.**
  `testdata/input|output|outhex/` 각 **6파일**. → 골든 파일 활용은 [#레퍼런스-테스트](#레퍼런스-테스트)

#### 대안 비교

| 방식 | 평가 |
|---|---|
| **RFC 8785 JCS** | ✅ 명세가 있고 테스트 벡터가 있고 Python 구현이 있다. **텍스트라 탐색기 디버깅이 쉽다** |
| **cbor2** (6.1.4 / 2026-08, ⭐305, MIT, 휠 48개) | ⭕ **가장 현실적인 대안.** RFC 8949 §4.2에 canonical form이 정의돼 있다. 단 **바이너리라 P2 탐색기 디버깅이 불편** |
| msgpack | ❌ **정규 형식 명세가 없어 합의에 부적합.** wire 전송용으로만 |
| `canonicaljson` (Matrix.org) | ❌ **JCS와 규칙이 다르다.** 이름 때문에 혼동하기 쉽다 |
| `dag-cbor` | ❌ ⭐17, 2023-12 방치 |
| PyPI `json-canonicalization` | ❌ **404, 존재 확인 실패** |

#### 실제로 걸리는 함정

- **`tuple`은 JSON에서 `list`로 돌아온다.** 왕복(round-trip) 후 해시가 달라지는 가장 흔한 원인.
- **`int` 타임스탬프가 `float`으로 돌아오는 경우** — 역시 해시가 달라진다.
- **비ASCII 문자의 이스케이프** — 한글 게시판이므로 반드시 만난다. `ensure_ascii` 설정에 따라 바이트가 달라진다.
- **키 정렬 기준** — JCS는 **UTF-16 코드 단위 기준** 정렬이다. Python의 기본 문자열 정렬(코드 포인트)과 **BMP 밖 문자에서 갈린다.** 이모지를 쓰는 게시판이면 걸린다.

> **권고**: `rfc8785/_impl.py`를 읽고 **직접 짠 뒤 cyberphone의 6쌍 골든 벡터로 교차 검증**하라. 그리고 float을 체인에 넣지 마라.

### 체인구조

한 블록이 **이전 블록의 해시를 자기 입력에 포함**하면, 과거를 고치는 순간 그 뒤가 전부 어긋난다.
이 한 문장이 블록체인의 전부이고, Phase 1에서 눈으로 확인하게 되는 것이다.

- **레퍼런스**: `jamesob/tinychain`의 단일 파일 구조가 **체인 + 멤풀 + UTXO + reorg를 한 화면에서 보는** 가장 좋은 예다 (→ [3.1](#31-교육용-python-블록체인-구현체)).
  단 **전역 변수(`active_chain`, `mempool`, `utxo_set`) + `with_lock` 데코레이터 구조는 SQLite 설계에 그대로 못 옮긴다.**
- **블록 인덱스라는 별도 개념**: 체인은 "블록의 리스트"가 아니다. **블록 트리 + 그 위에서 고른 최적 경로**다.
  Bitcoin Core의 `CBlockIndex`(`src/chain.h`)와 `chainActive`가 이 둘을 분리한다.
  Phase 1에서는 리스트로 시작해도 되지만, **Phase 5에서 포크가 생기는 순간 트리로 바뀐다는 것을 미리 알고 있어야** 구조가 덜 깨진다.
  tinychain 소스의 `# #realname chainActive` 주석이 이 대응을 알려준다.
- **"체인이 깨졌다"는 상태는 실제 네트워크에 존재하지 않는다.** 실제 노드는 유효하지 않은 블록을 **받지 않고 버린다.**
  깨진 체인을 보관하고 "몇 번부터 깨졌다"를 보고하는 것은 **학습용 장치**다. 이 차이를 알고 써야 한다.
- **⚠️ 반례**: `dvf/blockchain`은 블록 dict 전체를 통째로 `json.dumps` 해싱하고 PoW가 블록 내용과 무관하다.
  **"체인처럼 생겼지만 체인이 아닌 것"의 표본**이다 → [#언제-블록체인이-필요한가](#언제-블록체인이-필요한가)

### 블록헤더

**헤더와 바디를 분리하는 이유는 하나다: 채굴 루프가 헤더만 해싱하게 하기 위해서.**
nonce를 바꿀 때마다 글 1,000개를 다시 직렬화할 수는 없다. 바디는 **머클 루트 32바이트로 요약**되어 헤더에 들어간다.

- **비트코인 블록 헤더는 정확히 80바이트**다: `version`(4) + `prev_block_hash`(32) + `merkle_root`(32) + `timestamp`(4) + `nBits`(4) + `nonce`(4).
  - 명세: https://developer.bitcoin.org/reference/block_chain.html
  - **SPV(라이트 클라이언트)가 헤더만 받아 검증할 수 있는 것이 이 80바이트 덕분이다.**
- **이더리움 헤더**는 `parentHash` 외에 **상태 트리 루트(`stateRoot`)**가 더 있다 — "거래 목록"이 아니라 **"계정 상태 전체"를 해시로 요약**한다는 차이다.
- **nBits compact 인코딩** (P4에서 실제로 필요해진다)
  - 32비트에 256비트 target을 욱여넣는 형식: 상위 1바이트가 지수, 하위 3바이트가 가수.
  - **최고 해설**: learnmeabitcoin "Target" https://learnmeabitcoin.com/technical/mining/target/
  - **Python 이식의 최고 원본**: btcd `blockchain/difficulty.go`의 **`CompactToBig()` L45 / `BigToCompact()` L53** (→ [3.5](#35-합의--난이도--포크-선택--reorg))
  - Python판 정답 참고: jimmysong `code-ch09/helper.py`의 `bits_to_target`, `calculate_new_bits`
  - ⚠️ `15Dkatz/python-blockchain-tutorial`은 **nBits 없이 int로 난이도를 직접 다룬다.** 간단하지만 실제 체인과 대응되지 않는다.
- **이 프로젝트의 `Block` 필드 집합은 Phase 1에서 고정한다** — `nonce`·`difficulty`가 Phase 4까지 안 쓰여도 자리를 비워 두는 이유는
  **나중에 추가하면 모든 블록 해시가 바뀌기 때문**이다. 결정 내용은 [개발계획서 6절](01-개발계획서.md#6-코드-구조).
  - **`Block.difficulty`의 의미는 compact target(nBits)으로 확정했다.** "선행 0비트 개수"로 저장하지 않는다 —
    그러면 **P4의 ASERT가 낸 연속 target을 표현할 수 없어 매 블록 반올림**되고, *"halflife만큼 늦으면 target이 정확히 2배"* property가 통과하지 못하며,
    **P5의 chainwork(`2**256 // (target+1)`)도 계단식으로만 증가**한다.
    선행 0비트는 **랩의 직관 설명과 화면 표시 어휘**로만 쓴다. (같은 이유로 위의 `15Dkatz/...` 경고가 우리에게 그대로 적용된다.)
- **화면에 무엇을 어떤 순서로 보여줄 것인가**는 btc-rpc-explorer의 실제 필드 순서를 그대로 쓰면 된다 (→ [3.2](#32-블록-탐색기-ui)).

### 머클트리

> 🔴 **Phase 1 필독. 이 절을 읽지 않고 머클 루트를 구현하면 거의 확실히 취약점이 들어간다.**

머클 트리는 두 가지를 준다: ① 바디를 32바이트로 요약 ② **"이 글이 이 블록에 있다"를 log N개 해시로 증명**.
휴대폰이 비트코인을 검증할 수 있는 이유가 ②다.

#### CVE-2012-2459 — 홀수 리프 복제의 함정

**Bitcoin Core `src/consensus/merkle.cpp` L16~49에 대문자 경고 주석이 통째로 박혀 있다. 원문 첫 줄:**

> `/*     WARNING! If you're reading this because you're learning about crypto and/or designing a new system that will use merkle trees, keep in mind that the following merkle tree algorithm has a serious flaw related to duplicate txids, resulting in a vulnerability (CVE-2012-2459).`

```
        A                  A
      /  \               /   \
    B     C            B       C
   / \    |           / \     / \
  D   E   F          D   E   F   F
 / \ / \ / \        / \ / \ / \ / \
 1 2 3 4 5 6        1 2 3 4 5 6 5 6
```

레벨의 해시 개수가 홀수면 **마지막 것을 복제**해서 다음 레벨을 만든다. 그 탓에
`[1,2,3,4,5,6]`과 `[1,2,3,4,5,6,5,6]`이 **같은 루트**를 만든다.

**이유를 정확히 짚어 두자 — "`hash(F)`와 `hash(F,F)`가 둘 다 C가 되기 때문"이 아니다.**
왼쪽 6리프 트리에서도 `D,E,F` **3노드 레벨에서 마지막 `F`가 복제**되어 `C = H(F,F)`가 된다. 양쪽 모두 `C = H(F,F)`다.
충돌의 원인은 **3노드 레벨의 복제가 4노드 레벨(`D,E,F,F`)과 완전히 동일한 상위 레벨(`B=H(D,E)`, `C=H(F,F)`)을 만든다**는 것이다.
즉 **복제가 "리프를 실제로 하나 더 붙인 것"과 구분되지 않는다.** 그래서 `[...5,6]`과 `[...5,6,5,6]`이 같은 루트로 접힌다.

**공격 시나리오**: 트랜잭션을 복제한 변조 블록은 **머클 루트도 블록 해시도 원본과 같다.**
노드가 이걸 검증 실패시키고 **"이 블록 해시는 영구 무효"로 마킹**하면, 이후 도착하는 **진짜 유효 블록까지 거부**한다 → **DoS.**

**Core의 방어**: `uint256 ComputeMerkleRoot(std::vector<uint256> hashes, bool* mutated)` —
**`mutated` out-파라미터**로 변조를 보고하고, 동일한 두 해시를 짝짓게 되는 경우를 "머클 루트가 틀린 블록"과 동일 취급한다.
**중요: 모든 레벨에서 검사한다.** 상위 레벨에서도 동일 쌍이 나타날 수 있어 **리프만 검사하면 뚫린다.** (`src/consensus/merkle.h` L17~26)

#### 이 프로젝트의 선택

| 선택지 | 설명 | 평가 |
|---|---|---|
| **① promote (채택)** | 홀수 노드를 **복제하지 말고 그대로 위 레벨로 올려보낸다** | ✅ **취약점 자체가 성립하지 않는다.** 비트코인 호환이 필요 없는 학습용 체인엔 이게 정답 |
| ② Bitcoin 호환 + `mutated` | 비트코인과 동일하게 복제하되 **`mutated` 플래그를 반드시 구현하고 모든 레벨에서 검사** | ⭕ 비트코인과 값을 맞춰야 할 때만 |

- **property test로 세울 불변식**: **"서로 다른 tx 리스트 두 개는 절대 같은 머클 루트를 갖지 않는다."**
  hypothesis로 리스트 길이를 1~20으로 흔들면 **복제 방식에서는 반례가 나온다.**
  이것이 **이 프로젝트에서 가장 교육적인 실패 테스트**가 될 것이다.
- ⚠️ **`jamesob/tinychain`의 `get_merkle_root()`(L917)에도 이 방어가 없다.** 주교재라고 그대로 베끼면 같은 함정에 빠진다.
- **2차 역상 공격 방어**: 리프 해시와 내부 노드 해시를 **도메인 분리**하라(예: 접두 바이트 `0x00` / `0x01`).
  안 하면 "내부 노드 값을 리프인 척" 제시하는 증명이 통과할 수 있다. Certificate Transparency(RFC 6962)가 이 방식을 쓴다.
- **함께 읽기**: Bitcoin Optech "Merkle tree vulnerabilities" https://bitcoinops.org/en/topics/merkle-tree-vulnerabilities/
  (64바이트 트랜잭션 혼동 공격 등 추가 함정 — **본문 내용까지는 미확인**, 링크 유효성만 확보)
- **머클 증명 Python 구현 참고**: jimmysong `code-ch11/merkleblock.py`

### 영속화

Phase 1은 JSON 파일, Phase 2는 SQLite다. 전환 비용을 0에 가깝게 만드는 것이 이 주제의 목표다.
(전환 시점과 DoD는 [개발계획서 Phase 2](01-개발계획서.md#phase-2--블록-탐색기-v1--저장소-교체-35일))

#### 원자적 쓰기 (atomic write)

**증상**: 저장 도중 프로세스가 죽으면 JSON 파일이 **문법 중간에서 잘린다.** 다음 로드에서 `JSONDecodeError` → **체인 전체를 잃는다.**

**표준 해법**: 같은 디렉터리에 임시 파일로 전부 쓰고 → `flush()` + `os.fsync()` → **`os.replace()`로 교체**.
`os.replace`는 POSIX에서 원자적이고 Windows에서도 원자적으로 동작한다(`os.rename`과 달리 대상이 있어도 실패하지 않는다).
- 표준 문서: https://docs.python.org/3/library/os.html#os.replace
- 디렉터리 엔트리까지 확실히 하려면 부모 디렉터리도 `fsync`해야 한다는 점은 **DB가 아닌 파일 저장소의 한계**다 — 그래서 Phase 2에서 SQLite로 간다.

#### SQLite로 가는 이유

- **트랜잭션이 공짜로 따라온다.** [3.5](#35-합의--난이도--포크-선택--reorg)의 reorg 절차 ③~⑤를 **하나의 트랜잭션으로 묶으면** Core가 손으로 하는 롤백이 `ROLLBACK` 한 줄이 된다.
- `chain_work` 같은 **256비트 정수는 hex `TEXT` 또는 `BLOB`**으로 저장하고 tip 선택은 `ORDER BY chain_work DESC`.
  (hex TEXT로 저장할 때는 **고정 길이 zero-padding**을 해야 문자열 비교 순서가 수치 순서와 일치한다.)
- **WAL 모드**(`PRAGMA journal_mode=WAL`)가 "채굴 프로세스가 쓰는 동안 웹 요청이 읽는" 패턴에 맞는다.
- 공식 문서: https://www.sqlite.org/wal.html · https://www.sqlite.org/isolation.html · Python `sqlite3`: https://docs.python.org/3/library/sqlite3.html
- ⚠️ Python 3.12부터 `sqlite3`의 기본 autocommit 동작 관련 설정(`autocommit` 속성)이 추가됐다.
  **묵시적 트랜잭션에 기대지 말고 `BEGIN`을 명시하라** — reorg 원자성이 여기 걸린다.

#### `Storage` 추상화

두 백엔드(JSON, SQLite)가 **같은 테스트를 통과해야 한다**는 것이 이 추상화의 검증 기준이다.
인터페이스 시그니처와 선언 시점은 [개발계획서 6절](01-개발계획서.md#6-코드-구조)에 고정돼 있다.
- Python `Protocol`(구조적 서브타이핑) 문서: https://docs.python.org/3/library/typing.html#typing.Protocol · PEP 544 https://peps.python.org/pep-0544/
- **append-only가 인터페이스 수준의 설계다.** 수정·삭제 메서드를 만들지 않으면 "정상 경로로는 변조가 불가능"해진다.
  실습용 `/admin/tamper`는 **이 인터페이스를 우회해 저장소를 직접 건드리는 방식**으로 만들어야 그 대비가 드러난다.

### 노드 저장구조

Phase 5에서 노드가 여러 개가 되는 순간, **"어느 노드의 체인인가"를 파일시스템 수준에서 갈라 놓아야 한다.**

- **🔴 docker compose에서 `--scale` / `deploy.replicas`를 쓰면 안 된다.** 실측 결과:
  레플리카들이 **같은 named volume을 공유해 체인 데이터가 섞이고**, 컨테이너가 자기 인덱스를 모르며(hostname이 랜덤 ID), **포트 배정이 매번 달라진다.**

- **재시작 후 체인이 보존되는가**가 이 주제의 검증 기준이다. 컨테이너 안의 경로가 아니라 **볼륨에 붙어 있어야** 보존된다.
- **키 파일은 체인 데이터와 같은 디렉터리에 두지 마라.** `.gitignore`에 `*.key`, `keystore/`가 Phase 0부터 선등록돼 있는 이유다.
- **참고 저장소**: `cometbft/cometbft` 루트의 compose — **고정 IP 멀티노드 패턴**이라 특정 노드 쌍만 분할하기 쉽다.
  ⚠️ `satwikkansal/python_blockchain_app`은 파이썬 진입점이라 눈에 띄지만 **`network_mode: host`라 분할 실험이 불가능**하다.
  → **bridge 네트워크로 고치는 것 자체가 좋은 첫 연습**이 된다.
  `danielemiliogarcia/simchain`은 분할 실험 설계도로 가장 부합하나 **⭐2 1인 프로젝트라 설계만 참고**할 것.

#### hypothesis 활용

- **P1 — `@given` + `@st.composite`**: `st_tx`(`author` 주소 bytes20, `body` text, `ts` int, `nonce` int, `sig` None) → `st_block` → `st_chain`(제네시스부터 유효 연결).
  **금액 필드는 없다.** 이 체인의 tx는 `{author, body, ts, nonce, sig}`이고 값을 옮기지 않는다 (→ [ADR-0002](decisions/ADR-0002-on-chain-post-body.md)).
- **P5 — `RuleBasedStateMachine`** (도입 시점은 **P5**다. [Phase 5 DoD](01-개발계획서.md#phase-5--p2p-네트워크와-합의-710일)가 이걸 요구한다):
  `@initialize`로 제네시스, `@rule`로 mine / submit_to_mempool / reorg / rollback, `@invariant`로 불변식.
  **P3·P4의 불변식은 `@given`으로 충분하다** — 상태기계가 필요해지는 건 노드가 여럿이고 메시지 순서가 변수가 되는 P5부터다.
  **`Bundle`은 "만든 블록을 다시 입력으로 쓰는" 재귀 구조에 맞고, `consumes()`는 멤풀 tx가 블록에 포함되면 제거되는 모델링에 그대로 쓰인다.**
- **shrinking**: reorg 버그를 잡으면 **"블록 3개 + 재구성 1회" 같은 최소 반례**로 줄여 준다.
- **`@settings` 권장값**: 로컬 `max_examples=50, stateful_step_count=30, deadline=None`(**PoW 때문에 deadline 해제는 필수**) /
  CI `max_examples=500, stateful_step_count=100, derandomize=True`.
  **P4 채굴 테스트는 난이도를 1로 고정한 테스트 전용 파라미터를 반드시** 둬라.

#### 불변식 체크리스트 (Phase별)

| Phase | 불변식 | 형태 |
|---|---|---|
| P1 | `deserialize(serialize(x)) == x` | `@given` |
| P1 | 정규화 직렬화는 dict 키 순서에 불변 | `@given` |
| P1 | 머클 증명은 포함 leaf에 항상 통과 / 변조 leaf에 항상 실패 | `@given` |
| P1 | **서로 다른 tx 리스트는 절대 같은 머클 루트를 갖지 않는다** (CVE-2012-2459) | `@given` |
| P3 | 유효 서명 항상 통과 / 1비트 변조 시 항상 실패 | `@given` |
| P3 | 같은 nonce 재사용 tx는 **항상** 거부 | `@given` |
| P3 | 멤풀에 확정된 tx가 남아 있지 않다 | `@given` |
| P4 | 블록 해시 ≥ target인 블록은 항상 거부 | `@given` |
| P4 | ASERT는 순수 함수다 — time_delta 증가 → target 단조 증가, halflife만큼 늦으면 target 정확히 2배 | `@given` |
| P5 | **누적 난이도가 더 큰 체인만 채택** (길이가 아니라!) | `@invariant` |
| P5 | reorg 후 **패배 분기의 tx가 유실 없이 멤풀로 복귀**하고, 확정된 글 집합 = 최적 체인의 글 집합 | `@invariant` |
| P5 | 최적 체인 높이는 단조 증가, 감소는 reorg 시에만 + 그때 chainwork는 증가 | `@invariant` |
| P6 | 이중지불 시도는 **어떤 도착 순서에도** 하나만 확정 | `@rule` 시퀀스 |
| (P8) | 총 공급량 = 제네시스 + Σ(블록 보상) / reorg 후 잔고 합계 보존 | `@invariant` — **본선 체인의 tx에는 금액이 없다**(→ [ADR-0002](decisions/ADR-0002-on-chain-post-body.md)). Phase 8 코인 트랙을 할 때만 |

> **`@rule`/`@invariant`로 표시된 항목은 P5에서 `RuleBasedStateMachine`이 도입된 뒤**에 상태기계로 옮겨 검사한다.
> 그전에는 같은 성질을 `@given`으로 검사한다. 상태기계를 P3에 미리 들이지 마라 — 모델링할 상태가 아직 없다.

#### 비동기 테스트 — 반드시 아는 함정

- ⚠️ **pytest-asyncio 1.x에서 `event_loop` fixture가 완전히 제거됐다**(1.0.0 / 2025-05).
  **인터넷 예제 대부분이 이 fixture를 쓴다 — 전부 깨진다. 복붙 금지.**
  1.3.0(2025-11) Python 3.9 지원 중단 / **1.4.0(2026-05)** pytest **≥8.4** 요구, `event_loop_policy` 오버라이드 **deprecated** → 새 훅 **`pytest_asyncio_loop_factories`**.
- ⚠️ **`asyncio.sleep()`은 루프의 `time()`을 쓰므로 freezegun / time-machine으로 빨라지지 않는다.**
  "10초 뒤 타임아웃"을 즉시 돌리려면
  ① **의존성 주입**(`await self._sleep(10)` → 테스트에서 `asyncio.sleep(0)`으로 교체)이 정답,
  ② 또는 커스텀 루프 팩토리로 `loop.time()`을 가상 시계로(pytest-asyncio 1.4의 `pytest_asyncio_loop_factories`가 공식 지원).
  **`time-machine`의 진짜 용처는 블록 타임스탬프 검증**(미래 블록 거부, MTP 규칙) **테스트다.**
- **anyio 선택 가이드**: FastAPI를 쓰므로 **anyio가 이미 의존성에 들어와 있다**(Starlette 기반).
  **추천: anyio 플러그인 단독**(백엔드 파라미터화는 끄고 asyncio만). 문서 https://anyio.readthedocs.io/en/stable/testing.html
  **구조적 동시성(task group)**으로 노드를 관리하면 "한 노드가 죽으면 그룹 전체가 정리된다"가 공짜다 — **좀비 태스크 누수가 P2P flaky의 주범이다.**
- **flaky 대응 규칙**
  - **전역 `random` 금지.** `self._rng = random.Random(seed)`를 노드마다 주입하고 **seed를 로그에 찍어라.**
  - **금지: `await asyncio.sleep(0.1)`로 "동기화".** flaky 1번 원인이다. `anyio.Event`로 명시적 신호를 써라.
  - 모든 P2P 테스트에 **`anyio.fail_after()` 타임아웃 상한** — 데드락이 CI를 무한정 잡는 걸 막는다.

#### 결정적 시뮬레이션 테스트 (DST) — 이 프로젝트에서 가장 임팩트 큰 설계

원형은 **FoundationDB**이고 현대 구현은 **TigerBeetle의 VOPR**다 (→ [3.7](#37-테스트)).
핵심 한 줄: **모든 비결정성(시간, 난수, I/O, 스케줄)을 단일 지점으로 모으고 시드로 제어한다.**

Python 축소판의 뼈대:

1. 노드는 **실제 소켓을 모른다** — `Transport` 프로토콜에만 의존한다.
2. 프로덕션 `TcpTransport` / 테스트 `SimTransport` — 메시지를 **`(도착시각, seq, src, dst, payload)` 힙**에 넣고 시뮬레이터가 **시각 순으로 배달**한다.
3. 드롭 / 중복 / 재정렬 / 지연은 **주입된 `random.Random(seed)`로만** 결정한다. **`time.time()` 호출 금지, `clock.now()` 주입.**
4. 매 스텝 후 불변식 체커를 실행한다 (TigerBeetle `state_checker.zig` 역할).
5. 실패하면 **시드 하나만 출력**하면 완전히 재현된다.
6. **이 시뮬레이터를 hypothesis `RuleBasedStateMachine`의 백엔드로 쓰면 시드 탐색 + shrinking을 공짜로 얻는다.**

이 조합이면 **P6 공격 시나리오(이중지불, 셀피시 마이닝, 이클립스)를 수작업 시나리오 없이 자동 탐색 + 최소 반례로 축소**할 수 있다.
설계를 그대로 옮길 대상은 TigerBeetle `src/testing/packet_simulator.zig`와 quickcheck-dynamic의 Model/Action 분리다.

#### 외부 구현과의 교차 검증

- **서명**: `ecdsa`는 **RFC 6979 결정적 nonce**를 구현하므로 **같은 입력 → 같은 서명**이 나온다.

### 테스트넷

**Phase 1 직후의 사이드 퀘스트와 Phase 7 본편에서 쓴다.** 목적이 서로 다르다:
사이드 퀘스트는 **기준선 만들기**(내 장난감 체인 vs 진짜 체인), Phase 7은 **앵커링**이다 (→ [#앵커링](#앵커링)).

- **Sepolia** — 이더리움의 현행 주력 테스트넷.
  - 공식 안내: https://ethereum.org/en/developers/docs/networks/
  - **선택 이유**: 자료·Etherscan 지원이 가장 두텁고 faucet 접근성이 좋다. (Holesky는 밸리데이터 테스트 성격이 강하다.)
- **web3.py** — https://web3py.readthedocs.io/ · 저장소 https://github.com/ethereum/web3.py
  트랜잭션 전송, `data` 필드에 임의 바이트 싣기, 영수증 대기, 컨트랙트 호출까지 전부 여기서 끝난다.
- **RPC 엔드포인트**: Alchemy / Infura. 둘 다 무료 티어에 **요청 한도**가 있다 — 폴링 루프를 돌리면 금방 닿는다.
- **Faucet**: 정책이 자주 바뀐다. **메인넷 잔고 요구, 계정 나이 요구, 일일 한도**가 붙는 경우가 흔하다.
  ⚠️ **이 문서에 특정 faucet URL을 적어 두지 않는다** — 조사 시점에도 정책이 유동적이었고, 적어 두면 곧 틀린 정보가 된다. `ethereum.org`의 네트워크 문서에서 현행 목록을 확인하라.
- **Etherscan (Sepolia)** — https://sepolia.etherscan.io/ — tx 해시로 조회하면 `Input Data`에 내가 넣은 바이트가 그대로 보인다.
  **"내가 만든 해시가 남의 체인에 박혀 있다"를 눈으로 보는 것이 이 퀘스트의 전부다.**
- **계정 키 관리**: 여기서 만드는 키는 **테스트넷 전용이고 실제 가치가 없다.** 그래도 `.env` / `*.key`는 커밋하지 마라 — **습관을 여기서 들이는 것이 목적**이다.
- **위험**: faucet 고갈 · 정책 변경 · RPC 한도로 앵커링이 막힐 수 있다.
  → **앵커링은 실패해도 로컬 체인이 정상 동작하는 선택적 기능으로 분리**하는 것이 이 프로젝트의 결정이다 ([개발계획서 8절](01-개발계획서.md#8-위험과-대응)).

### 앵커링

**앵커링은 "내 체인의 상태 요약을 남의 체인에 기록해 두는 것"이다.**
그러면 **서버를 완전히 장악한 공격자도 과거를 못 지운다** — 로컬에서 재채굴해 앞뒤를 맞춰도 **온체인에 박힌 값과 불일치**하기 때문이다.

- **무엇을 올리나**: 블록 하나를 통째로 올릴 수는 없다. **`(height, 32바이트 블록 해시)`**면 충분하다.
  **머클 루트가 아니다.** 머클 루트는 **그 블록의 tx 집합만** 커밋하므로, 공격자가 3번 블록을 고치고 42번까지 재채굴해도
  **42번의 글 집합이 그대로면 루트도 그대로**라 대조를 통과해 버린다. 과거 전체를 누적 커밋하는 값은 `prev_hash`가 쌓인 **블록 해시**다.
  → [ADR-0003](decisions/ADR-0003-anchor-target.md)
  Phase 1에서 만든 머클 루트는 **블록 해시의 입력**으로 여기에 쓰인다 — 선후 관계는 그대로다 ([순서 제약 7번](01-개발계획서.md#7-순서-제약)).
- **두 가지 방식**
  1. **tx `data` 필드에 싣기** — 컨트랙트 없이 즉시 가능. Phase 1 사이드 퀘스트가 이 방식이다.
  2. **최소 컨트랙트에 기록** — `Anchor.sol`처럼 `(height, block_hash, timestamp)`를 저장하고 이벤트를 발행. 조회가 구조화된다. Phase 7 본편.
     (머클 루트를 부가 필드로 함께 올려도 되지만 **불일치 판정에는 쓰지 않는다** → [ADR-0003](decisions/ADR-0003-anchor-target.md))
- **타임스탬핑이라는 관점**: 앵커링의 본질은 **"이 데이터가 이 시각 이전에 존재했다"는 증명**이다.
  선행 사례:
  - **OpenTimestamps** — https://opentimestamps.org/ · 저장소 https://github.com/opentimestamps/opentimestamps-client
    비트코인에 머클 루트를 앵커하는 표준적 구현. **여러 문서를 하나의 머클 트리로 묶어 루트 하나만 올리는 집계(aggregation)** 방식이 핵심 아이디어다.
  - **Certificate Transparency (RFC 6962)** — https://datatracker.ietf.org/doc/html/rfc6962
    append-only 로그 + 머클 트리 + **일관성 증명(consistency proof)**. "로그가 과거를 고치지 않았다"를 증명하는 구조가 이 프로젝트가 하려는 것과 정확히 같다.
    **머클 트리의 도메인 분리(리프 `0x00` / 내부 `0x01`)도 여기서 온다** → [#머클트리](#머클트리)
- **Solidity 최소 컨트랙트 + Remix 배포**를 고른 이유는 **툴체인(Foundry/Hardhat) 학습이 본 목표를 밀어내지 않게** 하기 위해서다
  ([개발계획서 5절](01-개발계획서.md#5-기술-스택)). Remix: https://remix.ethereum.org/ · Solidity 문서: https://docs.soliditylang.org/
- **앵커 주기의 트레이드오프**: 자주 올릴수록 보호 구간이 촘촘해지지만 **가스가 든다.**
  "마지막 앵커 이후의 블록들은 아직 보호되지 않는다"는 사실을 **탐색기 화면에 명시**하는 것이 정직한 설계다.
- **검증 방향**: 로컬 블록 해시 → 온체인 블록 해시 대조. **불일치를 발견하는 쪽이 로컬**이라는 점에 주의하라.
  진짜 공격자는 탐색기 코드도 고칠 수 있다. **앵커의 가치는 "제3자가 독립적으로 대조할 수 있다"는 데 있다** — Etherscan 링크를 노출하는 이유다.

### 호스팅

> 이 절은 배포 조사(주제 8)의 결과다. Phase 7 계획에 이미 반영돼 있다 ([개발계획서 Phase 7](01-개발계획서.md#phase-7--배포--공개-테스트넷-앵커링-47일)).

블록체인 노드가 요구하는 것은 일반 웹앱과 다르다. **세 가지가 동시에** 필요하다:

1. **상시 실행** (sleep 없음) — 채굴과 P2P 연결이 끊기면 안 된다
2. **임의 inbound TCP** (HTTP 전용 아님) — 노드 간 포트를 열어야 한다
3. **영속 디스크** (읽기전용 FS 아님) — 체인 데이터가 남아야 한다

#### 비교

|---|---|---|---|---|---|
| **Oracle Always Free** | ✅ | ✅ | ✅ | **무료** | ✅ **세 조건을 동시에 주는 유일한 무료 옵션** |

시간을 쓰지 마라.

#### ⚠️ Oracle Always Free의 유휴 회수 정책

**7일간 CPU · 네트워크 · 메모리가 모두 20% 미만이면 회수 대상**이 된다.
**한가한 데모 노드가 정확히 여기 걸린다.**
→ **주기적 더미 트랜잭션 크론**을 배포 체크리스트에 넣어야 한다 (Phase 7 DoD 항목).

#### 그 외 운영 사항

- 도메인 + HTTPS(리버스 프록시), 헬스체크 엔드포인트, 시드 노드 주소를 **설정으로 외부화**할 것.
- **🔴 `/admin/tamper` 파괴 엔드포인트는 기본 비활성 + 환경변수 명시 활성.**
  인터넷에 열려 있으면 **누구나 내 체인을 깨뜨릴 수 있다.** 배포 전 체크리스트에 항목으로 박아라.
- **불변 게시판에 개인정보를 쓰면 삭제할 수단이 없다.** 공개 노드라면 글 길이 제한 · 레이트 리밋 · 경고 표기가 선택이 아니라 필수다.

### 언제 블록체인이 필요한가

> 이 절은 **의욕이 떨어질 때 읽는 절**이자, 이 프로젝트가 만드는 것의 **정직한 한계**를 적는 절이다.

**블록체인이 필요한 조건은 "분산된 신뢰"다.** 세 가지가 동시에 성립할 때만 값을 한다:

1. **여러 당사자가 같은 상태를 봐야 하는데**
2. **서로를 신뢰하지 않고**
3. **모두가 믿을 중앙 관리자를 세울 수 없다**

하나라도 빠지면 **중앙 DB가 더 빠르고 싸고 안전하다.**

| 상황 | 답 |
|---|---|
| 운영자 한 명이 DB를 관리한다 | **PostgreSQL.** 감사 로그가 필요하면 append-only 테이블 + 서명 |
| 여러 조직이 있지만 **모두가 신뢰하는 제3자가 있다** | 중앙 원장 + **로그 투명성**(Certificate Transparency 방식) → [#앵커링](#앵커링) |
| 데이터 무결성만 필요하다 | **해시 체인 + 타임스탬핑.** 합의도 채굴도 필요 없다 |
| 참여자가 알려져 있고 신뢰된다 | **Raft / Paxos** 같은 permissioned 합의. **결정적 확정(finality)**을 얻고 reorg가 없다 → [3.5의 Raft 카드](#35-합의--난이도--포크-선택--reorg) |
| 참여자가 **익명이고 무제한**이다 | **PoW/PoS.** 대가로 **확률적 확정만** 가능하고 reorg를 감수한다 |

**"확률적 확정"이 이 프로젝트의 핵심 체험이다.** Phase 5에서 확정된 줄 알았던 글이 reorg로 사라지는 장면,
Phase 6에서 컨펌 수별 성공률 표를 직접 채우는 것 — 그게 이 차이의 실물이다.

#### 🔴 반례 — `dvf/blockchain` (⭐8,039)

**별 8천 개가 넘는데 포크 선택이 `if length > max_length` 한 줄이다**(`blockchain.py` **L90**).
서명이 없고, 머클이 없고, PoW가 블록 내용과 무관하다 (→ [3.1의 경고 카드](#31-교육용-python-블록체인-구현체)).

**이게 정확히 피해야 할 "최장 체인" 오해다.** 올바른 규칙은 **누적 난이도(chainwork) 최대**이고,
동점이면 **먼저 받은 것(first-seen)**이다 → [3.5의 포크 선택 절](#35-합의--난이도--포크-선택--reorg).

이 저장소가 주는 교훈은 두 가지다:
1. **"블록체인처럼 생긴 것"과 블록체인은 다르다.** 블록 리스트 + 해시 필드가 있다고 체인이 아니다. **검증 규칙이 곧 블록체인이다.**
2. **스타 수는 정확성의 근거가 아니다.** → [1.2 평가 기준](#12-채택--탈락-기준)

- "The Longest Blockchain is not the Strongest Blockchain" — https://cryptoservices.github.io/blockchain/consensus/2019/05/21/bitcoin-length-weight-confusion.html
- Satoshi 백서 §11 "Calculations" — https://bitcoin.org/bitcoin.pdf — **확정이 왜 확률인지가 여기서 시작한다**

### 용어사전

한글 문서와 영어 식별자 사이에서 헷갈릴 때 보는 표다. **코드 식별자는 영어를 쓴다**(→ [CLAUDE.md](../CLAUDE.md)).

| 한국어 | 영어 / 식별자 | 한 줄 뜻 |
|---|---|---|
| 해시 | hash | 임의 길이 입력 → 고정 길이 출력. 이 프로젝트는 SHA-256 |
| 이중 해시 | SHA256d | `SHA256(SHA256(x))`. 비트코인 방식 |
| 눈사태 효과 | avalanche effect | 입력 1비트 변화가 출력 절반을 바꾼다 |
| 정규화 직렬화 | canonical serialization / `canonical_bytes` | 해시 입력을 한 가지 형태로 못박는 것 → [#직렬화](#직렬화) |
| 블록 | block | 헤더 + 바디 |
| 블록 헤더 | block header | 해싱 대상. 비트코인은 80바이트 → [#블록헤더](#블록헤더) |
| 이전 블록 해시 | `prev_hash` / parentHash | 체인을 잇는 필드 |
| 제네시스 블록 | genesis block | 0번 블록. 이전 해시가 없다 |
| 높이 | height | 제네시스로부터의 블록 번호 |
| 팁 | tip / chain tip | 현재 최적 체인의 마지막 블록 |
| 머클 루트 | merkle root | 바디 전체를 32바이트로 요약 → [#머클트리](#머클트리) |
| 머클 증명 | merkle proof / inclusion proof | "이 항목이 그 루트에 포함된다"의 log N 증명 |
| 리프 / 내부 노드 | leaf / internal node | 도메인 분리 대상 |
| 트랜잭션 | transaction (tx) | 이 프로젝트에선 "글 1건" |
| 멤풀 | mempool | 아직 블록에 안 들어간 tx 대기열 |
| 고아 블록 | orphan block | 부모를 아직 못 받은 블록 |
| 스테일 블록 | stale block | 경쟁에서 진 유효 블록 (mempool.space의 `Stale Block` 배지) |
| 작업증명 | Proof of Work (PoW) | 블록 생성에 계산 비용을 붙이는 것 |
| 난이도 | difficulty | 목표값이 얼마나 작은가 |
| 목표값 | target | 블록 해시가 이보다 작아야 유효 |
| 압축 목표값 | nBits / compact | 256비트 target을 32비트로 인코딩 |
| 난이도 재조정 | difficulty adjustment (DAA) | 블록 간격을 목표에 수렴시키는 규칙 |
| 누적 난이도 | chainwork / `nChainWork` | **포크 선택의 기준.** 길이가 아니다 |
| 포크 선택 규칙 | fork choice rule | 여러 체인 중 하나를 고르는 규칙 |
| 재구성 | reorg (reorganization) | 최적 체인이 바뀌어 블록을 되돌리고 다시 연결하는 것 |
| 공통 조상 | fork point / common ancestor | reorg 계산의 시작점 |
| 되돌림 풀 | disconnectpool | 롤백한 블록의 tx를 모아 두는 버퍼 |
| 최초 수신 우선 | first-seen | chainwork 동점일 때의 규칙 |
| 확정 | finality | 결정적(Raft) vs **확률적**(PoW) |
| 컨펌 | confirmation | 그 블록 위에 쌓인 블록 수 |
| 초기 블록 다운로드 | IBD (initial block download) | 빈 노드가 전체 체인을 받아오는 과정 |
| 전파 | gossip / relay | 3단 릴레이: `INV` → `GETDATA` → `TX`/`BLOCK` |
| 플러드섭 / 가십섭 | floodsub / gossipsub | 전부에게 보내기 / mesh + IHAVE-IWANT |
| 메시 | mesh | gossipsub에서 본문을 주고받는 피어 집합 (`D=6`) |
| 피어 스코어링 | peer scoring | 시빌·스팸 방어의 실제 수단 |
| 네트워크 분할 | network partition | 일부 노드가 서로 못 보는 상태 |
| 이클립스 공격 | eclipse attack | 한 노드의 연결을 공격자가 전부 차지 |
| 시빌 공격 | sybil attack | 가짜 신원을 다수 만들기 |
| 이중 지불 | double spend | 같은 자원을 두 번 쓰기. 이 프로젝트에선 **이중 게시** |
| 셀피시 마이닝 | selfish mining | 블록을 숨겼다 푸는 전략 (Eyal & Sirer) |
| 타임워프 공격 | timewarp attack | 조정 구간 첫 블록 시각을 끌어내려 난이도를 낮추기 |
| 중앙값 과거 시각 | MTP (median time past) | 직전 11블록 timestamp의 중앙값 (BIP113) |
| 서명 | signature | 개인키로 만들고 공개키로 검증. **암호화가 아니다** |
| 결정적 nonce | deterministic nonce (RFC 6979) | 같은 입력 → 같은 서명. **테스트 재현성의 전제** |
| 리플레이 방지 nonce | replay-protection nonce | 같은 tx의 재전송을 막는 카운터. 위의 nonce와 **다른 것** |
| 채굴 nonce | mining nonce | PoW 탐색용 숫자. 위 둘과 또 다른 것 |
| 주소 | address | 공개키의 해시 + 버전 바이트 + 체크섬 |
| 체크섬 | checksum | base58check의 끝 4바이트. 오타를 잡는다 |
| 키스토어 | keystore | 개인키 저장소. **잃으면 복구 불가** |
| 앵커링 | anchoring | 내 체인의 루트를 남의 체인에 기록 → [#앵커링](#앵커링) |
| 속성 기반 테스트 | property-based test (PBT) | 예시가 아니라 **불변식**을 검증 |
| 불변식 | invariant | 언제나 참이어야 하는 성질 |
| 반례 축소 | shrinking | 실패 입력을 최소 형태로 줄이기 |
| 결정적 시뮬레이션 테스트 | DST (deterministic simulation testing) | 시드 하나로 완전 재현 → [#pytest](#pytest) |

(이 결정은 [개발계획서 5절](01-개발계획서.md#5-기술-스택)과 Phase 3 항목에 반영돼 있다.)

#### 학습 경로 3단계

1. **(a) 순수 파이썬 직접 구현 — P3 첫 구간**
   `karpathy/cryptos`의 `blog.ipynb` 정독 → `curves.py` + `ecdsa.py`를 **보지 않고 재작성**한 뒤 대조.
   유한체 역원은 `pow(a, -1, p)`, Jacobian 좌표 점 연산은 `eth_keys/backends/native/jacobian.py` 참고, 결정적 nonce는 RFC 6979.
   **검증**: `ecdsa` 라이브러리와 **동일 입력에 동일 서명**. 단 `sign()`이 아니라 **`sign_deterministic()`**을 써야 결정적이고(기본 `sign()`은 랜덤 nonce),
   비교 전에 **인코딩(DER)과 low-S를 맞춰야** 한다 — `sigencode=sigencode_der_canonize`.
2. **(b) `ecdsa` 라이브러리 — P3 후반**
   자기 구현을 오라클로 대체. **이 시점에 README 경고 + CVE-2024-23342를 읽고 왜 순수 Python으로는 못 고치는지 이해한다.**
3. **(c) `coincurve` 교체 — P4 직전**
   **백엔드 추상화 인터페이스를 먼저 만들고**(eth-keys `backends/base.py` 패턴) 교체.
   **property test로 두 백엔드의 출력 일치를 검증**한다 — **단 "동일 인코딩(DER) + low-S 정규화 후" 일치다.**
   날것끼리 비교하면 약 절반의 입력에서 실패한다(위 3.3 카드의 경고).
   그리고 이 대조 테스트는 **`ecdsa`로도 서명을 생성**한다 — **테스트 전용 키에 한해 허용**되며,
   금지 대상은 `src/bbschain/`의 프로덕션 키 생성·서명 경로다 ([개발계획서 Phase 3 DoD](01-개발계획서.md#phase-3--지갑--서명--트랜잭션-46일)).

### 5.3 테스트 플러그인

플러그인별 판정과 버전은 [#pytest](#pytest)의 표에 있다. 여기서는 **선택의 갈림길만** 정리한다.

| 갈림길 | 선택 | 근거 |
|---|---|---|
| anyio 플러그인 vs pytest-asyncio | **anyio 단독** (백엔드 파라미터화는 끄고 asyncio만) | FastAPI(Starlette)가 **이미 anyio를 끌고 온다.** 의존성이 하나 준다. `loop.call_later` 같은 저수준 시간 조작이 필요할 때만 pytest-asyncio |
| freezegun vs time-machine | **time-machine** | C 확장으로 프로세스 레벨 대체 → 더 빠르고 정확. freezegun은 **1년 넘게 정체**이고 **C 확장이 읽는 시간은 못 속인다** |
| 시간 제어 vs 의존성 주입 | **둘 다, 용처를 나눠서** | `asyncio.sleep()`은 **어느 도구로도 빨라지지 않는다** → 슬립은 **주입**으로, **블록 타임스탬프 규칙 테스트는 time-machine**으로 |
| xdist 병렬화 | **P4 PoW만. P5 제외** | P2P 테스트는 **포트 충돌·공유 상태로 flaky**해진다 |
| 스냅샷 vs 골든 벡터 | **골든 벡터로 먼저 맞다는 걸 확인하고 스냅샷으로 굳힌다** | 스냅샷은 "무엇이 맞는가"를 모른다 → [#레퍼런스-테스트](#레퍼런스-테스트) |

조사 과정에서 **널리 퍼진 잘못된 정보 3건**을 확인했다. 검색하다 아래를 만나면 이 절을 기준으로 삼아라.

### (1) otterscan 정식 저장소

- ❌ `wmitsuda/otterscan` — ⭐**31** / 2024-04. **구 개인 저장소다.**
- ✅ **`otterscan/otterscan`** — ⭐**1,423** / 2026-02 / MIT. **이쪽이 정식이다.**
- 검색 결과 상위에 구 저장소가 뜨는 경우가 있다. 스타 수 차이(31 vs 1,423)로 즉시 구분된다.

### (2) Rosenfeld 이중지불 논문의 arXiv 번호

- ✅ **arXiv:1402.2009** — https://arxiv.org/abs/1402.2009
- **논문 작성일은 2012-12-11이지만 arXiv 등록은 2014-02**라 번호가 **1402 대역**이다.
- ❌ **"2012 arXiv"로 찾으면 나오지 않는다.** 인용문마다 연도가 2012로 적혀 있어 혼동이 생긴다.

### (3) ApeWorX 소유권 이전

- `github.com/ethereum/eth-account` → **`ApeWorX/eth-account`**
- `github.com/ethereum/eth-keys` → **`ApeWorX/eth-keys`**
- `gh api`로 **리다이렉트를 직접 확인**했다. 옛 URL도 리다이렉트되지만, 문서·이슈 링크는 새 경로를 쓰는 편이 낫다.

### (+) 함께 확인한 저자 오인용

- **"Checking laws of the blockchain with property-based testing" (IWBOSE 2018)의 저자는 Chepurnoy & Rathee다.**
  **Lamela Seijas / Thompson으로 잘못 인용되는 경우가 많다** — 검색으로 정정 확인했다.

## 8. 이 문서를 고쳐야 할 때

- 새 라이브러리·저장소를 조사했을 때 → 3절에 **같은 카드 형식**으로 추가한다. **"베끼지 말 것" 칸을 비워 두지 마라.**
- 링크가 죽었을 때 → 지우지 말고 **[1.3 탈락 목록](#13-탈락-목록--이미-확인했고-안-되는-것들)으로 옮긴다.** "이건 죽었다"가 정보다.
- 비교 결과가 [개발계획서 5절](01-개발계획서.md#5-기술-스택)의 스택 결정을 뒤집을 때 → **먼저 `docs/decisions/`에 ADR을 쓰고** 계획서를 고친 뒤 여기를 갱신한다.
- 랩에서 새 앵커가 필요해졌을 때 → **4절에 헤딩을 추가한다.** 다른 문서가 이미 링크를 걸어 둔 앵커는 **절대 이름을 바꾸지 마라.**
