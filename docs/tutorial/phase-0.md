## 0단계에 블록체인이 없다. 왜 맨 앞인가

솔직히 말하면 이 단계는 재미없다. 블록도 해시도 나오지 않는다.
그런데도 맨 앞에 있는 이유가 있다.

**앞으로 모든 단계의 합격 판정이 "테스트가 통과하는가" 하나로 표현되기 때문이다.**

Phase 1의 합격 기준도, Phase 5의 체인 수렴도, Phase 7의 앵커 대조도 전부 그 형태다
([개발계획서 2절](../01-개발계획서.md#2-phase-지도)).
그러니 먼저 물어야 할 것이 있다. **그 판정을 믿을 수 있나?**

체중계에 비유하면 쉽다.
다이어트를 시작하기 전에 체중계부터 확인한다. 눈금이 0에 있는지, 어제와 오늘 같은 값을 내는지,
어디에 놓느냐에 따라 값이 흔들리지는 않는지. **흔들리는 체중계로 잰 숫자는 아무 의미가 없다.**

Phase 0에서 만드는 것이 그 체중계다. 문서에서는 **판정기**라고 부르겠다.
판정기에는 요구가 하나 더 붙는다. **판정기 자신이 믿을 만한지를 판정할 수 있어야 한다.**
랩 세 개가 그 세 겹을 하나씩 만든다.

| 랩 | 만드는 것 | 이 겹이 없으면 |
|---|---|---|
| 0.1 | 판정 규칙 — 기계가 맞고 틀림을 말한다 | 틀린 코드가 조용히 남는다 |
| 0.2 | 판정 대상의 동일성 — 항상 같은 물건을 잰다 | "어느 폴더에서 돌렸느냐"에 따라 답이 달라진다 |
| 0.3 | 판정의 자동 반복 — 빈 컴퓨터에서도 잰다 | "내 컴퓨터에서는 되는데요"를 배포 직전에 처음 만난다 |

> ### ⚠️ 이 Phase는 이미 끝나 있다
>
> 사용자 요청에 따라 **랩 0.1 / 0.2 / 0.3을 에이전트가 대신 구현했다.**
> 기록은 [PROGRESS.md](../PROGRESS.md)에 있다.
>
> 그래서 이 문서를 읽는 방식이 다른 Phase와 다르다.
> **"만들기 전에 읽는 글"이 아니라 "이미 깔려 있는 것을 확인하며 읽는 글"이다.**
> 각 절의 "손으로 확인하기"를 실제로 돌려 보면 설명한 것이 네 저장소에 그대로 있다.
> 직접 만들어 보고 싶으면 각 절의 "이제 할 일"에 지우는 방법을 적어 뒀다.

## Lab 0.1 — 실패하는 테스트부터 보기

> **언제 읽나**: 랩의 "1. 먼저 깨져보기"를 해본 뒤, "3. 과제" 전에.
> **대응 랩**: [Lab 0.1](../labs/phase-0-setup.md#lab-01--실패하는-테스트부터-보기)

### 한 줄로 말하면

코드가 틀렸을 때 **기계가 대신 알려 주도록** 만드는 단계다.

### 지금 어디쯤인가

여기가 프로젝트의 첫 칸이다. 앞에서 한 것은 없다.

앞으로 "체인이 망가졌는지"를 판단해야 하는 순간이 수백 번 온다.
블록이 10개일 때는 터미널 출력을 눈으로 훑어 확인할 수 있다. 200개가 되면 못 한다.
게다가 눈으로 보는 판정은 **어제의 나와 오늘의 나가 다른 기준을 쓴다.**

그래서 가장 먼저 하는 일은 기능을 만드는 것이 아니라, **기계가 판정하게 만들어 두는 것**이다.

### 이 랩이 답하려는 질문

> **내가 방금 고친 코드가 틀렸다는 걸, 누가 나한테 말해 주지?**

### 배경 — 알아야 할 것

**테스트는 특별한 물건이 아니다. 그냥 함수다.**

이름이 `test_`로 시작하는 평범한 파이썬 함수를 파일에 적어 둔다.
그 안에서 검사하고 싶은 것을 `assert`로 쓴다. 끝이다. 새로 배울 문법은 없다.

```python
# tests/test_demo.py — 설명용 예시다. 랩 과제 파일과는 다른 것이다.
def test_two_plus_three_is_five() -> None:
    assert 2 + 3 == 5
```

**pytest는 이 함수들을 찾아서 대신 돌려 주는 도구다.** 하는 일은 셋뿐이다.

1. **찾는다** — 정해진 이름 규칙에 맞는 파일과 함수를 모은다
2. **돌린다** — 하나씩 호출한다
3. **보고한다** — `assert`가 틀린 함수를 실패로 표시하고, 무엇이 어떻게 달랐는지 보여 준다

3번이 pytest의 진짜 값어치다. `assert` 한 줄만 썼는데 출력은 이만큼 나온다.

```
E       AssertionError: assert {'a': 1, 'b': 2} == {'a': 1, 'b': 3}
E         Common items:
E         {'a': 1}
E         Differing items:
E         {'b': 2} != {'b': 3}
```

어느 키가 다른지, 값이 각각 뭔지까지 알아서 펼쳐 준다.
그래서 `assertEqual` 같은 전용 함수를 외울 필요가 없다. **파이썬 기본 문법 `assert`만 쓰면 된다.**
(어떻게 이게 가능한지는 이 절 맨 아래 접이식에 있다. 지금은 몰라도 된다.)

마지막으로 알아 둘 것 하나. **`pytest`를 돌려서 나오는 색은 두 가지다.**
초록은 "검사한 것이 전부 맞았다", 빨강은 "적어도 하나가 틀렸다".
그런데 **초록에는 뜻이 하나 더 숨어 있다.** 그 얘기가 질문 3이다.

### 랩과 연결하기

랩 ①("먼저 깨져보기")에서 하는 일은 30초짜리다. 아직 안 해봤다면 이런 일이 일어난다.

1. 아무 함수나 하나 만든다. 두 수를 더하는 함수 같은 것
2. 손으로 한 번 실행해서 "잘 되네" 확인한다
3. 그 함수를 **일부러 틀리게 고친다.** `+`를 `-`로
4. 아무것도 실행하지 않고 다음 작업으로 넘어간다

**여기서 네가 볼 것은 "아무것도 일어나지 않는 장면"이다.**
경고도, 빨간 줄도, 에러 메시지도 없다. 터미널은 조용하다.

중요한 건 "틀렸다"가 아니다. **"틀렸다는 사실이 아무 데도 기록되지 않았다"** 는 쪽이다.
판정기가 없는 상태의 기본값은 초록이 아니다. **무응답**이다.
그리고 무응답은 사람이 초록으로 읽는다.

이미 해봤다면 이 점을 짚어 두자 — 그 조용함은 지금은 무해하지만,
Phase 1에서 해시 계산이 미묘하게 틀린 채 블록 50개가 쌓이면 똑같이 조용하다.

### 질문 1 — pytest는 어떤 파일과 어떤 함수를 테스트로 인식하나? (규칙을 정확히)

pytest는 마법으로 테스트를 찾지 않는다. **이름 규칙 몇 개**로 찾는다.

pytest가 폴더를 훑을 때는 이름이 `test_`로 시작하거나 `_test.py`로 끝나는 파일만 들여다본다.
그 안에서 이름이 `test`로 시작하는 함수를 모은다.
클래스로 묶고 싶으면 클래스 이름을 `Test`로 시작하면 된다.
단 그 클래스에 `__init__`이 있으면 pytest는 그 클래스를 건너뛴다. 조용히 건너뛴다.

정리하면 이렇다. **세 번째 열을 눈여겨봐라.**

| 대상 | 기본 규칙 | 언제 적용되나 | 바꾸는 설정 키 |
|---|---|---|---|
| 파일 | `test_*.py` **또는** `*_test.py` | **폴더를 훑을 때만** | `python_files` |
| 클래스 | `Test`로 시작. **`__init__`이 있으면 수집 안 함** | 언제나 | `python_classes` |
| 함수·메서드 | `test`로 시작 | 언제나 | `python_functions` |

**나머지 절반은 "어디서부터 찾나"다.**

- 명령에 **경로를 주면** 그 경로만 본다. `uv run pytest tests/unit/test_merkle.py`
- 경로를 **안 주면** 설정 파일의 `testpaths` 값을 본다
- 그것도 없으면 현재 폴더부터 전부 훑는다

`conftest.py`는 예외다. 이 파일은 테스트가 아니라 **폴더 단위 설정 파일**이다.
pytest가 테스트보다 먼저 읽는다. 공통 준비 코드를 여기 두면 그 아래 테스트 전부가 쓴다.
Phase 1에서 바로 쓰게 된다.

**여기서 자주 틀리는 것 하나.**

파일 이름 규칙은 **pytest가 스스로 폴더를 뒤질 때 쓰는 필터**다.
파일 경로를 콕 집어 주면, 이름이 규칙에 안 맞아도 pytest는 그 파일을 테스트 모듈로 읽는다.

```
uv run pytest /tmp/collect_demo/helper_module.py   # 1 test collected — 이름이 달라도 수집된다
uv run pytest /tmp/collect_demo                    # no tests collected — 같은 파일이 여기선 빠진다
```

**"이름을 안 맞추면 무조건 안 돈다"는 틀린 요약이다.**
이름과 **부르는 방식**이 같이 결정한다.
단 함수 이름 규칙은 그대로다 — 경로를 지정해도 `test`로 시작하지 않는 함수는 돌지 않는다.

**이 프로젝트의 설정이 같은 원리의 예다.** `pyproject.toml`에 이렇게 들어 있다.

```toml
[tool.pytest.ini_options]
testpaths = ["tests/test_smoke.py"]
addopts = "-ra"
```

왜 `tests` 폴더 전체가 아니라 파일 하나인가.
`tests/unit/`과 `tests/integration/`에는 **Phase 1 구현을 기다리는 테스트**가 미리 들어 있다.
구현할 모듈이 아직 없으니 지금 돌리면 전부 실패한다. 그게 정상이다.
하지만 그대로 두면 **`uv run pytest`가 영원히 빨강**이 된다.

빨강이 기본값이 되는 순간 빨강은 정보가 아니게 된다. 판정기가 죽는 것이다.
그래서 기본 실행에서 빼 뒀다. Phase 1이 끝나면 `["tests"]`로 되돌린다.

그런데도 이 명령은 **그대로 동작한다.**

```
uv run pytest tests/unit/test_merkle.py -v
```

`testpaths`는 **경로 인자가 없을 때만** 쓰이는 값이기 때문이다. 경로를 주면 그쪽이 이긴다.

**두 필터가 같은 성질을 공유한다.**
`testpaths`도, 파일 이름 규칙도 **pytest가 스스로 찾아 나설 때만** 작동한다.
내가 경로를 직접 지정하면 둘 다 비켜선다.

이 저장소에서 숫자로 확인된다.

```
uv run pytest --collect-only -q          # 2 tests collected   ← testpaths 가 정한 범위
uv run pytest --collect-only -q tests    # 68 tests collected  ← 경로를 주면 testpaths 는 무시된다
```

"기본 실행은 초록, 지정하면 Phase 1 테스트 68개도 볼 수 있다"가 설정 한 줄로 성립한다.

### 질문 2 — `assert`가 실패하면 파이썬은 무엇을 던지나? pytest는 그걸로 뭘 하나?

**파이썬 쪽 답은 한 줄이다.** `assert`는 이것과 같은 뜻이다.

```
if not 조건:
    raise AssertionError(메시지)
```

그래서 던져지는 것은 **`AssertionError` 하나**다. pytest 전용 예외 같은 건 없다.

**pytest 쪽은 그 예외를 잡아서 보고한다.**
테스트 함수에서 예외가 올라오면 그 테스트를 실패(`F`)로 기록한다.
그게 `AssertionError`면 한 걸음 더 간다 — **양쪽 값이 어떻게 달랐는지를 펼쳐서 보여 준다.**

배경 절에서 본 그 출력이 이것이다. 같은 `assert` 한 줄인데, 그냥 파이썬으로 돌리면 이렇게 나온다.

```
AssertionError
```

끝이다. 무엇이 달랐는지는 알려 주지 않는다.
**두 출력의 차이가 pytest를 쓰는 이유의 절반쯤 된다.**

이 기능의 이름은 **assertion rewriting**이다.
pytest가 테스트 파일을 읽어 들이는 시점에 `assert` 문을 손봐서, 실패했을 때 쓸 설명을 미리 준비해 둔다.
**지금은 "그런 게 있다"까지만 알면 된다.** 어떻게 하는지는 아래 접이식에 있다.

다만 경계 하나는 지금 알아 두는 편이 낫다.
**이 친절한 출력은 테스트 파일과 `conftest.py` 안에서만 나온다.**
테스트가 불러 쓰는 일반 헬퍼 모듈 안에 `assert`를 넣으면 메시지가 빈약해진다.
검사는 테스트 파일 안에서 하는 편이 좋다는 실용적 결론이 여기서 나온다.

### 질문 3 — 테스트가 실패하는 것을 먼저 보고 나서 고치는 순서를 왜 권하나?

**한 번도 실패해 본 적 없는 테스트는 아무것도 증명하지 않는다.**

초록에는 두 가지 뜻이 섞여 있다.

1. "코드가 맞다"
2. **"이 테스트는 사실 아무것도 검사하지 않는다"**

**둘은 화면에서 구별되지 않는다.** 똑같이 초록이다.
구별하는 방법은 하나뿐이다. **빨강을 한 번 보는 것.**

초록이 거짓말을 하는 전형적인 경우들이다.

| 실제 상태 | 화면에 보이는 것 |
|---|---|
| 파일명이 `test_`로 시작하지 않아 아예 수집이 안 됨 | `collected 0 items` — 바쁘면 초록으로 읽힌다 |
| `assert`를 빠뜨린 테스트 (함수 호출만 하고 끝) | 초록 |
| 엉뚱한 모듈을 검사 (설치본 대신 소스, 혹은 반대) | 초록 |
| `skip`이나 `xfail`이 조용히 걸려 있음 | 초록에 가까운 요약 |

랩이 `__version__` 없이 먼저 돌려 **빨강을 보라**고 한 것은 그래서다.
**그 빨강이 "이 테스트는 `__version__`이 없으면 알아챈다"는 증거다.**
증거를 확보한 다음에 통과시키면, 그 초록은 비로소 정보가 된다.

효과가 하나 더 있다. 빨강은 **실패 메시지를 읽는 유일한 기회**다.
지금 읽어서 이해 안 되는 메시지는, Phase 5에서 밤 11시에 체인이 갈라졌을 때도 이해 안 된다.
메시지를 다듬기 좋은 타이밍은 처음 빨강을 본 그 순간이다.

### 손으로 확인하기

**실험 A — pytest가 실패를 얼마나 자세히 보여 주는가.** 임시 파일 하나면 된다.

```python
# /tmp/collect_demo/test_diff_demo.py
def test_dict_diff() -> None:
    assert {"a": 1, "b": 2} == {"a": 1, "b": 3}
```

```
uv run pytest /tmp/collect_demo/test_diff_demo.py
python -c "assert {'a': 1, 'b': 2} == {'a': 1, 'b': 3}"
```

첫 명령은 어느 키가 어떻게 다른지까지 펼쳐서 보여 준다.
둘째 명령은 `AssertionError` 한 줄로 끝난다. **같은 `assert`인데 출력이 다르다.**

**실험 B — 이름 규칙은 언제 걸리는가.** 같은 파일을 이름만 바꿔 두 가지로 부른다.

```
mv /tmp/collect_demo/test_diff_demo.py /tmp/collect_demo/helper_module.py

uv run pytest --collect-only -q /tmp/collect_demo/helper_module.py   # 1 test collected
uv run pytest --collect-only -q /tmp/collect_demo                    # no tests collected
```

**같은 파일인데 결과가 다르다.** 경로를 집어 주면 이름과 무관하게 읽고,
폴더를 맡기면 이름 규칙에 걸려 조용히 빠진다.
빠질 때 에러도 경고도 없다는 점이 중요하다. 바쁘면 그 화면을 초록으로 읽는다.

**실험 C — 이 저장소에서 같은 일이 일어난다.**

```
uv run pytest --collect-only -q | tail -1          # 2 tests collected
uv run pytest --collect-only -q tests | tail -1    # 68 tests collected
```

66개의 차이가 Phase 1을 기다리는 선작성 테스트다. 사라진 게 아니라 **범위 밖**이었을 뿐이다.

> 이 세 실험을 한 번에 돌려 주는 스크립트가 워크북에 있다 →
> `workbook/phase-0/experiments/01_pytest_collection.py`

### 자주 하는 오해

| 오해 | 실제 |
|---|---|
| 테스트를 쓰려면 특별한 문법을 배워야 한다 | `test_`로 시작하는 평범한 함수 + `assert`가 전부다 |
| 테스트 파일은 반드시 `test_`로 시작해야 한다 | `*_test.py`도 기본 규칙에 들어 있다 |
| 이름이 규칙에 안 맞으면 어떻게 불러도 안 돈다 | **파일 경로를 직접 주면 수집된다.** 이름 규칙은 폴더를 훑을 때 쓰는 필터다 |
| 클래스로 묶으려면 `unittest.TestCase`를 상속해야 한다 | `Test*` 이름이면 된다. 단 **`__init__`이 있으면 수집되지 않는다** |
| `collected 0 items`는 통과다 | 아니다. 하나도 안 돌았다는 뜻이다. 초록으로 착각하기 가장 쉬운 화면 |
| `uv run pytest`가 저장소의 모든 테스트를 돈다 | `testpaths` 때문에 스모크만 돈다. Phase 1 테스트는 경로를 명시해야 돈다 |
| 진단을 얻으려면 `assert x == y, "긴 설명"`을 써야 한다 | pytest가 이미 양쪽 값을 보여 준다. 메시지는 **의도**를 적을 때만 쓸모 있다 |

### 3줄 요약

1. 테스트는 `test_`로 시작하는 평범한 함수고, 검사는 `assert` 한 줄이면 된다.
2. pytest는 테스트를 찾고, 돌리고, 실패를 **자세히** 보고한다.
   **파일 이름 규칙과 `testpaths`는 "pytest가 스스로 찾아 나설 때"만 걸리는 필터다.**
3. **실패를 한 번 본 테스트만 믿을 수 있다.** 초록은 "검사하지 않았음"과 구별되지 않는다.

<summary>더 깊이 — assertion rewriting은 어떻게 그 출력을 만드나 (지금 몰라도 된다)</summary>

pytest는 파이썬의 import 과정에 **자기 훅을 끼워 넣는다.**
테스트 모듈을 읽어 들일 때 소스를 그대로 실행하지 않고, 먼저 **AST(추상 구문 트리)를 다시 쓴다.**

`assert a == b`를 만나면 대략 이런 모양으로 바꾼다.

- `a`와 `b`의 값을 임시 변수에 먼저 담는다
- 비교가 실패하면, 담아 둔 값들로 설명 문자열을 조립한다
- 그 문자열을 붙여서 `AssertionError`를 던진다

그래서 **표준 `assert`를 그대로 쓰면서도** `assertEqual` 계열 API가 주는 진단을 얻는다.
pytest가 `unittest`처럼 전용 단언 메서드를 요구하지 않는 이유가 이것이다.

**경계 1 — 재작성 대상이 정해져 있다.**
테스트 모듈, `conftest.py`, 등록된 플러그인만 재작성된다.
테스트가 import하는 일반 헬퍼 모듈 안의 `assert`는 재작성되지 않아 메시지가 빈약하다.
그 모듈까지 포함하려면 `pytest.register_assert_rewrite("패키지.모듈")`을 테스트 수집 전에 호출해야 한다.

**경계 2 — 재작성 결과는 캐시된다.**
`__pycache__`에 저장되는데, 파일명에 pytest 버전이 박힌다.
이 저장소의 `tests/__pycache__/test_smoke.cpython-312-pytest-9.1.1.pyc`가 그 물증이다.
pytest 버전이 바뀌면 캐시가 자동으로 무효화된다.

**함정 — `python -O`.**
최적화 모드로 돌리면 파이썬이 `assert` 문을 **통째로 제거한다.**
테스트를 `-O`로 돌리면 안 되는 이유다. 전부 통과한 것처럼 보인다.

**failed와 error의 구분.**
테스트 **본문**에서 난 예외는 `failed`, **준비 코드(픽스처)** 에서 난 예외는 `error`로 분류된다.
원인을 찾는 방향이 다르다. `error`면 테스트 자체가 아니라 준비 단계를 봐야 한다.

**rootdir이 정해지는 방식.**
pytest는 설정 파일(`pyproject.toml`의 `[tool.pytest.ini_options]`, `pytest.ini`, `tox.ini` …)이 있는
디렉터리를 rootdir로 잡는다. rootdir은 "어디를 수집할지"가 아니라 **상대 경로와 설정의 기준점**이다.
실행 위치를 바꿔도 같은 설정이 적용되는 이유가 여기 있다.

## Lab 0.2 — uv 프로젝트와 src 레이아웃

> **언제 읽나**: 랩의 "1. 먼저 깨져보기"를 해본 뒤, "3. 과제" 전에.
> **대응 랩**: [Lab 0.2](../labs/phase-0-setup.md#lab-02--uv-프로젝트와-src-레이아웃)

### 한 줄로 말하면

파이썬이 우리 패키지를 **언제나 같은 곳에서** 찾게 만드는 단계다.

### 지금 어디쯤인가

Lab 0.1에서 판정 규칙을 만들었다. 기계가 맞고 틀림을 말해 준다.

그런데 아직 빈 곳이 있다. **그 기계가 매번 같은 물건을 재고 있나?**
체중계를 카펫 위에 놓으면 값이 달라진다. 지금 우리 상태가 그렇다.
테스트 파일은 그대로인데 **실행하는 폴더를 바꾸면 결과가 달라진다.**

이 랩은 그 흔들림을 없앤다.

### 이 랩이 답하려는 질문

> **`import bbschain`이라고 쓰면, 파이썬은 그걸 대체 어디서 찾나?**

### 배경 — 알아야 할 것

**`import`는 폴더 목록을 순서대로 뒤지는 일이다.**

파이썬은 `sys.path`라는 리스트를 들고 있다. 그냥 폴더 경로들의 목록이다.
`import bbschain`을 만나면 **그 목록을 앞에서부터 훑어 처음 찾은 것을 쓴다.**
찾으면 멈춘다. 뒤에 뭐가 더 있든 보지 않는다.

여기서 문제가 생긴다. **그 목록의 맨 앞에 무엇이 들어가는지가 실행 방법마다 다르다.**
스크립트로 실행할 때, 모듈로 실행할 때, pytest로 실행할 때가 전부 다르다.
그래서 **똑같은 코드가 어디서 실행하느냐에 따라 다른 파일을 불러올 수 있다.**
(정확히 어떻게 다른지는 아래 접이식에 표로 정리해 뒀다. 결론만 알면 이 절은 넘어간다.)

해결 방향은 두 가지다.

- **매번 경로를 손으로 끼워 넣는다** — `sys.path.insert(...)`, `PYTHONPATH=...`
- **패키지를 제대로 설치한다** — 그러면 경로 걱정이 사라진다

앞의 것은 문제를 숨긴다. 실행 환경마다 다시 해야 하고, Phase 7에서 컨테이너에 올리는 순간 전부 터진다.
**이 프로젝트는 뒤의 길을 간다.** 그러려면 우리 코드가 "설치 가능한 패키지"여야 한다.
그 선언서가 `pyproject.toml`이고, 설치를 대신 해 주는 도구가 `uv`다.

### 랩과 연결하기

랩 ①에서는 **같은 테스트를 서로 다른 조건으로 세 번 돌린다.** 아직 안 해봤다면 이런 일이 일어난다.

1. 프로젝트 루트에서 테스트를 돌린다 → 아마 된다
2. **다른 폴더로 이동해서** 같은 파일을 절대경로로 지정해 돌린다
3. 혹은 `src/` 폴더를 `source/`로 **이름만** 바꿔 본다

2번이나 3번에서 이걸 보게 된다.

```
ModuleNotFoundError: No module named 'bbschain'
```

**코드는 한 글자도 안 바뀌었다.** 바뀐 것은 실행 위치와 폴더 이름뿐이다.
그러니 이건 코드의 문제가 아니라 **"파이썬이 `bbschain`을 어디서 찾고 있었나"** 의 문제다.

이미 해봤다면 이렇게 정리하면 된다.
2번은 `sys.path`의 맨 앞이 바뀐 것이고, 3번은 설치가 가리키던 자리가 사라진 것이다.
원인이 다르다. 그런데 **증상은 똑같다.** 그래서 이 에러 하나로는 원인을 알 수 없다.

### 질문 1 — src 레이아웃과 flat 레이아웃의 차이는? src 레이아웃이 막아 주는 사고는?

차이는 폴더 하나다. **패키지를 저장소 루트 바로 밑에 두느냐, `src/` 안에 한 겹 넣느냐.**

```
flat 레이아웃                     src 레이아웃
repo/                            repo/
├── bbschain/      ← 루트 바로 밑  ├── src/
│   └── __init__.py              │   └── bbschain/
└── tests/                       │       └── __init__.py
                                 └── tests/
```

**flat에서는 저장소 루트가 `sys.path`에 들어오는 순간 `./bbschain/`이 그냥 import된다.**
설치하지 않아도 import가 된다. 편해 보인다. **그 편함이 정확히 문제다.**

테스트가 검사하는 대상이 "설치된 패키지"가 아니라 **"지금 폴더에 있는 디렉터리"** 가 되기 때문이다.
둘은 다를 수 있다. 그리고 남들이 받는 것은 앞의 것이다.

**src 레이아웃은 그 경로를 구조적으로 끊는다.**
`repo/`가 `sys.path`에 있어도 `repo/bbschain`은 존재하지 않는다.
`import bbschain`이 성공하려면 **설치가 되어 있어야만 한다.**
결과적으로 테스트는 언제나 **남들에게 배포될 물건 그 자체**를 검사한다.

막아 주는 사고를 구체적으로 적으면 이렇다.

| 사고 | flat에서 | src에서 |
|---|---|---|
| 빌드 설정 누락으로 파일이 배포본에 안 담김 | 로컬 테스트는 계속 초록. **설치한 사용자만 터진다** | 설치 자체가 깨져 즉시 발각 |
| `__init__.py` 누락, 패키지 이름 오타 | 우연히 동작 | 바로 실패 |
| 루트의 `tests/`, `docs/` 같은 폴더가 최상위 이름으로 import됨 | 이름 충돌 가능 | 애초에 후보가 아님 |
| 스크립트로는 되는데 설치본에선 안 되는 import | 감지 불가 | 감지됨 |

한 줄로: **flat은 "내 컴퓨터에서만 되는 상태"를 초록으로 표시할 수 있고, src는 그럴 수 없다.**

### 질문 2 — editable install(`-e`)은 일반 설치와 무엇이 다른가?

보통 설치는 **파일을 복사한다.** 그러면 소스를 고쳐도 설치본은 옛날 그대로다.
개발 중에는 재앙이다. 한 줄 고칠 때마다 다시 설치해야 한다.

**editable 설치는 복사 대신 "저기 있다"는 표시를 남긴다.**

| | 일반 설치 | editable 설치 |
|---|---|---|
| 하는 일 | 파일을 `site-packages`로 **복사** | 원본 소스를 가리키는 **표시**를 심는다 |
| 소스를 고치면 | 반영 안 됨. 재설치해야 함 | 다음 import부터 바로 반영 |
| 실제로 불러오는 파일 | `…/site-packages/bbschain/…` | `…/repo/src/bbschain/…` |
| 표준 | — | **PEP 660** |

**이 프로젝트는 이미 editable 상태다.** `uv sync`가 프로젝트 자신을 그렇게 설치한다.
가상환경 안에 우리 `src/` 폴더의 절대 경로가 적힌 파일이 한 줄 생기고,
파이썬이 시작할 때 그 줄을 읽어 `sys.path`에 넣는다. 마법이 아니라 **파일 하나**다.

그래서 랩 ①의 3번이 실패한 이유도 설명된다.
**`src/`를 `source/`로 바꾸면 그 한 줄이 가리키는 곳이 사라진다.**

주의할 경계가 하나 있다. **자동으로 반영되는 것은 "파일 내용"뿐이다.**
`pyproject.toml`의 의존성이나 진입점 설정을 고쳤다면 `uv sync`를 다시 돌려야 한다.
`uv run`이 실행 전에 환경을 맞춰 주므로 대개 신경 쓸 일이 없지만,
"고쳤는데 반영이 안 된다" 싶을 때 가장 먼저 의심할 자리다.

### 질문 3 — 락 파일(`uv.lock`)은 왜 커밋해야 하나? `pyproject.toml`의 버전 범위만으로는 왜 부족한가?

**두 파일이 답하는 질문이 다르다.**

`pyproject.toml`에 `pytest>=8.0`이라고 적는 것은 **"8.0 이상이면 뭐든 괜찮다"** 는 뜻이다.
허용 범위를 적은 것이지, 무엇이 깔렸는지를 적은 게 아니다.

| | `pyproject.toml` | `uv.lock` |
|---|---|---|
| 적는 것 | **허용 집합** (`pytest>=8.0`) | **실제로 뽑힌 하나** (`pytest 9.1.1`) |
| 딸려 오는 패키지 | 안 적힌다 | 전부 적힌다 |
| 무결성 검증 | 없음 | 파일 해시까지 |
| 답하는 질문 | "무엇과 호환되나" | "지금 무엇이 깔려 있나" |

`>=8.0`은 오늘 9.1.1을 뽑고, 반년 뒤 같은 명령이 9.4를 뽑는다.
그 사이에 동작이 조금 바뀌면 **어제까지 초록이던 커밋이 오늘 빨강**이 된다. 코드는 그대로인데.
게다가 직접 적은 의존성은 4개여도 실제로 깔리는 패키지는 수십 개고,
**그것들의 버전은 `pyproject.toml` 어디에도 없다.**

락 파일은 그 결과 전체를 고정한다.
커밋해 두면 저장소를 받은 사람이, CI가, Phase 7의 컨테이너가 **같은 집합**을 얻는다.
재현 가능한 판정기의 전제 조건이다.

**"애플리케이션은 커밋하고 라이브러리는 커밋하지 않는다"** 는 관례도 여기서 나온다.
라이브러리는 남의 환경에 설치되므로 **범위가 곧 계약**이고, 하나로 고정하면 오히려 방해가 된다.
이 프로젝트는 노드 소프트웨어 — 애플리케이션이다. 그래서 커밋한다.

이게 블록체인 프로젝트에서 특히 중요한 이유가 있다.
노드 소프트웨어는 **여러 사람의 컴퓨터에서 완전히 같게 동작해야 하는** 프로그램이다.
라이브러리 버전 차이가 저장 형식이나 해시 한 바이트를 바꾸면, 그 노드는 체인에서 갈라진다.
Phase 1에서 저장 형식을 문서로 못 박는 것과 지금 락을 커밋하는 것은 **같은 종류의 방어**다.

### 손으로 확인하기

지금 import되는 `bbschain`이 **어디 있는 파일인지** 직접 본다.

```
uv run python -c "import bbschain; print(bbschain.__file__)"
```

출력이 `…/site-packages/bbschain/…`가 아니라 **이 저장소의 `src/bbschain/__init__.py`** 를 가리키면
editable 설치가 맞다. 복사본이 아니라 네가 지금 고치는 그 파일이다.

한 줄 더. 파이썬이 뒤지는 폴더 목록을 그대로 찍어 본다.

```
uv run python -c "import sys; print(*sys.path, sep='\n')"
```

이 목록 어딘가에 이 저장소의 `src/`가 들어 있다. 그게 앞 명령의 결과를 만든 원인이다.

### 자주 하는 오해

| 오해 | 실제 |
|---|---|
| `import`는 알아서 프로젝트를 찾아 준다 | `sys.path` 목록을 앞에서부터 뒤진다. 그 목록은 실행 방법마다 다르다 |
| editable이면 `pyproject.toml`을 고쳐도 자동 반영된다 | 자동 반영되는 건 **소스 파일 내용**뿐. 설정을 바꾸면 다시 `uv sync` |
| `uv.lock`은 생성물이니 `.gitignore`에 넣는다 | **애플리케이션은 커밋한다.** 라이브러리와 규칙이 다르다 |
| `PYTHONPATH`나 `sys.path.insert`로 해결하면 같은 것이다 | 문제를 **숨기는** 것이다. 환경마다 다시 해야 하고 배포에서 터진다 |
| `uv sync`만 하면 락이 항상 최신이다 | `uv sync`는 필요하면 **락을 갱신한다.** 갱신을 막고 실패시키려면 `--locked`가 필요하다 (Lab 0.3) |

### 3줄 요약

1. `import`는 폴더 목록을 뒤지는 일이고, **그 목록은 실행 방법마다 달라진다.**
2. `src/` 안에 패키지를 두면 **설치하지 않고는 import할 수 없게** 되어, 테스트가 항상 배포될 물건을 검사한다.
3. `pyproject.toml`은 허용 범위를, `uv.lock`은 실제로 깔린 것을 적는다. **재현은 뒤쪽이 만든다.**

### 이제 할 일

- [ ] `uv run python -c "import bbschain; print(bbschain.__file__)"` 로 경로를 눈으로 확인한다
- [ ] `pyproject.toml`을 열어 `[build-system]`, `[tool.hatch.build.targets.wheel]`,
      `[dependency-groups]`가 각각 무슨 말을 하는지 위 설명과 맞춰 본다
- [ ] `uv.lock`을 열어 **직접 적지 않은 패키지가 몇 개나 들어 있는지** 본다
- [ ] 직접 해보고 싶다면: `pyproject.toml`을 `/tmp`에 **백업한 뒤** 랩 3절의 과제대로 다시 써 본다.
      다 쓰면 `uv sync` → `uv run pytest`가 초록이어야 한다. 막히면 백업으로 되돌린다
- [ ] [PROGRESS.md](../PROGRESS.md)에 회고 3줄

<details>
<summary>더 깊이 — `sys.path[0]`은 누가 채우나, `.pth` 파일의 실물 (지금 몰라도 된다)</summary>

**`sys.path`의 맨 앞은 실행 방식에 따라 다르게 채워진다.** 랩 ①에서 결과가 갈린 원인이 이 표에 있다.

| 실행 방식 | `sys.path[0]` |
|---|---|
| `python script.py` | `script.py`가 들어 있는 **디렉터리** |
| `python -m pkg` / `python -c ...` / 대화형 | **현재 작업 디렉터리** |
| `pytest` (기본 `prepend` import 모드) | 테스트 파일에서 위로 올라가 `__init__.py`가 **없는 첫 디렉터리** |

실행 위치가 바뀌면 `sys.path[0]`이 바뀌고, 찾아지는 패키지가 바뀐다.
flat 레이아웃에서 "루트에서 돌리면 되고 다른 데서 돌리면 안 되는" 현상의 정체가 이것이다.

**editable 설치의 실물.**
PEP 660은 "원본을 가리킨다"는 결과만 정하고, 방법은 빌드 백엔드에 맡긴다.
경로를 추가하는 `.pth` 파일을 쓰기도 하고, import 훅으로 동작하는 finder 모듈을 넣기도 한다.

이 프로젝트의 백엔드는 hatchling(`packages = ["src/bbschain"]`)이고, 결과는 이 파일이다.

```
.venv/lib/python3.12/site-packages/_editable_impl_bbschain.pth
```

직접 열어 보면 한 줄이 들어 있다 — 이 저장소 `src/`의 절대 경로다.

```
cat .venv/lib/python3.12/site-packages/_editable_impl_bbschain.pth
```

파이썬은 시작할 때 `site-packages` 안의 `.pth` 파일들을 읽어 각 줄을 `sys.path`에 추가한다.
그래서 `src/`가 경로에 들어가고 `bbschain`이 import된다.
**`src/`의 이름을 바꾸면 이 줄이 가리키는 곳이 사라진다** — 랩 ① 3번이 실패한 이유가 정확히 이것이다.
</details>

## Lab 0.3 — CI를 초록으로

> **언제 읽나**: 랩의 "1. 먼저 깨져보기"를 해본 뒤, "3. 과제" 전에.
> **대응 랩**: [Lab 0.3](../labs/phase-0-setup.md#lab-03--ci를-초록으로)

### 한 줄로 말하면

**빈 컴퓨터에서도** 초록인지를 매번 자동으로 확인하게 만드는 단계다.

### 지금 어디쯤인가

Lab 0.1에서 판정 규칙을, Lab 0.2에서 판정 대상의 동일성을 만들었다.
이제 내 컴퓨터에서는 `uv run pytest`가 안정적으로 같은 답을 낸다.

**남은 구멍은 "내 컴퓨터"라는 말 자체다.**
내 컴퓨터는 지금까지 내가 한 모든 일의 퇴적층 위에 있다.
옛날에 깔아 둔 패키지, 손으로 만든 환경변수, 커밋하지 않은 파일이 쌓여 있다.
**그 퇴적층은 커밋되지 않는다.** 남들은 받지 못한다.

이 랩은 판정을 내 컴퓨터 바깥으로 옮긴다.

### 이 랩이 답하려는 질문

> **"내 컴퓨터에서는 되는데요"를 어떻게 미리 잡나?**

### 배경 — 알아야 할 것

**CI(Continuous Integration)는 "대신 돌려 주는 빈 컴퓨터"다.**

GitHub에 코드를 올리면, GitHub이 **깨끗한 컴퓨터를 한 대 빌려 준다.**
그 컴퓨터가 내 저장소를 새로 내려받고, 내가 적어 둔 명령을 순서대로 돌리고, 결과를 알려 준다.
끝나면 그 컴퓨터는 사라진다. 다음에도 또 새 컴퓨터가 온다.

**내가 적어 둔 명령**이 들어가는 자리가 `.github/workflows/` 아래의 YAML 파일이다.
이 파일을 **워크플로(workflow)** 라고 부른다. 내용은 세 덩어리뿐이다.

1. **언제 돌릴까** — `on:` (push할 때, PR을 열 때 …)
2. **어디서 돌릴까** — `runs-on:` (우분투 최신 버전 등)
3. **무엇을 돌릴까** — `steps:` (체크아웃 → 도구 설치 → 린트 → 테스트)

결과는 GitHub 커밋 목록 옆에 **초록 체크 ✓ 또는 빨간 ✗** 로 붙는다.
이 프로젝트에서는 그 체크 하나가 "이 커밋은 빈 컴퓨터에서도 통과한다"는 뜻이다.

**핵심은 "빈 컴퓨터"다.** CI가 잡아 주는 것은 버그가 아니라
**내 환경에만 있는 것에 몰래 기대고 있던 부분**이다.

### 랩과 연결하기

랩 ①에서는 **내 컴퓨터와 빈 컴퓨터의 차이를 손으로 만들어 본다.** 아직 안 해봤다면 이렇다.

1. `uv.lock`을 임시로 `.gitignore`에 넣어 본다
2. 혹은 dev 의존성 하나를 `pyproject.toml`에서 지우고 테스트를 돌려 본다
3. 임시 폴더에 저장소를 새로 clone해서 `uv sync && uv run pytest`를 그대로 돌려 본다

**네가 볼 것은 "내 폴더에서는 되는데 새로 받은 곳에서는 안 되는 상태"다.**
이게 "내 컴퓨터에서는 되는데요"의 실물이다.

원인을 찾는 명령은 이것 하나다.

```
git status --ignored
```

추적되지 않는 파일, 커밋 안 한 설정, 남아 있는 가상환경이 보인다.
**여기 보이는 것들이 곧 "나만 가진 것"의 목록이다.**

이미 해봤다면 이렇게 정리하자. CI는 3번을 **매 커밋마다 자동으로** 하는 장치다.
손으로 하면 잊어버리고, 잊어버린 채로 몇 주가 지나면 원인이 쌓여서 못 찾는다.

### 질문 1 — GitHub Actions에서 워크플로가 언제 돌게 되어 있나? (트리거 이벤트)

워크플로 파일의 **`on:` 키**가 정한다. 이 프로젝트는 이렇게 돼 있다.

```yaml
on:
  push:
    branches: [main]
  pull_request:
```

읽는 법은 그대로다.

- **`push` + `branches: [main]`** — `main`에 커밋이 들어올 때만 돈다
- **`pull_request`** — PR을 열 때, PR에 새 커밋을 올릴 때, 닫았다 다시 열 때 돈다

둘을 같이 쓰는 이유가 있다. **PR 작업 중에는 `pull_request`가, 머지된 뒤에는 `push`가 담당한다.**
만약 `push`에 브랜치 필터를 안 걸면 PR 브랜치에 push할 때마다 **같은 검사가 두 번** 돈다.
낭비이기도 하지만, 같은 결과가 두 줄로 보여서 헷갈린다.

이 파일에는 블록이 하나 더 있다.

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

같은 브랜치에 연달아 push하면 **앞 실행을 취소한다.**
러너 시간을 아끼는 효과가 눈에 띄지만, 더 중요한 이유는 따로 있다
(→ 이 절 맨 아래 접이식).

Phase 7에서 다시 만나게 될 트리거도 있다. 수동 실행 버튼(`workflow_dispatch`), 정해진 시각 실행(`schedule`).

### 질문 2 — CI 러너에는 uv가 설치돼 있나? 없다면 어떻게 넣나?

**없다.**

`ubuntu-latest` 이미지에는 파이썬 여러 버전, git, curl, docker 같은 것이 미리 들어 있다.
uv는 없다. 넣지 않으면 `uv: command not found`로 끝난다.

넣는 방법은 공식 액션 한 단계다.

```yaml
- name: Install uv
  uses: astral-sh/setup-uv@v5
  with:
    enable-cache: true
    cache-dependency-glob: "uv.lock"
    python-version: "3.12"
```

세 옵션이 각각 하는 일이다.

| 옵션 | 효과 |
|---|---|
| `enable-cache: true` | 내려받은 패키지를 보관해 둔다. 두 번째 실행부터 빨라진다 |
| `cache-dependency-glob: "uv.lock"` | **락이 바뀔 때만** 그 보관본을 버린다 |
| `python-version: "3.12"` | uv가 쓸 파이썬 버전을 못 박는다 |

마지막 줄이 왜 필요한가.
`pyproject.toml`의 `requires-python`은 `>=3.12`라 **3.13도 3.14도 조건을 만족한다.**
러너 기본 파이썬이 올라가는 날, CI는 아무 예고 없이 다른 인터프리터로 돌게 된다.
**판정기가 스스로 흔들리면 판정을 믿을 수 없다.** 그래서 여기서 고정한다.

그다음 단계는 이렇게 이어진다.

```yaml
- run: uv sync --locked --all-groups
- run: uv run ruff check
- run: uv run pytest -v
```

**`--locked`가 이 워크플로에서 가장 중요한 한 단어다.**

`uv sync`는 락과 `pyproject.toml`이 어긋나면 **조용히 다시 계산해서** 설치를 진행한다.
로컬에서는 편하다. CI에서는 재앙이다.
CI는 초록인데, 그 초록이 증명한 의존성 집합이 **남들이 받는 집합과 다르기** 때문이다.
판정기가 판정 대상을 스스로 바꿔 버린 셈이다.

`--locked`는 어긋난 순간 실패시킨다.
"락을 갱신하고 커밋하라"는 요구가 빌드 실패라는 형태로 표현되는 것이다.

`--all-groups`는 `[dependency-groups]`의 그룹을 빠짐없이 설치하게 한다.
이 프로젝트의 `dev` 그룹에는 `pytest`, `ruff`, `mypy`, `hypothesis`가 들어 있다.

마지막 `uv run pytest -v`에는 **경로 인자가 없다.**
Lab 0.1에서 본 규칙대로 `testpaths`에 적힌 스모크 테스트만 수집된다.
즉 **CI 판정기의 범위는 `pyproject.toml`이 정한다.**
Phase 1 구현이 끝나 `testpaths`를 `["tests"]`로 되돌리는 순간 CI의 판정 범위도 같이 넓어진다.
**워크플로 파일은 고치지 않는다.**

### 질문 3 — 테스트가 CI에서만 실패하고 로컬에서 통과한다면, 가장 먼저 의심할 것 3가지는?

먼저 전제를 뒤집어야 한다.
**CI가 이상한 게 아니라 로컬이 오염된 경우가 훨씬 많다.**
CI는 매번 빈 컴퓨터에서 시작한다. 내 컴퓨터는 아니다.

위에서부터 순서대로 확인한다.

| # | 의심할 것 | 확인 방법 |
|---|---|---|
| 1 | **커밋되지 않은 파일에 의존** — 추적 안 되는 데이터 파일, 무시된 설정, 로컬 `.env` | `git status --ignored`. 임시 폴더에 clone해서 재현 (랩 ①이 바로 이것) |
| 2 | **의존성·파이썬 버전 차이** — 락이 어긋남, 옛날에 깔아 둔 패키지가 남아 있음 | 로컬에서 `uv sync --locked --all-groups` 실행, `uv run python -V`를 CI 로그와 대조 |
| 3 | **실행 위치·경로 가정** — 절대 경로, 현재 폴더 기준 상대 경로, `./out.json` 같은 임시 파일 | 다른 폴더에서 같은 테스트 실행. 파일을 쓰는 테스트라면 임시 폴더를 쓰게 고쳤는지 확인 |

**여기까지로 대부분 잡힌다.** 안 잡히면 → 이 절 맨 아래 접이식에 세 개가 더 있다.

한 가지는 이 프로젝트에서 유독 중요하니 지금 말해 둔다.
**타임존과 로케일이다.** 시각을 문자열로 만드는 방식이 컴퓨터마다 다르면, 그 문자열이 들어간 **해시가 달라진다.**
"CI에서만 다른 해시가 나온다"는 Phase 4에서 실제로 만나게 될 증상이다.
Phase 1에서 저장 형식을 못 박는 이유가 정확히 이 종류의 차이를 없애기 위해서다.

### 손으로 확인하기

내 로컬 판정기와 CI 판정기가 **같은 물건인지** 두 줄로 대조한다.

```
uv run python -V
git ls-files --others --exclude-standard
```

첫 줄의 파이썬 버전이 워크플로에 못 박은 `3.12`와 맞는지 본다.
둘째 줄은 **추적되지 않는 파일 목록**이다.
여기 뭔가 있고 테스트가 그걸 읽고 있다면 1번 원인이 확정이다.

그리고 CI와 **똑같은 설치 명령**을 로컬에서도 한 번 돌려 둔다. 락 어긋남은 push 전에 잡힌다.

```
uv sync --locked --all-groups
```

성공하면 아무 말 없이 끝난다. 실패하면 락을 갱신하라고 말해 준다.

### 자주 하는 오해

| 오해 | 실제 |
|---|---|
| 러너에 파이썬이 있으니 uv도 있을 것이다 | 없다. `setup-uv` 단계가 빠지면 `command not found` |
| `uv sync`와 `uv sync --locked`는 같다 | 락이 어긋났을 때 동작이 **정반대**다. 하나는 다시 계산, 하나는 실패 |
| `concurrency`는 그냥 비용 절감 옵션이다 | 오래된 실행 결과가 뒤늦게 최신 상태를 덮는 것도 막는다 |
| 로컬에서 되니까 CI 설정이 잘못된 것이다 | 대개 반대다. CI가 깨끗하고 로컬이 퇴적층 위에 있다 |
| CI가 초록이면 배포해도 안전하다 | CI가 보장하는 건 "내 판정기가 깨끗한 환경에서도 같은 답을 낸다"까지다. 판정기가 검사하지 않는 것은 여전히 모른다 |

### 3줄 요약

1. CI는 **매번 빈 컴퓨터를 빌려** 내 명령을 대신 돌려 주는 장치다.
2. `--locked`가 없으면 CI가 **판정 대상을 스스로 바꿔** 버린다. 초록의 의미가 사라진다.
3. CI에서만 실패하면 먼저 로컬을 의심한다. **커밋 안 된 파일 → 의존성 차이 → 경로 가정** 순서로 본다.

### 이제 할 일

- [ ] `.github/workflows/ci.yml`을 열어 `on:` / `runs-on:` / `steps:` 세 덩어리를 찾아 본다
- [ ] `uv sync --locked --all-groups`를 로컬에서 돌려 CI와 같은 설치가 되는지 확인한다
- [ ] `git status --ignored`로 **나만 가진 것**의 목록을 한 번 본다
- [ ] 아직 안 했다면: 첫 커밋과 `git push origin main`은 **사용자가 직접** 한다.
      push한 뒤 GitHub Actions 탭에서 초록 체크를 확인하고
      [PROGRESS.md](../PROGRESS.md)의 Phase 0 DoD 나머지를 켠다
- [ ] 직접 해보고 싶다면: `.github/workflows/ci.yml`을 `/tmp`에 **백업한 뒤 지우고**
      랩 3절의 과제대로 다시 써 본다. 일부러 테스트 하나를 깨뜨려 **빨간 ✗까지 봐야** 판정기를 믿을 수 있다

<summary>더 깊이 — `concurrency`의 진짜 이유, PR이 검사하는 커밋, 나머지 원인 3가지 (지금 몰라도 된다)</summary>

**`concurrency`가 막는 것.**
러너 시간 절약은 부수 효과다. 진짜 이유는 **결과가 순서대로 도착하지 않기 때문**이다.
커밋 A를 push하고 곧바로 B를 push하면 두 실행이 동시에 돈다.
A가 더 오래 걸리면 **A의 결과가 B보다 늦게 도착해서 최신 상태를 덮어쓴다.**
B가 깨졌는데 초록으로 보이거나, 그 반대가 된다. 앞 실행을 취소하면 그 일이 생기지 않는다.

**`pull_request`가 검사하는 커밋.**
PR에서 도는 워크플로는 내 브랜치의 HEAD가 아니라 **"머지했다고 가정한 결과 커밋"** 에서 돈다.
그 사이 `main`이 움직였다면 **CI가 검사한 코드는 내 로컬과 다르다.**
"로컬은 되는데 CI만 실패"의 원인 중 가장 찾기 어려운 부류다.
CI 로그의 checkout 커밋 SHA를 로컬 HEAD와 대조하면 확인된다.

**원인 4~6.** 본문의 1~3으로 안 잡힐 때 본다.

| # | 원인 | 확인 방법 |
|---|---|---|
| 4 | **환경변수·로케일·타임존** — 로컬 `TZ`, `LANG`, 쉘 프로필에 넣어 둔 값 | `env` 출력을 CI 로그와 비교. 시각을 다루는 테스트라면 특히 |
| 5 | **테스트 순서·공유 상태 의존** — 로컬은 일부만 돌려 왔고 CI는 전체를 처음부터 돈다 | 순서를 섞어 돌려 본다. 전역 상태·클래스 변수·파일 재사용을 의심 |
| 6 | **검사 대상 커밋이 다름** — 위의 머지 결과 커밋 문제 | CI 로그의 checkout SHA를 로컬 HEAD와 대조 |

4번은 이 프로젝트에서 특히 자주 나온다.
타임존이나 로케일이 타임스탬프 문자열을 바꾸면 **해시가 바뀐다.**
Phase 1의 정규 직렬화와 Phase 4의 타임스탬프 검증이 겨냥하는 게 정확히 그 종류의 차이다.
