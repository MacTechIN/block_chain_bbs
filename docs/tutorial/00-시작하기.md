# 시작하기 — 우리가 지금 뭘 만드는 중인가

> **이 프로젝트에서 가장 먼저 읽는 문서다.**
> 다른 튜토리얼 문서는 "통독하지 마라"고 말한다. 이 문서는 반대다. **처음부터 끝까지 읽어라.**
> 10분이면 읽는다. 읽고 나면 "내가 뭘 만드는 중이고 왜 이 순서인가"가 잡힌다.

**읽는 사람**: 파이썬으로 함수와 클래스를 써 본 사람. 터미널이 낯설지 않은 사람.
블록체인은 몰라도 된다. 암호학도 몰라도 된다. 그래서 이 문서가 있다.

---

## 1. 우리가 만드는 것

**글이 블록에 담기는 게시판이다.**

평범한 게시판은 글 하나를 데이터베이스의 한 줄로 저장한다.
관리자는 그 줄을 지울 수 있다. 고칠 수도 있다. **고친 흔적은 남지 않는다.**
"이 글은 처음부터 이런 내용이었다"를 증명할 방법이 없다. 믿을 근거는 관리자에 대한 신뢰뿐이다.

우리가 만드는 게시판은 그 신뢰를 계산으로 대체한다.
글은 **블록**이라는 상자에 담긴다. 상자는 앞 상자와 묶여 줄줄이 이어진다.
중간 상자의 글을 한 글자만 고치면 그 뒤 상자가 **전부** 어긋난다.
프로그램을 돌리면 이렇게 말한다.

```
INVALID: block #3 hash mismatch
         blocks #4..#10 invalidated (chain broken from #3)
```

이 화면을 Phase 1이 끝날 때 네 손으로 본다.
그리고 마지막에는 이 게시판이 **여러 대의 컴퓨터에서 동시에 돌면서도 같은 글 목록에 합의한다.**
관리자가 없는데도 모두가 같은 게시판을 본다 — 그게 이 프로젝트의 최종 장면이다.

---

## 2. 블록체인이 뭔가

### 한 번 쓰면 못 지우는 공책

공책 한 권을 떠올려라. 규칙이 세 개 있다.

1. **맨 뒤에만 쓴다.** 중간에 끼워 넣을 수 없고, 쓴 것을 지울 수 없다.
2. **한 페이지를 다 쓰면 그 페이지의 지문을 뜬다.** 지문은 짧은 문자열 하나다. 페이지 내용이 조금이라도 다르면 지문도 완전히 달라진다.
3. **다음 페이지 맨 위에 앞 페이지의 지문을 적는다.**

이제 누가 몰래 5쪽의 글자 하나를 고쳤다고 하자.
5쪽의 지문이 바뀐다. 그런데 6쪽 맨 위에는 **예전 지문**이 적혀 있다. 둘이 안 맞는다.
고친 사람이 6쪽도 고치면? 그럼 7쪽이 안 맞는다. 끝까지 전부 다시 써야 한다.

**한 장을 찢으면 뒤가 전부 티가 난다.** 이게 블록체인의 핵심 아이디어 전부다.

여기서 "지문"에 해당하는 것이 **해시(hash)** 다.
어떤 데이터든 넣으면 고정 길이 문자열 하나가 나오는 함수다. 같은 입력이면 항상 같은 값이 나온다.
그리고 입력이 한 글자만 달라도 결과는 알아볼 수 없을 만큼 달라진다.
"페이지"가 **블록(block)**, 페이지들이 지문으로 이어진 전체가 **체인(chain)** 이다.

### 공책 하나로는 부족하다

공책 비유는 여기까지만 맞는다. 한계가 두 개 있고, 둘 다 이 프로젝트 후반부의 주제다.

**한계 1 — 공책이 하나면 태워 버리면 끝이다.**
아무리 지문을 잘 이어 놓아도 공책 자체를 통째로 다시 쓰면 아무도 모른다.
그래서 진짜 블록체인은 **공책을 수백 부 복사해 서로 모르는 사람들에게 나눠 준다.**
하나를 고쳐도 나머지가 다르다고 말한다. Phase 5에서 우리가 만드는 것이 이 부분이다.

**한계 2 — 그러면 공책끼리 내용이 다를 때 누구 말이 맞나.**
이 질문의 답이 **합의(consensus)** 다.
우리는 "다시 쓰는 데 계산 비용이 가장 많이 든 공책을 믿는다"는 규칙을 쓴다.
그 비용을 만드는 장치가 **작업증명(Proof of Work)** 이고, Phase 4의 주제다.

그러니 지금은 이렇게만 쥐고 가라.
**해시로 페이지를 잇고(Phase 1), 여러 부를 복사하고(Phase 5), 누구 말이 맞는지 정하는 규칙을 둔다(Phase 4).**

## 3. 왜 직접 만드나

파이썬에는 블록체인 라이브러리가 이미 있다. 가져다 쓰면 하루 만에 "블록체인 게시판"이 돈다.
그런데 그렇게 하면 배우지 못한다. 이유는 둘이다.

**첫째, 라이브러리는 이미 안전하다.** 안전한 물건은 왜 안전한지 보여 주지 않는다.
`chain.add_block(data)`를 호출하고 `True`를 받으면, 무엇을 막았는지 알 길이 없다.
방어가 무엇을 막는지 알려면 **방어가 없을 때 무슨 일이 일어나는지를 봐야 한다.**

**둘째, 어려운 부분은 자료구조가 아니라 규칙이다.**
블록 클래스를 만드는 건 30분이면 된다. 진짜 어려운 건 이런 것들이다.
"같은 글인데 왜 컴퓨터마다 해시가 다르지?", "두 노드가 동시에 블록을 만들면?",
"내 블록 5개가 방금 취소됐는데 그게 정상이라고?"
라이브러리는 이 질문들을 **이미 풀어서 숨겨 놓았다.** 숨겨진 답은 읽어도 남지 않는다.

우리는 곡선 수학이나 TCP 소켓 같은 것까지 다시 짜지는 않는다.
**직접 짜는 것은 검증 규칙과 합의다.** 그 경계는 [개발계획서 5절](../01-개발계획서.md#5-기술-스택)이 정해 뒀다.

## 4. 전체 지도 — Phase 0부터 8까지

각 Phase는 **눈으로 보는 장면 하나**로 끝난다. 장면이 없는 단계는 이 계획에 넣지 않았다.

| Phase | 한 문장으로 | 이 단계가 끝나면 네가 보게 되는 것 |
|---|---|---|
| 0 | 판정기를 먼저 깐다 (테스트와 CI) | 터미널의 초록 `2 passed`, GitHub 커밋 옆 초록 체크 |
| 1 | 글을 블록에 담고 해시로 잇는다 | 저장 파일의 글자 하나를 고치면 터미널이 "#3부터 깨졌다"고 지목 |
| 2 | 브라우저에서 체인을 보고 깨뜨린다 | 상단 배지가 초록 `CHAIN VALID` → 변조하면 빨강, 파손 블록부터 빨간 줄 |
| 3 | 개인키를 가진 사람만 자기 이름으로 쓴다 | 남의 이름을 사칭한 글이 `invalid signature`로 거부되는 화면 |
| 4 | 블록 하나를 만드는 데 계산 비용을 붙인다 | 난이도를 올릴수록 채굴 카운터가 눈에 띄게 느려지는 실시간 화면 |
| 5 | 노드 여러 대가 같은 체인에 수렴한다 | 탭 3개가 같은 마지막 블록. 끊으면 갈라지고 다시 이으면 합쳐진다 |
| 6 | 앞에서 만든 방어를 내 손으로 뚫는다 | 51% 공격 버튼을 누르자 내가 쓴 글이 체인에서 사라지는 장면 |
| 7 | 인터넷에 올리고 이더리움에 못 박는다 | 휴대폰으로 쓴 글이 노트북에 뜨고, Etherscan에 내 블록 해시가 보인다 |
| 8+ | 확장 트랙 — 골라서 한다 | 고르는 것에 따라 다름 |

**순서에는 이유가 있다.** 몇 가지만 미리 말해 둔다.

- **0단계에 블록체인이 없는 이유**: 이후 모든 단계의 합격 판정이 "테스트가 통과하는가" 하나다.
  그 판정기를 못 믿으면 나머지 전부를 못 믿는다. 그래서 판정기를 맨 먼저 만든다.
- **서명(3)이 네트워크(5)보다 먼저인 이유**: 남이 보낸 블록을 받을지 말지 정하려면,
  그 안의 글이 정당한지 판별할 기준이 **먼저** 있어야 한다.
- **공격 실습이 6단계에만 있지 않은 이유**: 혼자서도 재현되는 공격은 그 단계가 끝나자마자 바로 해 본다.
  여러 노드가 있어야만 가능한 공격만 6단계에 모았다.

더 자세한 판단 근거는 → [개발계획서 3절](../01-개발계획서.md#3-이-순서를-고른-이유-설계-판단)

## 5. 이 프로젝트의 학습 방식 — 먼저 부순다

이 프로젝트의 규칙을 한 줄로 쓰면 이렇다.

> **먼저 허술하게 만든다. 직접 부숴 본다. 그다음에 고친다.**

이걸 **Break-First**라고 부른다. 순서가 거꾸로인 것처럼 보이지만 의도한 것이다.

"prev_hash가 있어서 변조에 강하다"는 문장을 **읽어서** 아는 것과,
내 게시판 파일을 에디터로 고쳤는데 프로그램이 아무것도 눈치채지 못하는 장면을 **보고 나서** 아는 것은 다르다.
앞의 것은 사흘이면 흐려진다. 뒤의 것은 남는다.

그래서 모든 랩(실습)은 이 네 박자로 간다.

```
① 먼저 깨져보기   →   ② 왜 그런지 읽기   →   ③ 직접 고치기   →   ④ 눈으로 확인
   방어 없는 상태를        (여기가 튜토리얼)      (과제 — 네가 쓴다)     (안 넘어가면
   내 손으로 부순다                                                      할 이유가 없다)
```

여기서 나오는 중요한 결과가 하나 있다.
**튜토리얼을 미리 읽으면 손해다.** 답을 알고 공격을 재현하면 그건 재현이 아니라 확인이다.
놀라지 않은 것은 기억에 남지 않는다.
그래서 튜토리얼의 모든 절 맨 위에는 **"언제 읽나"** 라는 박스가 붙어 있다. 그 줄만 지키면 된다.

한 가지 더. **정답 코드는 어디에도 없다.**
랩은 함수 이름과 만족해야 할 조건, 그리고 3단계 힌트까지만 준다. 통과시키는 코드는 네가 쓴다.
대신 **테스트는 미리 주어져 있다.** 무엇을 만들어야 하는지는 테스트가 말해 준다.

## 7. 용어 미리보기 — 지금 외우지 마라

앞으로 나올 말들을 한 줄씩 적어 둔다.
**지금 외우려 하지 마라.** 처음 보는 단어가 나왔을 때 "아, 여기 있었지" 하고 돌아올 자리다.
각 용어는 실제로 필요한 랩에서 다시, 제대로 설명된다.

| 용어 | 한 줄 뜻 | 처음 나오는 곳 |
|---|---|---|
| 해시 (hash) | 아무 데이터나 넣으면 나오는 고정 길이 지문. 같은 입력 → 같은 값 | Phase 1 |
| 블록 (block) | 글 몇 개와 요약 정보를 담은 상자 | Phase 1 |
| 체인 (chain) | 블록들이 앞뒤로 이어진 줄. 앞 블록의 해시를 들고 있어서 이어진다 | Phase 1 |
| 제네시스 블록 (genesis) | 0번 블록. 앞 블록이 없는 유일한 블록 | Phase 1 |
| 정규 직렬화 (canonical bytes) | 해시에 넣기 전에 데이터 모양을 한 가지로 못 박는 것 | Phase 1 |
| 머클 루트 (merkle root) | 블록 안의 글 전부를 해시 하나로 요약한 값 | Phase 1 |
| 트랜잭션 (transaction) | 체인에 담기는 한 건의 기록. 이 프로젝트에선 **글 1개** | Phase 1 |
| 지갑 (wallet) | 개인키를 보관하는 것. 은행 계좌가 아니라 **열쇠 꾸러미**다 | Phase 3 |
| 서명 (signature) | 개인키로 만들고 공개키로 확인하는 도장. **암호화가 아니다** | Phase 3 |
| 주소 (address) | 공개키를 짧게 줄인 문자열. 남에게 알려 주는 이름표 | Phase 3 |
| 멤풀 (mempool) | 아직 블록에 못 들어간 글들의 대기열 | Phase 3 |
| 채굴 (mining) | 조건을 만족하는 블록을 찾을 때까지 숫자를 바꿔 가며 해시를 계산하는 일 | Phase 4 |
| 작업증명 (PoW) | "이 블록을 만드는 데 계산을 썼다"는 증거 | Phase 4 |
| 난이도 (difficulty) | 그 조건이 얼마나 까다로운가 | Phase 4 |
| 노드 (node) | 체인 한 부를 들고 도는 프로그램 한 대 | Phase 5 |
| 합의 (consensus) | 노드들이 서로 다른 체인을 들고 있을 때 하나를 고르는 규칙 | Phase 5 |
| 포크 (fork) | 체인이 두 갈래로 갈라진 상태 | Phase 5 |
| 재구성 (reorg) | 갈라진 갈래 중 다른 쪽이 이겨서 내 블록 일부가 취소되는 일 | Phase 5 |
| 이중 지불 (double spend) | 같은 것을 두 번 쓰기. 여기선 **같은 글을 두 갈래에 따로 넣기** | Phase 6 |
| 테스트넷 (testnet) | 진짜 돈이 안 걸린 연습용 공개 체인 | SQ 1.6 |
| 앵커링 (anchoring) | 내 체인의 값을 남의 큰 체인에 기록해 두는 것 | Phase 7 |

한↔영 대조표 전체가 필요하면 → [기술리서치 #용어사전](../02-기술리서치.md#용어사전)

## 8. 시작하는 법

**Phase 0은 이미 끝나 있다.** 사용자 요청으로 에이전트가 대신 세팅했다
(기록은 [PROGRESS.md](../PROGRESS.md)에 있다). 그래서 지금 이 명령이 바로 돈다.

```
uv sync
uv run pytest
```

마지막 줄에 초록 `2 passed`가 보이면 준비가 끝난 것이다.

그다음 순서는 이렇다.

1. **[Phase 0 튜토리얼](phase-0.md)** 을 읽는다.
   이미 깔려 있는 것들이 각각 무슨 일을 하는지 확인하는 단계다. 30~40분.
2. **[Phase 1 랩](../labs/phase-1-chain.md)** 의 Lab 1.1 "1. 먼저 깨져보기"를 연다.
   **여기서부터는 네가 직접 만든다.**
3. 그 화면을 본 뒤에 `phase-1.md`의 대응 절을 읽는다. 순서를 바꾸지 마라.
4. 랩 하나가 끝날 때마다 [PROGRESS.md](../PROGRESS.md)에 회고 3줄을 적는다.
   **배운 것 / 헛짚은 것 / 다음에 확인할 것.** 이게 하루 루프의 마지막 칸이다.

막히면 [학습계획서 5절](../03-학습계획서.md#5-막혔을-때-에스컬레이션-규칙)에 막혔을 때의 규칙이 있다.
혼자 오래 붙잡고 있는 것을 권하지 않는다. 규칙에 시간 제한이 적혀 있다.
