# Phase 1 튜토리얼 — 해시에서 체인까지

> **이 문서는 읽는 교재다.**

## 이 문서는 누구를 위한 것인가

파이썬은 써 봤다. 함수·클래스·딕셔너리·터미널은 익숙하다.
**블록체인은 처음이다.** 해시라는 말은 들어봤지만 설명은 못 한다.
역상·충돌·생일 문제 같은 암호학 용어는 모른다.

그 사람을 기준으로 썼다. 어려운 것은 전부 접이식 상자(`더 깊이`)로 내렸다.
**접힌 상자는 안 열어도 된다.** 열지 않아도 랩은 끝까지 갈 수 있다.
한 번에 다 이해하려고 하지 마라. 모르는 채로 넘어가도 되는 것을 접어 둔 것이다.

## Phase 1에서 우리가 만드는 것

게시판이다. 글을 쓰면 저장되고, 목록으로 볼 수 있다. 여기까지는 평범하다.

다른 점은 딱 하나다. **누가 저장된 글을 몰래 고치면 프로그램이 알아챈다.**

보통의 게시판은 못 알아챈다. 데이터 파일을 에디터로 열어 글자를 바꾸고 저장하면 끝이다.
프로그램은 그게 원래 그랬다고 믿는다. 의심할 근거가 아무 데도 없기 때문이다.

Phase 1은 그 "의심할 근거"를 만드는 과정이다. 도구는 하나뿐이다 — **해시**.
해시로 글을 요약하고, 요약끼리 사슬로 엮고, 여러 글의 요약을 나무로 묶는다.
그러면 어디를 건드려도 계산이 맞지 않게 된다.

## Lab 1.1 — 해시 감각 잡기

> **언제 읽나**: 랩의 "1. 먼저 깨져보기"를 실제로 해본 뒤, "3. 과제" 전에.
> **대응 랩**: [Lab 1.1](../labs/phase-1-chain.md#lab-11--해시-감각-잡기)

### 한 줄로 말하면

긴 내용을 짧은 값 하나로 줄이는 도구를 손에 익히는 랩이다.

### 지금 어디쯤인가

Phase 1의 첫 랩이다. 아직 게시판도, 블록도, 체인도 없다.

앞으로 만들 모든 것이 **해시**라는 도구 하나 위에 선다.
글이 바뀌었는지 아는 것도, 블록을 이어 붙이는 것도, 글 1000개를 한 값으로 요약하는 것도 전부 해시다.
그래서 여기서 도구부터 만져 본다. **이 랩에는 만들 프로그램이 없다.** 관찰이 전부다.

### 이 랩이 답하려는 질문

**파일이 어제와 똑같은지 어떻게 확인하지?**

### 배경 — 알아야 할 것

#### 통째로 비교하는 방법의 문제

어제 받은 설치 파일이 오늘 것과 같은지 확인하고 싶다고 하자.
가장 확실한 방법은 **통째로 비교**다. 첫 바이트부터 끝까지 하나씩 맞춰 본다.

정확하지만 두 가지가 걸린다.

1. **원본을 갖고 있어야 한다.** 2GB 파일이면 2GB를 따로 보관해야 한다
2. **느리다.** 비교할 때마다 전체를 읽어야 한다

그리고 원본을 보관하는 순간 이상해진다. **그 보관본이 안 바뀌었다는 건 또 어떻게 아나?**

#### 해시 — 내용을 짧은 지문으로 줄인다

해시 함수(hash function)는 **아무리 긴 내용이든 짧은 값 하나로 줄이는 함수**다.
그 짧은 값을 해시값, 다이제스트(digest), 또는 그냥 해시라고 부른다.

SHA-256이라는 해시 함수를 쓰면 결과는 **늘 64글자**다. 내용이 1바이트든 10GB든 똑같이 64글자다.

```
"hello"                   → 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
"hello "  (끝에 공백 하나) → 3f79bb7b435b05321651daefd374cdc681dc06faa65e374e38337b88ca046dea
```

이 값을 **지문**이라고 생각하면 거의 맞다. 사람 대신 데이터의 지문이다.

| 지문의 성질 | 해시에서는 |
|---|---|
| 같은 사람은 늘 같은 지문 | **같은 입력은 늘 같은 해시** |
| 지문을 보고 얼굴을 그릴 수 없다 | **해시에서 원래 내용을 되살릴 수 없다** |
| 다른 사람은 다른 지문 | **다른 입력은 다른 해시** (사실상) |

비유가 안 맞는 지점이 하나 있다. 사람은 살이 좀 쪄도 지문이 그대로다.
**해시는 반대다. 한 글자만 바뀌어도 값이 통째로 달라진다.** 위의 `"hello"`와 `"hello "`를 보라.
비슷한 구석이 하나도 없다. 이걸 **눈사태 효과(avalanche effect)**라고 부른다.

정리하면 해시에는 네 가지 성질이 있다.

- **결정성** — 같은 입력이면 언제 어디서 돌려도 같은 값이 나온다
- **눈사태 효과** — 1비트만 달라도 출력이 완전히 달라진다
- **되돌릴 수 없음** — 해시값만 보고 원래 내용을 알아낼 수 없다
- **겹치지 않음** — 같은 값을 내는 서로 다른 입력을 찾을 수 없다

앞의 둘은 **눈에 보인다.** 돌려 보면 바로 확인된다.
뒤의 둘은 **안 보인다.** 그래서 이름을 정확히 알아야 한다. 뒤의 둘에 붙은 이름이
**역상 저항(preimage resistance)**과 **충돌 저항(collision resistance)**이고, 질문 2에서 다룬다.

#### 해시는 바이트열만 먹는다

여기가 이 랩의 진짜 함정이다.

해시 함수는 글자도, 딕셔너리도, 객체도 모른다. **바이트열(bytes)만 안다.**
그래서 파이썬 객체를 해시하려면 누군가 먼저 바이트열로 바꿔야 한다.

```
파이썬 객체  ──(???)──▶  bytes  ──해시 함수──▶  64글자
                ↑
          여기가 비어 있다
```

**그 빈칸을 아무렇게나 채우면 사고가 난다.** 랩에서 보게 될 것이 정확히 그 사고다.

### 랩과 연결하기

랩 §1에서 다섯 가지를 해 본다. 아직 안 했다면 이런 일이 일어난다.

| 랩 실험 | 결과 |
|---|---|
| ① 같은 문자열을 100번 해시 | 100번 다 같은 값 — **결정성** |
| ② 끝에 공백 하나만 추가 | 완전히 다른 값 — **눈사태 효과** |
| ③ `{"author":..,"body":..}` vs 키 순서만 바꾼 것 | **다른 값** ← 문제 |
| ④ `json.dumps(a)` vs `json.dumps(a, indent=2)` | **다른 값** ← 문제 |
| ⑤ 같은 한글을 UTF-8 / UTF-16으로 인코딩 | **다른 값** ← 문제 |

①②는 예상대로다. ③④⑤가 이상하다. **논리적으로 같은 데이터인데 해시가 다르다.**

랩이 던진 질문은 이거다. **해시 함수가 이상한 건가, 내가 넘긴 입력이 달랐던 건가?**

답은 후자다. `{"author": "sam", ...}`이라는 객체는 해시 함수에 닿기 전에 누군가 바이트열로 바꿨다.
그 "누군가"가 매번 다른 바이트열을 만든 것이다. 위 그림의 빈칸을 그때그때 다르게 채웠다.

**해시는 결백하다. 범인은 바이트열로 바꾸는 단계다.**
이 한 문장이 Phase 1 전체의 출발점이고, Lab 1.3에서 `canonical_bytes`를 만드는 이유다.

### 질문 1 — SHA-256의 출력은 항상 몇 비트인가? 입력 길이와 관계가 있나?

**항상 256비트다. 입력 길이와 아무 관계가 없다.**

256비트 = 32바이트 = 16진수로 찍으면 64글자다. 이 세 가지는 같은 말이다.
빈 바이트열을 넣어도 64글자, 10MB를 넣어도 64글자다.

어떻게 그럴 수 있나. SHA-256은 입력을 한 입에 삼키지 않는다.
**입력을 일정한 크기로 잘라 하나씩 먹으면서, 고정된 크기의 "상태"를 계속 갱신한다.**
마지막 상태가 곧 출력이다. 상태 크기가 256비트로 고정이므로 출력도 256비트다.

```
상태(256비트) ─먹고 갱신→ 상태 ─먹고 갱신→ 상태 ─ ... ─▶ 마지막 상태 = 해시값
                  ↑              ↑
               입력 조각 1     입력 조각 2      (조각이 몇 개든 상태 크기는 그대로)
```

**이 성질이 왜 중요한가.** 크기를 미리 알 수 있으면 어디든 넣을 수 있다.
DB 컬럼도, 고정 길이 헤더도, 남의 블록체인 트랜잭션도 32바이트면 들어간다.
Phase 7에서 우리 체인의 상태를 이더리움에 올릴 수 있는 것도 이 덕분이다.

<details>
<summary>더 깊이 — SHA-256이 안에서 하는 일 (지금 몰라도 된다)</summary>

두 단계로 동작한다.

**① 패딩 — 입력을 512비트의 배수로 만든다**

```
[원본 메시지] [1] [0 0 0 ... 0] [원본 길이를 64비트로]
             ↑                  ↑
             구분 비트 하나      "원래 몇 비트였는지"를 끝에 박는다
```

길이를 끝에 박는 것이 중요하다. 이게 없으면 `"ab"`와 `"ab\x00"`처럼
패딩 뒤 모습이 같아지는 입력들이 같은 해시를 낼 수 있다.

**② 압축 함수 — 512비트 블록을 하나씩 먹으며 256비트 상태를 갱신한다**

```
초기 상태(256비트, 상수)
      │
      ▼
  압축함수 ◄── 블록 1 (512비트)
      │
      ▼
  압축함수 ◄── 블록 2
      │
      ▼
     ...              ← 블록이 몇 개든 상태는 항상 256비트
      │
      ▼
   최종 상태 256비트 = 해시값
```

이 구조(패딩 + 압축 함수 반복)를 **Merkle–Damgård 구조**라고 부른다.
Lab 1.4의 머클 트리와 이름이 같은 사람(Ralph Merkle)에서 왔지만 **다른 물건**이다. 헷갈리지 마라.

**부작용 하나**: 최종 상태가 곧 출력이므로, 해시값을 아는 사람은 그 상태에서
**이어서 계속 해시할 수 있다.** 이게 길이 확장 공격(length extension attack)이고,
비트코인이 `SHA256(SHA256(x))`를 쓰는 이유다.
우리 체인은 정규 직렬화가 입력을 확정하므로 단일 SHA-256으로 충분하다.

### 질문 2 — "충돌(collision)"과 "역상(preimage)"은 각각 무엇을 못 하게 만드는 성질인가?

평범한 말로 먼저 풀어 보자. 지문 비유를 그대로 쓴다.

- **역상 찾기** — 지문만 주고 "이 지문의 주인이 누구냐"를 알아내는 것
- **2차 역상 찾기** — 특정 사람을 가리키며 "이 사람과 지문이 같은 다른 사람을 데려와라"
- **충돌 찾기** — 사람은 아무나 좋다. **지문이 같은 두 사람을 아무나 찾아와라**

셋 다 불가능해야 한다. 각각이 깨지면 다른 사고가 난다.

| 성질 | 정의 | 깨지면 공격자가 할 수 있는 일 |
|---|---|---|
| **결정성** | 같은 입력 → 항상 같은 출력 | 검증이 무작위로 실패한다. 애초에 시스템이 안 돈다 |
| **눈사태 효과** | 1비트만 바뀌어도 출력의 절반가량이 바뀐다 | "조금 고쳤으니 해시도 비슷하겠지" 식의 근사 비교가 가능해진다 |
| **역상 저항** (preimage) | 해시값 `h`를 주고 `H(x) = h`인 `x`를 못 찾는다 | 블록 해시만 보고 **글 내용을 복원**한다 |
| **제2 역상 저항** (second preimage) | **특정 `x`가 주어졌을 때** `H(y) = H(x)`인 다른 `y`를 못 찾는다 | **내가 쓴 글 #3을 다른 내용으로 바꿔치기**한다. 해시는 그대로다 |
| **충돌 저항** (collision) | `H(x) = H(y)`인 **아무** 쌍 `(x, y)`를 못 찾는다 | 두 버전의 글을 미리 만들어 두고 나중에 **말을 바꾼다** |

**이 프로젝트에서 각각이 어디에 걸리는지가 중요하다.**

- **제2 역상 저항**이 깨지면 → Lab 1.3의 변조 탐지가 무력해진다.
  공격자가 "같은 해시를 내는 다른 글"을 만들어 끼워 넣는다
- **충돌 저항**이 깨지면 → Lab 1.4의 머클 루트가 무너진다. 서로 다른 글 목록이 같은 루트를 낸다

**제2 역상과 충돌의 차이가 핵심이다.** 전자는 표적이 정해져 있다(내 글 #3을 노린다).
후자는 공격자가 **양쪽 다 고를 수 있다.** 고를 자유가 많을수록 쉽다.
**그래서 충돌이 훨씬 쉽다.** 얼마나 쉬운지는 아래 접이식에 있다.

그리고 미리 말해 둘 것이 하나 있다.
**Lab 1.4에서 만날 CVE-2012-2459는 SHA-256이 깨져서 생기는 문제가 아니다.**
해시는 멀쩡한데 **트리 구조가 스스로 충돌을 만들어낸다.** 직접 보게 된다.

<details>
<summary>더 깊이 — 충돌이 왜 역상보다 훨씬 쉬운가 (지금 몰라도 된다)</summary>

**생일 문제.** 23명이 모이면 같은 생일인 두 명이 있을 확률이 50%를 넘는다.
365일이나 되는데 23명이면 충분하다는 게 직관에 반한다.
비교 대상이 **사람 수가 아니라 쌍의 수**(23×22/2 = 253쌍)이기 때문이다.

해시도 같다. 출력이 `N`가지면 충돌을 찾는 데 `N`번이 아니라 **√N번** 정도면 된다.

| | 값 |
|---|---|
| SHA-256의 출력 가짓수 | 2²⁵⁶ ≈ 10⁷⁷ |
| 역상을 무차별 탐색하는 비용 | 약 2²⁵⁶ |
| **충돌**을 무차별 탐색하는 비용 | 약 **2¹²⁸** ≈ 3.4 × 10³⁸ |

2¹²⁸은 2²⁵⁶에 비하면 "겨우"지만 여전히 **불가능**하다.
비트코인 전체 네트워크의 해시레이트(초당 10²¹회 수준)로 돌려도 10¹⁷년쯤 걸린다.
우주 나이가 1.4 × 10¹⁰년이다.

**기억할 것**: 해시 길이를 반으로 줄이면 충돌 내성은 **제곱근**만큼 줄어든다.
128비트 해시는 2⁶⁴ = 1.8 × 10¹⁹ 번이면 충돌이 나온다. 현대 하드웨어로 도달 가능한 범위다.
"짧게 잘라서 쓰자"는 유혹이 왜 위험한지가 여기 있다.

</details>

### 질문 3 — `hashlib.sha256()`에 str을 그냥 넣으면 왜 `TypeError`가 나나? 이 에러가 사실은 무엇을 강제하고 있는 건가?

```
TypeError: Strings must be encoded before hashing
```

**표면적인 이유**: 해시 함수는 바이트열에 대해 정의된 함수다. `str`은 바이트열이 아니다.
`"안"`이라는 글자는 추상적인 기호 하나이고,
**메모리에서 몇 바이트인지는 인코딩을 고르기 전에는 정해지지 않는다.**

| `"안녕"`의 인코딩 | 바이트 | 길이 |
|---|---|---|
| UTF-8 | `ec 95 88 eb 85 95` | 6 |
| UTF-16LE | `48 c5 55 b1` | 4 |
| EUC-KR | `be c8 b3 e7` | 4 |

**진짜 이유는 이것이다. 파이썬이 "네가 골라라"고 강제하고 있다.**

만약 `hashlib`이 친절하게 "기본 인코딩으로 알아서 처리"해 줬다고 하자.
그 기본값은 운영체제·지역 설정·파이썬 버전에 따라 달라질 수 있다.
그러면 **내 노트북과 서버가 같은 글에 다른 해시를 매긴다.** 에러 없이, 경고 없이.
그리고 Phase 5에서 두 컴퓨터는 영원히 같은 결론에 도달하지 못한다.

`TypeError`는 불친절한 게 아니라 **가장 이른 시점에 터지는 안전장치**다.
랩 ⑤번 실험에서 UTF-8과 UTF-16의 해시가 달랐던 게 바로 이 에러가 막으려던 사고다.

**그리고 이 에러가 강제하는 건 인코딩 하나가 아니다.**
`str`을 못 넘긴다는 건 곧 **"객체 → 바이트열" 변환을 네가 직접 써야 한다**는 뜻이다.
그 변환에는 인코딩 말고도 정할 게 더 있다 — 랩 ③④에서 본 키 순서와 들여쓰기다.

```
파이썬 객체  ──(?)──▶  bytes  ──hashlib──▶  해시
             ↑
        이 빈칸의 이름이 "정규 직렬화(canonical serialization)"이고,
        Lab 1.3 에서 canonical_bytes 로 채운다
```

**랩 ③④⑤는 전부 이 빈칸을 아무렇게나 채웠을 때 생기는 사고다.** 하나의 문제였다.

### 손으로 확인하기

```python
import hashlib

a = hashlib.sha256(b"hello").digest()
b = hashlib.sha256(b"hello ").digest()          # 공백 하나 차이
diff = sum(bin(x ^ y).count("1") for x, y in zip(a, b))
print(diff, "/ 256 비트가 다르다")               # 130 안팎 — 대략 절반이다
print(len(hashlib.sha256(b"x" * 10_000_000).hexdigest()))   # 64 — 입력 10MB, 출력은 그대로
```

눈사태 효과는 "많이 바뀐다"가 아니라 **"각 비트가 동전 던지기처럼 독립적으로 바뀐다"**는 뜻이다.
그래서 입력이 다르면 차이가 늘 128 근처가 된다.
0에 가깝거나 256에 가까운 값이 나오면 그게 이상한 것이다.

### 자주 하는 오해

| 오해 | 실제 |
|---|---|
| "해시가 다르면 내용이 다른 거다" | 맞다. 하지만 **거꾸로는 틀리다.** 내용이 같아도 바이트열이 다르면 해시가 다르다. 랩 ③④⑤가 이것이다 |
| "해시는 암호화다. 풀면 원문이 나온다" | 해시는 **한 방향**이다. 복호화 키 같은 건 없다. 원문이 짧고 뻔하면(비밀번호) 하나씩 넣어 보며 *맞힐* 수는 있다 |
| "충돌은 이론적 얘기고 실제로는 안 일어난다" | SHA-256은 그렇다. **MD5와 SHA-1은 실제로 뚫렸다.** 예제 코드에서 MD5를 봤다면 그건 낡은 코드다 |
| "긴 입력은 해시가 길어진다" | 항상 256비트다. 상태 크기가 고정이다 |
| "해시를 앞 8글자만 잘라 써도 된다" | 8글자 = 32비트. 충돌이 6만 5천 번이면 나온다. **화면 표시용으로만** 잘라라 |
| "`TypeError`는 귀찮으니 `str(x).encode()`로 때우자" | `str(dict)`는 파이썬이 눈으로 보라고 만든 표현이다. 키 순서가 그대로 새어 나오고 버전이 바뀌면 포맷도 바뀐다. **랩 ③의 문제를 더 나쁜 형태로 되살린다** |

방어가 하나도 없는 게시판을 직접 만들고, 직접 고쳐 보고, **아무도 눈치채지 못하는 것**을 확인하는 랩이다.

### 지금 어디쯤인가

Lab 1.1에서 해시라는 도구를 손에 넣었다. 아직 쓰지는 않았다.

방어 없는 게시판을 만들어 놓고, 그게 얼마나 무방비인지를 눈으로 본다.
그 다음 랩(1.3)부터 하나씩 막는다.

**여기서 쓴 코드는 버릴 코드다.** `labs/` 아래에 두고 `src/`에는 넣지 마라.

### 이 랩이 답하려는 질문

**저장해 둔 글을 누가 몰래 고쳤는지 어떻게 알지?**

### 배경 — 알아야 할 것

#### 무언가를 비교하지 않으면 알 수 없다

어제 쓴 글이 오늘도 그대로인지 알고 싶다.
파일을 열어 읽어 보면 지금 내용은 알 수 있다. **그런데 어제 내용을 모른다.**

비교할 상대가 없으면 판단이 불가능하다. 이건 논리의 문제이지 기술의 문제가 아니다.
지금 화면에 보이는 것이 유일한 정보라면, **그게 맞는지 틀린지 말할 근거가 없다.**

```
    [지금 데이터]        [???]
          │               │
          └──── 비교 ─────┘
                 │
                 ▼
           같다 / 다르다
```

그래서 **미리 무언가를 떠 놔야 한다.** Lab 1.1에서 배운 도구가 여기 들어온다 — **해시**다.
글을 쓸 때 지문을 떠 두면, 나중에 다시 지문을 떠서 맞춰 볼 수 있다.

#### 지문을 아무 데나 두면 소용없다

그런데 지문을 **글과 같은 파일에 적어 두면 의미가 없다.**
글을 고치는 사람이 지문도 같이 고치면 그만이기 때문이다.

그래서 조건이 세 개다.

| 조건 | 없으면 |
|---|---|
| ① 지문이 **존재**한다 | 비교 자체가 불가능하다 |
| ② 지문이 **글보다 먼저** 만들어졌다 | 고친 다음 뜬 지문은 변조를 승인한 것일 뿐이다 |
| ③ 지문이 **공격자 손이 닿지 않는 곳**에 있다 | 같이 고쳐진다 |

**Phase 전체가 사실 ③번 하나를 푸는 과정이다.**
재계산에 **비용**을 붙이는 게 Phase 4, 지문을 **남의 컴퓨터**에도 두는 게 Phase 5,
**남의 체인**에 박아 두는 게 Phase 7이다.

#### 글 하나씩 지문을 뜨면 절반만 잡힌다

여기가 이 랩에서 가장 중요한 대목이다. 구체적으로 보자.

글이 세 개 있고, 각각의 지문을 따로 갖고 있다고 하자.

```
글 1 "점심 뭐 먹지"   지문 h1
글 2 "회의 3시"       지문 h2
글 3 "퇴근하자"       지문 h3
```

공격자가 할 수 있는 일을 하나씩 따져 보자.

- **글 2의 내용을 고친다** → 다시 지문을 뜨면 h2와 다르다. **잡힌다**
- **글 2를 지문과 함께 통째로 지운다** → 남은 글 1, 3은 지문이 멀쩡하다. **안 잡힌다**
- **글 1과 글 3의 순서를 바꾼다** → 두 글 다 내용이 안 변했다. 지문도 그대로다. **안 잡힌다**

**지문 하나는 자기 글 하나만 고정한다.**
"이 목록이 세 개짜리다", "1번 다음이 2번이다" 같은 정보는 **어느 지문에도 들어 있지 않다.**

이 "고정한다"를 전문 용어로 **커밋(commit)한다**고 말한다.
지금까지 나온 것을 정리하면 커밋해야 할 것이 세 가지다.

| 커밋 대상 | 막는 것 |
|---|---|
| **개별 값** | 내용 수정 |
| **집합** (목록 전체) | 삭제·삽입 |
| **순서** | 재배열 |

개별 지문은 첫 줄만 한다. **나머지 두 줄이 Lab 1.3과 1.4가 존재하는 이유다.**

#### 세 단어를 구분하라 — 인증·인가·무결성

이 랩에서 일어나는 일에는 정확한 이름이 있다.

| | 묻는 것 | 이 랩에서 |
|---|---|---|
| **인증**(authentication) | 이 요청을 보낸 게 정말 sam인가? | 있어도 소용없다. 요청 자체가 없었다 |
| **인가**(authorization) | sam이 이 글을 고칠 권한이 있나? | 있어도 소용없다. 앱을 안 거쳤다 |
| **무결성**(integrity) | 지금 이 데이터가 **내가 알던 그 데이터**인가? | **이게 없었다** |

로그인·권한·HTTPS는 전부 **앱이라는 문**에 다는 자물쇠다.
파일을 직접 여는 공격자는 문으로 들어오지 않는다.

Phase 3에서 서명을 붙이면 인증이 생기고, Lab 1.3에서 체인을 붙이면 무결성이 생긴다.
**다른 문제이고 다른 도구로 푼다.**

### 랩과 연결하기

랩 §1에서 게시판을 만들고 8가지를 해 본다. 아직 안 했다면 이런 일이 일어난다.

`posts.json`을 에디터로 열어 3번 글을 `"sam이 회사 돈을 횡령했다"`로 바꾸고 저장한다.
`list_all()`을 다시 돌린다. **아무 일도 일어나지 않는다.** 경고도, 에러도, 로그도 없다.

```
[1] sam: 첫 글
[2] sam: 두 번째 글
[3] sam: sam이 회사 돈을 횡령했다      ← 내가 방금 심은 글
[4] sam: 네 번째 글
```

글을 통째로 지워도, 순서를 바꿔도, 작성자 이름을 남의 것으로 바꿔도 똑같다.
프로그램은 3번 글이 원래 그랬다고 믿고, 앞으로도 영원히 그렇게 믿는다.

랩이 던지는 두 번째 질문이 핵심이다. **"관리자만 수정 가능" 권한 체크를 붙이면 막히나?**

**막히지 않는다.** 공격자는 앱의 함수를 부르지 않았다. 앱을 **완전히 우회해서** 파일을 직접 열었다.
배경에서 본 세 단어로 말하면, **인증 실패가 아니라 무결성 부재다.**

### 질문 1 — 이 게시판에서 "데이터가 바뀌었다"를 판단하려면, 원본에 대한 무엇을 미리 갖고 있어야 하나?

**원본에서 뜬 지문(해시)을, 공격자가 못 건드리는 곳에, 미리 갖고 있어야 한다.**
배경의 세 조건이 전부 필요하다.

랩의 게시판에는 **①번부터 없었다.** `posts.json`에 적힌 내용이 유일한 진실이고,
그걸 의심할 근거가 프로그램 어디에도 없었다.

②번은 놓치기 쉽다. **고친 뒤에 뜬 지문은 변조를 승인한 것이지 탐지한 것이 아니다.**
"저장할 때마다 해시를 갱신한다"는 코드는 무결성을 주지 않는다.

③번은 Phase 1 내내 따라다니고, **Phase 1이 끝나도 완전히 풀리지 않는다.**
파일 하나 안에 체인과 해시가 다 들어 있으니, 공격자가 전부 다시 계산하면 통과한다
(→ [Lab 1.3 §8 4번](../labs/phase-1-chain.md#lab-13--블록과-체인)).
그래서 Phase 4·5·7이 있다.

### 질문 2 — 원본 전체를 복사해 두는 것과 원본의 해시를 저장해 두는 것 — 둘 다 변조를 탐지한다. 차이는?

둘 다 탐지한다. 그런데 네 가지가 다르다.

| | 전체 복사 | 해시 저장 |
|---|---|---|
| **크기** | 원본과 같다 (글 10만 개면 10만 개) | 글 개수와 무관하게 **32바이트** |
| **기밀성** | 사본을 가진 쪽이 **내용을 전부 읽는다** | 해시만으로는 내용을 못 얻는다 (역상 저항) |
| **복구 가능성** | **원본을 되살릴 수 있다** | 되살릴 수 없다. "달라졌다"만 안다 |
| **비교 비용** | 전체를 바이트 단위로 대조 | 32바이트 비교 한 번 |

**크기가 이 프로젝트에서 가장 중요하다.**
질문 1의 조건 ③("공격자 손이 닿지 않는 곳")을 떠올려 보라. 그런 장소는 **비싸다.**
Phase 7에서 우리는 이더리움 테스트넷에 지문을 올린다. 거기에 들어가는 바이트마다 실제 돈이 든다.
글 10만 개를 통째로 올릴 수는 없다. **32바이트 하나면 된다는 것이 앵커링을 가능하게 만든다.**

**기밀성도 이 프로젝트에서 실제로 쓰인다.**
본문은 비공개로 두고 해시만 공개하면 "이 글이 그때 존재했다"는 증명만 남길 수 있다.
다만 **이 프로젝트는 학습이 목적이라 본문을 온체인에 통째로 넣기로 결정했다**
(→ [ADR-0002](../decisions/ADR-0002-on-chain-post-body.md)).

**"복구 가능성"은 대개 착각이다.** 사본으로 복구하려면 사본이 무사해야 하는데,
사본이 무사한지는 **또 다른 지문**으로 확인해야 한다. 문제가 한 겹 늘어날 뿐이다.
해시는 "복구"를 포기하는 대신 **"탐지"에만 집중해서 32바이트가 된다.** 좋은 거래다.

### 질문 3 — 각 글의 해시를 따로따로 저장해 두면 4번 공격은 막힌다. 그런데 6번(글 삭제)과 7번(순서 바꾸기)은 막히나?

**막히지 않는다. 그리고 이 문장이 Lab 1.3의 존재 이유다.**

배경에서 본 그대로다. 글마다 해시를 붙이면 **각 해시는 자기 글 하나만 커밋한다.**

```
글마다 해시:                       각 해시가 커밋하는 범위
┌──────────┬──────────┐
│ 글 1     │ h1       │   h1 ──▶ 글 1 의 내용
├──────────┼──────────┤
│ 글 2     │ h2       │   h2 ──▶ 글 2 의 내용
├──────────┼──────────┤
│ 글 3     │ h3       │   h3 ──▶ 글 3 의 내용
└──────────┴──────────┘
                           ← "이 목록이 3개짜리다"를 커밋하는 값은 어디에도 없다
                           ← "2번 다음이 3번이다"를 커밋하는 값도 없다
```

**커밋되지 않은 것은 변조를 탐지할 수 없다.** 랩의 공격 8개에 대입하면 이렇게 된다.

| 공격 | 왜 잡히나 / 안 잡히나 |
|---|---|
| ④ 글 3의 내용 수정 | **잡힌다.** `h3`이 글 3을 커밋한다 |
| ⑥ 글 5를 해시와 **세트로** 삭제 | **안 잡힌다.** 남은 글들은 전부 자기 해시와 일치한다. "원래 몇 개였나"를 아는 값이 없다 |
| ⑦ 글 5와 6의 **순서 교환** | **안 잡힌다.** 두 글 모두 내용이 안 변했으니 해시도 그대로다 |
| ⑧ 작성자 이름 위조 | **안 잡힌다** (해시를 같이 고치면). 이건 무결성이 아니라 **인증** 문제다 → Phase 3 |

한 줄로: **집합에 대한 커밋과 순서에 대한 커밋이 빠져 있다.**

그 둘을 채우는 것이 앞으로 두 랩이다.

| 커밋 대상 | 무엇을 막나 | 랩 1.2의 개별 해시 | 랩 1.3의 체인 | 랩 1.4의 머클 루트 |
|---|---|---|---|---|
| **개별 값** | 내용 수정 | ✅ | ✅ | ✅ |
| **집합** (목록 전체) | 삭제·삽입 | ❌ | ✅ | ✅ |
| **순서** | 재배열 | ❌ | ✅ | ✅ |
| **과거 전체** | 앞 블록 재작성 | ❌ | ✅ (`prev_hash`) | ❌ (그 블록만 커밋) |

마지막 행을 기억해 둬라. **머클 루트는 "과거 전체"를 커밋하지 않는다.**
그게 Phase 7에서 앵커에 머클 루트가 아니라 블록 해시를 올리는 이유다
(→ [ADR-0003](../decisions/ADR-0003-anchor-target.md)). Lab 1.4에서 다시 다룬다.

### 손으로 확인하기

```python
import hashlib
H = lambda s: hashlib.sha256(s.encode()).hexdigest()[:8]

posts, reorder, deleted = ["A", "B", "C"], ["A", "C", "B"], ["A", "B"]
print(sorted(H(p) for p in posts) == sorted(H(p) for p in reorder))   # True ← 순서 교환을 못 잡는다
print({H(p) for p in deleted} <= {H(p) for p in posts})               # True ← 삭제도 그냥 "짧은 목록"이다
print(H("".join(posts)) != H("".join(reorder)))                       # True ← 목록을 한 번에 커밋하면 잡힌다
```

세 번째 줄이 방향을 보여준다. **여러 개를 하나의 해시 입력으로 묶는 순간 집합과 순서가 커밋된다.**
다만 `"".join(...)`은 그 자체로 또 다른 함정을 갖고 있다 — `["AB"]`와 `["A","B"]`가 같은 바이트열이 된다.
**이 함정은 Lab 1.4에서 직접 만난다.** 지금은 방향만 잡아 두면 된다.

### 자주 하는 오해

| 오해 | 실제 |
|---|---|
| "로그인을 붙이면 변조가 막힌다" | 공격자는 앱을 거치지 않았다. **인증과 무결성은 다른 문제다** |
| "파일 권한을 `chmod 400`으로 하면 된다" | 파일 주인과 root는 언제든 되돌린다. 그리고 Phase 7에서 그 root는 **나 자신**이다 |
| "DB(SQLite)에 넣으면 안전하다" | `UPDATE` 한 줄이면 끝이다. **Phase 2의 ② 공격이 정확히 이것이다** |
| "해시를 저장했으니 무결성이 생겼다" | 해시를 **원본과 같은 파일**에 저장하면 같이 고쳐진다. 질문 1의 조건 ③ |
| "변조 탐지 = 변조 방지" | 탐지일 뿐이다. **막지는 못한다.** 블록체인도 못 막는다 — 다만 모두가 **알아챈다** |
| "이 랩 코드는 잘 만들어 두면 나중에 쓴다" | 버릴 코드다. `src/bbschain/`에 넣지 마라 |

### 3줄 요약

1. 비교할 **지문이 미리, 손 닿지 않는 곳에** 없으면 변조는 판단 자체가 불가능하다
2. 해시는 32바이트다. **작다는 것이 지문을 비싼 곳에 둘 수 있게 만든다**
3. 글마다 지문을 뜨면 **수정만** 잡힌다. **삭제와 순서 바꾸기는 안 잡힌다** — 다음 두 랩이 이걸 푼다

## Lab 1.3 — 블록과 체인

> **언제 읽나**: 랩의 "1. 먼저 깨져보기"(글마다 해시만 붙인 중간 버전으로 4가지 공격)를 해본 뒤, "3. 과제" 전에.
> **대응 랩**: [Lab 1.3](../labs/phase-1-chain.md#lab-13--블록과-체인)

### 한 줄로 말하면

글을 상자에 담고, 상자마다 **앞 상자의 지문**을 적어 두는 랩이다.

### 지금 어디쯤인가

Lab 1.2에서 글마다 지문을 뜨는 것만으로는 부족하다는 걸 봤다.
수정은 잡았지만 삭제와 순서 바꾸기는 못 잡았다.

이 랩에서 그걸 푼다. **Phase 1의 본체다.**
여기서 만드는 것이 `src/bbschain/` 아래에 실제로 남고, Phase 7까지 계속 쓰인다.

### 이 랩이 답하려는 질문

**글 하나를 고쳤을 때 "여기가 고쳐졌다"를 프로그램이 알아채게 하려면 무엇을 저장해야 하지?**

### 배경 — 알아야 할 것

#### 블록이란 무엇인가

**블록(block)은 글 몇 개를 담은 상자다.** 그게 전부다.
이름이 거창해서 어렵게 느껴지지만, 자료구조로 보면 그냥 묶음이다.

상자에는 안에 든 내용(글 목록)과, 겉면에 붙은 라벨이 있다.
이 라벨을 **헤더(header)**라고 부른다. 우리 체인의 라벨에는 이런 게 적힌다.

```
┌─ 블록 #3 ───────────────────────────┐
│ 라벨(헤더)                          │
│   index      = 3                    │  몇 번째 상자인가
│   prev_hash  = 앞 상자의 지문       │  ← 이게 핵심이다
│   timestamp  = 1700000000           │  언제 만들었나
│   merkle_root= 안에 든 글들의 요약  │  ← Lab 1.4 에서 채운다
│   nonce / difficulty                │  ← Phase 4 에서 쓴다. 지금은 자리만
├─────────────────────────────────────┤
│ 내용                                │
│   글 A, 글 B, 글 C                  │
└─────────────────────────────────────┘
```

**블록의 지문 = 라벨 전체를 해시한 값**이다. 라벨의 어느 한 글자만 달라져도 지문이 완전히 달라진다.

#### 상자를 잇는다 — 이게 체인이다

이제 핵심이다. **상자마다 앞 상자의 지문을 라벨에 적어 둔다.**

```
  #1 ────────────▶ #2 ────────────▶ #3 ────────────▶ #4
  지문 aaa         prev_hash=aaa    prev_hash=bbb    prev_hash=ccc
                   지문 bbb         지문 ccc         지문 ddd
```

이러면 무슨 일이 생기나. **#2의 글을 한 글자 고쳐 보자.**

#2의 라벨 안에는 글들의 요약이 들어 있다. 글이 바뀌면 요약이 바뀌고, 라벨이 바뀌고,
**#2의 지문이 `bbb`에서 다른 값으로 바뀐다.**

그런데 **#3의 라벨에는 `prev_hash = bbb`가 그대로 적혀 있다.** 파일에 박힌 문자열이라 따라 바뀌지 않는다.
**#2의 진짜 지문과 #3이 기억하는 지문이 어긋난다. 고리가 끊긴다.**

이게 **해시 체인(hash chain)**이다. 블록체인의 "체인"이 바로 이것이다.

공격자가 #3의 `prev_hash`도 고치면? 그러면 #3의 라벨이 바뀌므로 #3의 지문이 바뀌고, 이번엔 #4가 끊긴다.
**하나를 고치면 그 뒤를 전부 다시 계산해야 한다.**

#### 제네시스 — 맨 앞 상자

맨 앞 상자에는 **앞 상자가 없다.** 이 첫 블록을 **제네시스 블록(genesis block)**이라고 부른다.

앞이 없으니 `prev_hash`에 적을 게 없다. 그래도 **필드를 비우지는 않는다.**
비우면 제네시스만 다른 모양이 되고, 검증 코드가 두 갈래로 갈라지기 때문이다.
그래서 **의미 없는 고정값을 채운다.** 자세한 건 질문 2에서 다룬다.

#### 같은 내용이면 항상 같은 바이트가 나와야 한다

Lab 1.1에서 본 문제가 여기서 실제 설계 규칙이 된다.

지문은 **바이트열**에서 나온다. 그런데 같은 블록을 바이트열로 바꾸는 방법이 여러 개면,
**같은 블록에서 여러 개의 지문이 나온다.** 그러면 위 그림의 고리가 아무 때나 끊긴다.

그래서 규칙을 하나 정해서 못 박는다.
**"같은 내용이면 누가, 언제, 어느 컴퓨터에서 돌려도 똑같은 바이트열이 나오게 하는 규칙"** —
이것을 **정규 직렬화(canonical serialization)**라고 부르고, 랩에서 `canonical_bytes`라는 함수로 만든다.

규칙이 없으면 컴퓨터가 여러 대가 됐을 때 이렇게 된다.

```
노드 A: {"author":"sam","body":"hi"}  → 지문 aaa  → "블록 #7 의 지문은 aaa 다"
노드 B: {"body":"hi","author":"sam"}  → 지문 bbb  → "블록 #7 의 지문은 bbb 다"

같은 블록이다. 그런데 A 는 B 가 보낸 블록을 "지문이 틀렸다"며 거부한다.
B 도 A 를 거부한다. 두 체인은 영원히 만나지 못한다.
```

**그래서 직렬화는 "구현 세부사항"이 아니라 모두가 지켜야 할 규칙이다.**
환경마다 실제로 갈리는 지점은 이런 것들이다.

| 항목 | 무엇이 달라지나 |
|---|---|
| **키 순서** | 파이썬 dict는 넣은 순서를 기억한다. 같은 데이터를 다른 순서로 만들면 다른 JSON이 나온다 |
| **공백** | `", "` vs `","`. 라이브러리·포매터 버전에 따라 낀다 |
| **유니코드 이스케이프** | 한글을 그대로 쓸지 `\uXXXX`로 쓸지. 기본값에 의존하면 안 된다 |
| **소수 표기** | `0.1 + 0.2`의 마지막 자리가 언어·버전마다 다르다. **그래서 체인에 소수를 넣지 않는다** |
| **시퀀스 타입** | JSON에는 tuple이 없다. 저장했다 읽으면 `list`로 돌아온다 → Lab 1.5에서 직접 겪는다 |

그리고 **이 규칙은 나중에 못 바꾼다.** 바꾸는 순간 쌓인 블록의 지문이 전부 달라지고,
아무도 변조하지 않았는데 검증이 실패한다.
**규칙 변경은 "설정 바꾸기"가 아니라 "새 체인 시작하기"다.**
Phase 1에서는 블록 10개만 버리면 되니 싸다. **그래서 지금 고정한다.**
→ [ADR-0001](../decisions/ADR-0001-canonical-serialization.md)

> **Lab 1.4에서 `Block.hash` 입력이 바뀌는 건 위반이 아니다.**
> ADR-0001이 금지한 것은 **체인을 이어서 쓰면서** 규칙을 바꾸는 것이다.
> Lab 1.4는 Phase 1 안이고, 쌓인 블록이 10개뿐이고, **체인을 버리고 제네시스부터 다시 만든다.**

#### 과거를 고치는 함수는 아예 만들지 않는다

저장소에 `update_block()`이나 `delete_block()`을 만들지 않는다.
이건 게으름이 아니라 **설계**다. 이런 성질을 **append-only**(붙이기만 가능)라고 부른다.

메서드가 없으면 **정상 경로로는 과거를 고치는 것이 문법적으로 불가능**하다.
"고치지 말자"는 팀 규칙은 잊히지만, **존재하지 않는 함수는 호출할 수 없다.**

그래서 Phase 2의 실습용 변조 기능과 Lab 1.5의 `bbschain tamper`는
**저장소를 우회해 파일을 직접 건드리는 방식**으로 만든다.
공격 실습이 "우회해야만 가능하다"는 사실 자체가 방어가 작동한다는 증거다.

### 랩과 연결하기

랩 §1에서 Lab 1.2의 게시판에 **글마다 해시만** 붙인 중간 버전을 만들고 네 가지를 시도한다.
아직 안 했다면 이런 결과가 나온다.

| 랩 실험 | 결과 |
|---|---|
| ① 글 3의 `body`만 바꾼다 | **잡힌다** (해시 불일치) |
| ② `body`를 바꾸고 `hash` 필드도 새로 계산해 같이 바꾼다 | **안 잡힌다** |
| ③ 글 5를 해시와 세트로 삭제 | **안 잡힌다** |
| ④ 글 5와 6의 순서 교환 | **안 잡힌다** |

**1번만 잡히고 나머지는 전부 통과한다.** Lab 1.2 질문 3에서 예고한 그대로다.

랩이 정확히 짚는다. **②가 가능한 이유는 각 글의 해시가 그 글 자신만으로 계산되기 때문이다.**
그러면 해시 입력에 **무엇을 더 넣어야** ③④까지 막히는가?

답은 **"앞의 것 전부"**다. 그런데 앞의 것 전부를 매번 해시 입력에 넣을 수는 없다.
글이 1000개면 1000개를 다시 바이트열로 만들어야 한다.

그럴 필요가 없다. **앞의 것 전부를 이미 요약하고 있는 값이 하나 있다 — 앞 블록의 지문이다.**
그것 하나만 넣으면 된다. 배경에서 본 체인이 이것이다.

### 질문 1 — 블록 N의 해시 입력에 블록 N-1의 해시가 들어가면, 블록 3을 고쳤을 때 블록 4·5·6은 왜 같이 깨지나?

```
정상 체인

  #2 ──────────▶ #3 ──────────▶ #4 ──────────▶ #5
  hash=aaa       prev_hash=aaa   prev_hash=bbb   prev_hash=ccc
                 hash=bbb        hash=ccc        hash=ddd
                    ▲               │               │
                    └── 일치 ────────┘               │
                                    └── 일치 ────────┘
```

블록 3의 글을 한 글자 고친다. 해시는 내용의 함수이므로 **`hash=bbb`가 즉시 다른 값으로 바뀐다**
(눈사태 효과 — Lab 1.1).

```
#3 변조 직후

  #2 ──────────▶ #3 ──────────▶ #4 ──────────▶ #5
  hash=aaa       prev_hash=aaa   prev_hash=bbb   prev_hash=ccc
                 hash=xyz ◄─변조  hash=ccc        hash=ddd
                    ▲               ▲
                    │               └── #4 는 여전히 "bbb 를 가리킨다"고 적혀 있다
                    │                   그런데 #3 의 실제 해시는 xyz 다  → ❌ 끊김
```

**#4의 `prev_hash` 필드는 옛날 값(`bbb`)을 그대로 담고 있다.** 파일에 박제된 문자열이다.
#3의 해시가 바뀌었다고 #4의 필드가 따라 바뀌지 않는다.

공격자가 #4의 `prev_hash`를 `xyz`로 고치면?
**#4의 해시 입력이 바뀌었으므로 #4의 해시도 바뀐다.** 그러면 #5가 끊긴다.
#5를 고치면 #6이 끊긴다. **끝까지 전부 다시 계산해야 한다.**

> **이게 Phase 4로 이어진다.** 지금은 "전부 다시 계산"이 1밀리초면 끝난다.
> **즉 현재 방어는 반쪽이다.**
> Phase 4에서 재계산 한 번에 실제 비용(작업증명)이 붙는 순간,
> "전부 다시 계산"이 **경제적으로 불가능**해진다.
> **Phase 1이 만드는 것은 "변조 탐지"이지 "변조 방지"가 아니다.**

### 질문 2 — 제네시스 블록의 `prev_hash`에는 무엇을 넣나? 왜 그 값이어야 하나(또는 아무 값이어도 되나)?

**둘 다 맞다. 값 자체는 아무거나 괜찮고, 고정되어 있어야 한다는 것만 절대적이다.**

관습은 `"0" * 64`(32바이트 전부 0)다.
`"genesis"`나 `"우리 체인 v1"`이어도 기능상 동작한다. 단 **한 번 정하면 안 바꾼다.**

왜 고정이 절대적인가. **제네시스의 `prev_hash`는 체인 전체의 정체성이기 때문이다.**

```
GENESIS_PREV = "0"*64  ──▶ 제네시스 해시  ──▶ #1 해시  ──▶ #2 해시  ──▶ ... ──▶ 마지막 해시
     ↑                                                                            │
     └─────────── 이 한 값이 바뀌면 여기까지 전부 바뀐다 ──────────────────────────┘
```

제네시스 해시가 바뀌면 #1의 `prev_hash`가 안 맞고, 그게 #2를 깨뜨리고, 체인 전체가 무효가 된다.

**그리고 Phase 5에서 이 값은 "같은 네트워크인가"의 판별 기준이 된다.**
제네시스가 다른 두 노드는 서로의 블록을 전부 거부한다. **다른 체인이기 때문이다.**

> 비트코인의 제네시스는 `prev_hash`가 0이고, 그 안에
> *"The Times 03/Jan/2009 Chancellor on brink of second bailout for banks"*라는
> 신문 헤드라인이 박혀 있다. **"이 블록이 그날 이전에 만들어지지 않았다"는 증거**다.
> 값 자체는 임의여도 되지만, 그 임의성을 어떻게 쓰느냐는 설계자의 몫이라는 좋은 예다.

### 질문 3 — `validate_chain()`이 `bool` 대신 파손 인덱스를 반환해야 하는 이유는?

**Phase 2의 탐색기가 "3번부터 빨간 줄"을 그려야 하기 때문이다.**
`bool`만 있으면 화면에 "체인이 깨졌습니다"밖에 못 쓴다.
그건 Lab 1.2의 게시판보다 조금 나은 수준이다.

```
ValidationResult(ok=False, first_bad_index=3, reason="block hash does not match its contents")

  #0 ✅  #1 ✅  #2 ✅  #3 🔴  #4 ⚠️  #5 ⚠️  #6 ⚠️
                        ↑      └────────────────┘
                   최초 파손    유효한 조상에서 도달 불가
```

**`first_bad_index`가 "최초"여야 하는 이유가 여기 있다.**
질문 1에서 봤듯 #3이 깨지면 #4·#5·#6이 연쇄로 깨진다. 그런데 **공격자가 손댄 곳은 #3 하나다.**
"최초"를 돌려주면 **공격 지점을 정확히 지목**하는 것이고,
아무 인덱스나 돌려주면 연쇄 피해를 보고하는 것뿐이다.

검증을 앞에서부터 훑으며 **처음 깨진 곳에서 즉시 반환**하면 "최초"가 저절로 보장된다.
반대로 전체를 훑고 나서 "깨진 것들"을 모아 반환하면, 어느 게 원인이고 어느 게 결과인지 알 수 없다.

**일반화하면**: 검증 함수는 "실패했다"가 아니라 **"어디서 왜 실패했다"**를 돌려준다.
블록체인만의 규칙이 아니다. 파서·린터·컴파일러가 전부 이 형태다.
`bool`로 만들어 두면 Phase 2에서 호출부를 전부 고쳐야 한다 — 그래서 **Phase 1에 고정하는 계약**에 들어 있다
(→ [개발계획서 6절](../01-개발계획서.md#phase-1에-고정할-핵심-계약)).

### 손으로 확인하기

```python
import hashlib

def link(prev, body):                      # 학습용 데모다. Block.hash 가 아니다
    return hashlib.sha256((prev + "|" + body).encode()).hexdigest()

g = "0" * 64                                # 제네시스의 prev_hash
tip_ok  = link(link(link(g, "글1"),       "글2"), "글3")
tip_bad = link(link(link(g, "글1(변조)"), "글2"), "글3")
print(tip_ok[:12], tip_bad[:12], tip_ok == tip_bad)    # False
```

**맨 앞 글 하나를 고쳤는데 맨 끝 값이 달라졌다.**
마지막 블록의 지문 하나가 **과거 전체를 요약**하고 있다는 뜻이다.

Phase 7에서 이더리움에 올릴 값이 왜 머클 루트가 아니라 블록 해시인지가 여기서 이미 보인다
(→ [ADR-0003](../decisions/ADR-0003-anchor-target.md)).

### 자주 하는 오해

| 오해 | 실제 |
|---|---|
| "체인이 있으면 변조를 **막는다**" | 막지 못한다. **탐지**할 뿐이다. 공격자가 전부 재계산하면 통과한다 → Phase 4 |
| "`prev_hash`만 있으면 된다" | 그 블록 **자신의 내용**도 해시 입력에 있어야 한다. 아니면 내용만 고치는 공격이 통한다 |
| "제네시스도 `prev_hash`를 검증해야지" | 검증할 대상이 없다. **고정 상수와 같은지**만 본다 |
| "블록 3이 깨졌으면 3만 무효다" | #4 이후가 전부 **유효한 조상에서 도달 불가**다. 무효 판정의 범위가 다르다 |
| "`hash`를 dataclass 필드로 저장하자" | 저장된 해시는 변조 대상이 된다. **재계산해서 대조**하는 것이 검증이다 |
| "timestamp는 단조 증가해야 한다" | Phase 1의 **임시 규칙**이다. Phase 4에서 다른 규칙으로 **교체되어 사라진다** |
| "`nonce`/`difficulty`는 Phase 4에서 넣자" | 그때 넣으면 그때까지의 **모든 블록 해시가 바뀐다.** 쓰지 않는 필드를 미리 넣는 건 낭비가 아니라 보험이다 |
| "저장 파일도 `canonical_bytes` 포맷이어야 한다" | **별개 결정이다.** `chain.json`은 사람이 읽기 좋게 들여써도 된다. 해시는 **복원된 객체**에 대해 다시 계산한다 |

### 3줄 요약

1. **블록은 글을 담은 상자**이고, 상자 라벨에 **앞 상자의 지문**을 적는 것이 체인이다
2. 중간 하나를 고치면 **그 뒤가 전부 어긋난다.** 통과시키려면 끝까지 다시 계산해야 한다
3. 같은 내용이면 항상 같은 바이트열이 나오게 하는 규칙(**정규 직렬화**)이 없으면 이 전부가 무너진다

  **디버깅할 때 눈으로 읽을 수 있어서**이고, 그 대가로 규칙을 ADR에 손으로 못 박아야 한다.

  **"계정 상태 전체"**를 요약한다.
- **"체인이 깨진 상태"는 실제 네트워크에 존재하지 않는다.**
  실제 노드는 유효하지 않은 블록을 **받지 않고 버린다.**
  깨진 체인을 보관하고 "몇 번부터 깨졌다"를 보고하는 것은 **학습용 장치**다. 이 차이를 알고 써라.

### 읽기 A — 과제 전

> **언제 읽나**: 랩 §1의 1~4번(글 4개짜리 블록의 임시 루트, 증명하려면 전부 줘야 한다는 것,
> `["A","B"]`와 `["AB"]`의 충돌)을 해본 뒤, §3 과제 전에.
> **여기서는 홀수 개 처리의 답을 말하지 않는다.** 그건 네가 먼저 틀려 봐야 하는 부분이다.

#### 한 줄로 말하면

블록 안에 든 글 전체를 **32바이트 값 하나**로 요약하는 방법을 배우는 랩이다.

#### 지금 어디쯤인가

Lab 1.3에서 블록을 만들고 체인으로 이었다.
그런데 블록 라벨(헤더)에 `merkle_root`라는 칸을 만들어만 두고 제대로 채우지 않았다.
지금은 "글 전체를 이어붙여 해시한 값" 정도로 임시로 채워 놨을 것이다.

**이 랩에서 그 칸을 제대로 채운다.** 그리고 그 과정에서 실제 취약점 하나를 직접 만난다.

#### 이 랩이 답하려는 질문

**블록에 글이 1000개인데, 라벨에는 값 하나만 적고 싶다. 어떻게 요약하지?**

#### 배경 — 알아야 할 것

##### 라벨에 지문 1000개를 적을 수는 없다

블록 안에 글이 1000개 있다고 하자. 라벨에 글 1000개의 지문을 다 적으면 라벨이 32KB가 된다.
라벨은 작아야 한다. Lab 1.3에서 본 대로 라벨은 블록 지문의 재료이고, 계속 해시된다.

그러면 가장 단순한 방법은 **전부 이어붙여서 한 번 해시하는 것**이다.

```
H( 글1 + 글2 + 글3 + ... + 글1000 )  → 32바이트 하나
```

값 하나로 줄긴 줄었다. 그런데 두 가지가 걸린다.

**① 일부만 보여주고 증명할 수가 없다.**
"글 2번이 이 블록에 들어 있다"를 남에게 증명하려면, 그 사람이 직접 같은 값을 계산해 봐야 한다.
그러려면 **글 1000개를 전부 줘야 한다.** 한 개를 증명하려고 천 개를 보낸다.

**② 경계가 사라진다.**
`"A" + "B"`와 `"AB"`는 이어붙이고 나면 **완성된 바이트열이 똑같다.**
해시는 그 바이트열만 본다. **입력이 같으면 출력이 같다.**
그래서 서로 다른 글 목록이 같은 요약값을 낼 수 있다.
Lab 1.1에서 본 것과 똑같은 구조의 사고다 — **해시는 결백하고, 문제는 바이트열을 만든 방식이다.**

##### 둘씩 묶어 올라간다 — 이게 머클 트리다

①을 푸는 모양이 **트리(tree)**다. 방법은 단순하다.

1. 글마다 지문을 뜬다
2. 지문을 **둘씩 짝지어** 붙여서 다시 해시한다. 개수가 절반이 된다
3. 하나만 남을 때까지 반복한다

```
                      ROOT                        ← 맨 위. 하나만 남는다
                    ╱      ╲
              H(AB)          H(CD)
             ╱     ╲        ╱     ╲
          H(ab)   H(cd)  H(ef)   H(gh)
          ╱  ╲    ╱  ╲   ╱  ╲    ╱  ╲
         a    b  c    d e    f  g    h            ← 글 8개의 지문
```

맨 위에 남은 값 하나가 **머클 루트(Merkle root)**다. 이걸 블록 라벨에 적는다.
맨 아래 칸들을 **리프(leaf, 잎)**, 중간 칸들을 **내부 노드(internal node)**라고 부른다.

트리는 ②도 같이 푼다. 리프와 리프 사이에 **경계가 생기기 때문**이다.
`a`와 `b`는 각각 따로 해시된 뒤에 합쳐지므로, 붙여 쓴 것과 구분된다.

> **글 개수가 홀수면 마지막 하나는 짝이 없다.** 뭔가는 해야 한다.
> **그 "뭔가"를 어떻게 정하느냐가 이 랩의 핵심이고, 여기서는 답을 말하지 않는다.**
> 랩에서 먼저 한 번 정해 보고, 그게 어떻게 깨지는지를 본 다음 읽기 B로 온다.

##### 순서도 루트에 커밋된다

Lab 1.2 질문 3의 표를 다시 보라. 머클 루트는 **집합과 순서를 둘 다** 커밋한다.

`[a, b, c, d]`와 `[b, a, c, d]`는 첫 단계에서 `H(a,b)`와 `H(b,a)`로 갈린다.
붙이는 순서가 다르면 결과가 다르기 때문이다. 그 차이가 루트까지 올라간다.

**그래서 리프를 정렬하면 안 된다.** 정렬하는 순간 순서 정보가 사라지고,
글을 재배열한 블록이 원본과 구분되지 않는다 — Lab 1.2 ⑦번 공격이 그대로 되살아난다.

##### 왜 라벨에 글 전체 대신 루트 하나만 적는가

이유가 두 개다. **둘 다 나중 Phase로 이어진다.**

**① 채굴이 빨라진다.** Phase 4에서 블록을 만들려면 라벨의 숫자 하나(`nonce`)를 바꿔 가며
해시를 **초당 수만~수억 번** 다시 계산한다. 이때 해시 입력에 글 1000개가 들어 있으면
**매번 글 1000개를 다시 바이트열로 만든다.** 글은 한 글자도 안 변했는데도 그렇다.
루트 하나로 요약해 두면 **작은 라벨만** 해싱하면 된다.

**② 라벨만 받아도 검증이 된다.** 비트코인 라벨은 80바이트다.
15년치 라벨을 전부 받아도 수십 MB라 휴대폰이 감당한다.
"내 거래가 저 블록에 있다"는 짧은 증명 몇 개로 확인한다. **블록 전체를 받지 않는다.**
이걸 **경량 검증(SPV)**이라고 부른다.

> **그래서 `Block.hash`의 입력에서 `txs`를 빼는 것이 이 랩의 과제 2번이다.**
> 그리고 그 순간 **글 집합을 붙잡고 있는 고리가 `merkle_root` 하나뿐**이 된다.
> 고리가 하나뿐이라는 사실이 과제 3번으로 이어진다. 읽기 B에서 다룬다.

#### 랩과 연결하기

랩 §1의 앞부분에서 임시 구현(글 전체를 이어붙인 해시)의 한계 두 가지를 직접 본다.

| 랩 실험 | 결과 |
|---|---|
| ①② 글 4개짜리 블록을 만들고 글 2번만 바꾼다 | 루트가 바뀐다. 여기까지는 문제없다 |
| ③ "글 2번이 이 블록에 있다"를 증명해 보라 | **글 1·2·3·4를 전부 줘야 한다.** 글이 10만 개면 10만 개 전부 |
| ④ `["A","B"]`와 `["AB"]`의 임시 루트를 비교한다 | **같아진다.** 다른 블록인데 같은 루트다 |

배경에서 본 ①②가 정확히 이것이다.
④는 원인이 분명하다 — **이어붙이면 "어디까지가 첫 글인가"라는 정보가 사라진다.**
③이 더 근본적이고, **그걸 푸는 모양이 트리다.**

#### 질문 1 — 리프가 N개일 때 머클 트리의 높이는? 증명에 필요한 해시 개수는?

**높이는 ⌈log₂ N⌉, 증명에 필요한 해시도 ⌈log₂ N⌉개다.**

겁먹을 식이 아니다. **"절반으로 몇 번 접으면 1이 되나"**가 전부다.
리프 8개면 8 → 4 → 2 → 1. **3번 접으면 끝이다.** 그래서 높이가 3이다.

**증명(proof)이란 무엇인가.** 내 글 하나를 가진 사람이,
**나머지 글을 하나도 안 보고** 루트까지 계산해 올라갈 수 있게 해 주는 재료 묶음이다.
올라가는 길에서 **내가 갖고 있지 않은 반대쪽 짝**만 받으면 된다.

리프 `c`의 포함을 증명한다고 하자.

```
                      ROOT
                    ╱      ╲
              H(AB)          H(CD)
              ▲ 필요          ╱  (이건 내가 계산한다)
             ╱     ╲        ╱
          H(ab)   H(cd)  ...
          ▲ 필요   ╱  ╲
                  c    d
                       ▲ 필요
```

`c`를 가진 사람이 받아야 하는 것: **`d`, `H(ab)`, `H(AB)` — 세 개뿐이다.**
이 셋으로 `H(cd)` → `H(CD)` → `ROOT`를 차례로 계산해, 블록 라벨에 적힌 루트와 맞춰 보면 끝이다.
**글 8개 중 7개를 안 보고도 "c가 들어 있다"가 증명된다.**

| 리프 N | 트리 높이 | 증명 해시 개수 | 증명 크기(32B 기준) |
|---|---|---|---|
| 4 | 2 | **2** | 64 B |
| 8 | 3 | **3** | 96 B |
| 1,024 | 10 | **10** | 320 B |
| 1,000,000 | 20 | **20** | 640 B |

**글이 25만 배(4 → 100만) 늘어도 증명은 10배(2 → 20)다.**
랩 §6이 이 숫자를 직접 출력해 보라고 하는 이유가 이것이다.
표로 읽는 것과 화면에서 보는 건 다르다.

> **각 짝 해시에는 "왼쪽/오른쪽" 방향이 같이 필요하다.**
> `H(왼 + 오)`와 `H(오 + 왼)`은 다른 값이기 때문이다.
> 그래서 랩의 `merkle_proof` 시그니처가 `list[tuple[str, str]]` — **(짝 해시, 'L'|'R')** 쌍이다.
> 방향을 안 담으면 검증이 절반의 확률로 틀린다.

#### 손으로 확인하기 (A)

```python
import math
for n in (4, 8, 1024, 1_000_000):
    h = math.ceil(math.log2(n))
    print(f"리프 {n:>9,}개 → 높이 {h:>2} · 증명 해시 {h:>2}개 · {h*32:>3} 바이트")
```

**증명 크기가 리프 수에 비례하지 않고 훨씬 천천히 는다**는 것이 머클 트리의 전부다.
"글 100만 개짜리 블록의 포함 증명이 640바이트"라는 숫자를 한 번 보고 가라.

#### 자주 하는 오해 (A)

| 오해 | 실제 |
|---|---|
| "머클 루트는 압축이다" | **요약**이다. 루트에서 글을 복원할 수 없다 (역상 저항 — Lab 1.1 질문 2) |
| "머클 증명은 '이 글이 유효하다'를 증명한다" | **'이 블록에 들어 있다'만** 증명한다. 글이 규칙에 맞는지는 별개다 |
| "루트만 있으면 글 목록을 알 수 있다" | 알 수 없다. 대조만 가능하다 |
| "리프를 정렬하면 비교가 쉬워진다" | **순서 커밋이 사라진다.** 재배열 공격이 통한다 |
| "머클 루트가 있으면 과거 블록 변조도 잡힌다" | **아니다.** 머클 루트는 **그 블록의 글 집합만** 커밋한다. 과거를 커밋하는 건 `prev_hash`다 (→ [ADR-0003](../decisions/ADR-0003-anchor-target.md)) |
| "`merkle_root` 자리에 아무 값이나 넣고 나중에 고치면 된다" | Lab 1.3에서 이미 필드를 고정했다. **값 계산 방식만** Lab 1.4에서 확정한다 |

#### 3줄 요약 (A)

1. 글 전체를 이어붙여 해시하면 **일부만으로 증명할 수 없고, 글 사이의 경계가 사라진다**
2. 지문을 **둘씩 묶어 올라가면** 맨 위에 값 하나가 남는다. 그게 **머클 루트**다
3. 포함 증명은 **올라가는 길의 반대쪽 짝만** 모은 것이라 **글이 100만 개여도 640바이트**다

> 즉 ① 홀수 개 처리를 **네가 정한 방식으로 직접 구현**하고,
> ② `uv run pytest tests/unit/test_merkle.py -k no_two_leaf_lists_share_a_root`를 돌려
> ③ **hypothesis가 반례를 최소 형태로 줄여서 들이미는 것을 화면에서 본 뒤.**
>
> 아직 안 봤으면 **지금 닫고 랩으로 돌아가라.** 이 아래에 답이 있다.

#### 한 줄로 말하면

네 머클 구현이 **서로 다른 글 목록에 같은 루트를 주는** 이유와, 그걸 없애는 방법이다.

#### 랩과 연결하기 — 네가 본 것

```
Failing test case: test_no_two_leaf_lists_share_a_root(
    a=[b'\x00', b'\x01', b'\x02'],
    b=[b'\x00', b'\x01', b'\x02', b'\x02'],
)
  merkle_root(a) == merkle_root(b) == '9d1e...'
```

> hypothesis 버전에 따라 이 줄이 `Falsifying example:`로 나오기도 한다. 같은 것이다.

**글 3개짜리 블록과, 마지막 글을 한 번 더 복사해 붙인 글 4개짜리 블록의 루트가 완전히 같다.**
루트가 같으면 블록 해시도 같다. **변조된 블록과 원본 블록이 구분되지 않는다.**

이건 네 코드의 버그가 아니다.
**비트코인이 2009년부터 갖고 있는 설계 결함이고, 이름이 있다 — CVE-2012-2459.**

#### 질문 2 — 리프 개수가 홀수면 어떻게 처리하나? 복제(duplicate)와 승격(promote) 두 가지가 있는데, 각각 무엇을 잃고 무엇을 얻나?

먼저 **왜 홀수가 문제인가**부터. 트리는 두 개씩 짝지어 접어 올린다. 홀수면 마지막 하나가 짝이 없다.
뭔가는 해야 한다. 선택지가 둘이다.

| | 복제 (duplicate) | 승격 (promote) |
|---|---|---|
| **방식** | 마지막 해시를 하나 더 만들어 자기 자신과 짝지어 해시 | 짝 없는 해시를 **그대로** 다음 단계에 올려 보낸다 |
| **얻는 것** | 트리가 항상 꽉 찬 모양이다. 인덱스 계산이 단순하다. **비트코인과 값이 같다** | **서로 다른 리프 목록이 같은 루트를 낼 수 없다** |
| **잃는 것** | 🔴 **위 성질을 잃는다 (CVE-2012-2459)** | 비트코인과 값이 달라진다. 단계마다 노드 수가 불규칙해진다 |
| **증명 경로** | 승격 노드가 없으므로 경로 길이가 항상 ⌈log₂N⌉ | 승격된 노드는 **짝이 없어 경로에 아무것도 추가하지 않는다** |

**이 프로젝트는 promote를 쓴다.** 왜인지는 질문 3에서.

#### 질문 3 — CVE-2012-2459는 무엇이고, 왜 비트코인은 그걸 알면서도 못 고쳤나? 우리는 왜 고칠 수 있나?

##### 메커니즘 — 왜 `[1,2,3]`과 `[1,2,3,3]`의 루트가 같아지는가

**복제는 "리프를 실제로 하나 더 붙인 것"과 구분되지 않는다.** 이게 전부다.
그림으로 보면 한 단계에서 끝난다.

```
  [1, 2, 3]  ← 리프 3개                     [1, 2, 3, 3]  ← 리프 4개
                                                   ↑ 공격자가 마지막 글을 복사해 붙였다

  단계 0:   h1   h2   h3                    단계 0:   h1   h2   h3   h3
             │    │    │                               │    │    │    │
             └─┬──┘    └── 짝이 없다                   └─┬──┘    └─┬──┘
               │         → 복제해서 (h3,h3)              │         │  원래 한 쌍이다
               ▼            ▼                            ▼         ▼
  단계 1:   H(h1,h2)    H(h3,h3)            단계 1:   H(h1,h2)  H(h3,h3)
             └────┬───────┘                            └────┬──────┘
                  ▼                                         ▼
  ROOT:    H( H(h1,h2), H(h3,h3) )          ROOT:    H( H(h1,h2), H(h3,h3) )

                        ⬆  완전히 같은 값  ⬆
```

**단계 1을 만드는 순간 두 목록이 이미 구분 불가능해진다.** 그 위는 볼 것도 없다.

주의할 점 하나. 흔히 *"`H(h3)`와 `H(h3,h3)`가 둘 다 같은 값이 되기 때문"*이라고 설명하는데 **그건 틀렸다.**
복제 방식에서는 3개짜리 쪽도 **실제로 `H(h3,h3)`를 계산한다.** 양쪽 모두 `H(h3,h3)`다.
충돌의 원인은 **"짝 맞추려고 복제한 것"과 "원래 있던 중복 리프"를 구별할 정보가 트리 어디에도 없다**는 것이다.

그리고 이건 **리프 단계만의 문제가 아니다.** 어느 단계에서든 노드 개수가 홀수면 같은 일이 생긴다.
그래서 Bitcoin Core의 방어(`mutated` 플래그)는 **모든 단계에서** 검사한다. 리프만 검사하면 뚫린다.

##### 공격 — 왜 이게 서비스 거부(DoS)가 되는가

"같은 루트를 만든다"가 왜 위험한지가 처음엔 잘 안 보인다.
거래 내용을 바꾼 것도 아니고 **그냥 마지막 걸 한 번 더 복사했을 뿐**이지 않나?

시나리오를 따라가면 보인다.

```
1. 공격자가 진짜 블록 B 를 받는다.
2. 마지막 tx 를 복제한 변조 블록 B' 를 만든다.
   → B' 의 머클 루트 = B 의 머클 루트
   → B' 의 블록 해시 = B 의 블록 해시      ← 라벨이 완전히 같다
3. 공격자가 B' 를 네트워크에 뿌린다.
4. 노드가 B' 를 검증한다.
   → tx 가 중복이다 (같은 tx 를 두 번 쓸 수 없다)  → "유효하지 않은 블록"
5. 🔴 노드가 "이 블록 해시는 영구 무효" 라고 기억한다.
6. 나중에 진짜 블록 B 가 도착한다.
   → 해시가 같다 → 이미 무효로 기록돼 있다 → 거부
7. 그 노드는 진짜 체인에서 떨어져 나간다.
```

**5번이 급소다.** "이 블록은 틀렸다"를 **블록 해시로 기억**하는 최적화가 문제를 만든다.
정상적인 최적화다 — 같은 나쁜 블록을 반복 검증하지 않으려는 것이다.
그런데 **나쁜 블록과 좋은 블록이 같은 해시를 가질 수 있다**면 그 기억이 독이 된다.

공격자는 **거래를 위조하지 않았다.** 블록을 훔치지도 않았다.
**노드가 진짜 블록을 스스로 거부하게 만들었을 뿐이다.** 그게 DoS다.

##### promote는 왜 이 성질을 없애는가

**복제하지 않으면 "복제한 것"과 "원래 있던 것"을 헷갈릴 일이 없다.**

```
  [1, 2, 3]  · promote 방식                [1, 2, 3, 3]  · promote 방식

  단계 0:   h1   h2   h3                   단계 0:   h1   h2   h3   h3
             └─┬──┘    │ 그대로 올라간다              └─┬──┘    └─┬──┘
               ▼       ▼                                ▼         ▼
  단계 1:   H(h1,h2)   h3                  단계 1:   H(h1,h2)  H(h3,h3)
             └────┬─────┘                            └────┬──────┘
                  ▼                                        ▼
  ROOT:    H( H(h1,h2), h3 )               ROOT:    H( H(h1,h2), H(h3,h3) )

                    ⬆  다르다  ⬆      h3 ≠ H(h3,h3)
```

왼쪽 트리의 단계 1 두 번째 값은 **리프 해시 `h3` 그 자체**이고,
오른쪽은 **내부 노드 `H(h3,h3)`**다. 둘은 다른 값이다. 루트도 달라진다.

**더 일반적으로**: promote 방식에서 서로 다른 목록이 같은 루트를 내려면
SHA-256의 충돌을 실제로 찾아야 한다 — 2¹²⁸ 작업이다(Lab 1.1 질문 2).
**구조가 스스로 충돌을 만들어 주는 일이 없어진다.**
이게 랩 §3의 🔴 불변식이고, hypothesis가 길이 1~20을 흔들며 검사하는 것이다.

##### 왜 비트코인은 못 고치고 우리는 고칠 수 있는가

**비트코인이 복제 방식을 쓰는 건 그게 더 나아서가 아니라 2009년에 그렇게 정해졌기 때문이다.**

머클 루트는 블록 해시의 입력이다. 계산 방식을 바꾸면 **과거 모든 블록의 해시가 바뀐다.**
Lab 1.3에서 배운 그대로다 — **규칙 변경은 설정 변경이 아니라 새 체인 시작이다**
(→ [ADR-0001](../decisions/ADR-0001-canonical-serialization.md)).
15년치 블록과 전 세계 수만 노드를 두고 그럴 수는 없다.

그래서 Bitcoin Core는 **고치는 대신 우회했다.**
루트를 계산하면서 동일한 두 해시를 짝짓게 되는 경우를 보고하고,
그런 블록을 "머클 루트가 틀린 블록"과 같이 취급한다. **모든 단계에서 검사한다.**
그리고 `src/consensus/merkle.cpp`에 **대문자 경고 주석**을 박아 뒀다. 첫 줄이 이렇다:

> `WARNING! If you're reading this because you're learning about crypto and/or designing a new system
> that will use merkle trees, keep in mind that the following merkle tree algorithm has a serious flaw
> related to duplicate txids, resulting in a vulnerability (CVE-2012-2459).`

**이 주석은 정확히 너에게 쓴 것이다.** 지금 네가 하고 있는 일이 저 문장의 상황이다.

**우리는 신규 체인이다.** 비트코인과 블록을 주고받지 않으므로 **값을 맞출 이유가 없다.**
호환성 제약이 없으면 **안전한 쪽을 고르는 게 당연하다.** 그래서 promote다.

> ⚠️ **주교재도 안전하지 않다.** `jamesob/tinychain`의 루트 계산에도 이 방어가 없다.
> "유명한 구현이니 그대로 옮기면 되겠지"가 이 랩에서 정확히 깨지는 지점이다.
> → [기술리서치 #머클트리](../02-기술리서치.md#머클트리)

#### 한 가지 더 — 검증은 왜 머클 루트를 재계산해야 하는가

랩 §3의 과제 3번이다. **이걸 빼먹으면 Phase 1 전체의 목적이 무너진다.**

읽기 A에서 본 대로, 과제 2번으로 `Block.hash`의 입력에서 `txs`가 빠진다.
그 순간 구조가 이렇게 된다.

```
        글 집합 (txs)
             │
             │  merkle_root()          ← 유일한 고리
             ▼
        merkle_root 필드  ──┐
        index               │
        prev_hash           ├──▶  라벨 해시 (Block.hash)
        timestamp           │
        nonce               │
        difficulty        ──┘
```

**글 집합을 붙잡고 있는 고리가 `merkle_root` 하나뿐이다.**
그런데 `merkle_root`는 블록에 **적혀 있는 값**이다.
공격자는 글을 고치면서 그 필드를 **안 건드리면** 된다.

```
공격자: 글 #2 의 body 를 "sam이 회사 돈을 횡령했다" 로 고친다.
        merkle_root 필드는 그대로 둔다.
        → txs 는 해시 입력이 아니다 → 라벨 해시가 안 바뀐다
        → prev_hash 링크도 멀쩡하다
        → validate() 통과 🔴
```

**Lab 1.2에서 직접 겪은 "파일을 고쳐도 앱이 눈치 못 챈다"로 그대로 되돌아간다.**

그래서 블록 자기검사에 한 줄이 필요하다 —
**블록에 적힌 `merkle_root`가, 그 블록의 `txs`로 다시 계산한 값과 같은가.**

이건 Lab 1.3에서 배운 원칙의 반복이다. **저장된 값은 믿지 않는다. 재계산해서 대조한다.**
`Block.hash`를 필드로 저장하지 않고 매번 계산하는 것과 정확히 같은 이유다.
**고리가 하나면, 그 고리를 확인하지 않는 검증은 검증이 아니다.**

> 랩 §6의 `test_block_hash_input_excludes_txs`와 `test_tampering_a_post_still_changes_block_hash`가
> **쌍인 이유가 이것이다.** 앞의 것만 통과시키면 성능은 얻고 무결성은 잃는다.

그리고 랩 §3에는 요구가 하나 더 있다 — **리프와 내부 노드를 다른 방식으로 해시하라**는 것이다.
왜 필요한지는 아래 접이식(`도메인 분리`)에 있다.

#### 손으로 확인하기 (B)

```python
import hashlib
H  = lambda *xs: hashlib.sha256(b"".join(xs)).digest()   # 내부 노드
lf = lambda s: hashlib.sha256(s).digest()                # 리프
a, b, c = lf(b"1"), lf(b"2"), lf(b"3")

# 복제 규칙(= 반례가 나온 그 규칙)으로 첫 단계를 접으면 — 과제 구현에 쓰지 마라
level_from_3 = [H(a, b), H(c, c)]   # [1,2,3]   : 짝 없는 c 를 복제해서 (c,c)
level_from_4 = [H(a, b), H(c, c)]   # [1,2,3,3] : (3,3) 이 원래 한 쌍
print(level_from_3 == level_from_4)  # True ← 단계 1 에서 이미 구분이 사라졌다
```

두 줄이 **글자까지 똑같아지는 것**이 이 취약점의 전부다.
서로 다른 리프 목록에서 출발했는데 같은 식에 도달했다. 그 위로는 무엇을 하든 같은 루트가 나온다.

#### 자주 하는 오해 (B)

| 오해 | 실제 |
|---|---|
| "CVE-2012-2459는 SHA-256이 약해서 생긴다" | 해시는 멀쩡하다. **트리 구조가 스스로 같은 입력을 만들어낸다** |
| "`H(h3)`와 `H(h3,h3)`가 같아서 생긴다" | 틀렸다. 복제 방식에서는 3개짜리 쪽도 **실제로 `H(h3,h3)`를 계산한다** |
| "리프 단계에서만 중복을 검사하면 된다" | **모든 단계에서** 생긴다. Core의 `mutated` 검사가 전 단계인 이유다 |
| "거래를 위조한 것도 아닌데 왜 공격인가" | 노드가 **진짜 블록을 영구 거부**하게 만든다. 그게 DoS다 |
| "비트코인이 쓰니까 복제가 표준이다" | 호환성 때문에 **못 고치는 것**이다. Core 소스에 대문자 경고가 박혀 있다 |
| "promote면 증명 코드는 그대로 둬도 된다" | **승격된 노드는 짝이 없다.** 경로에 넣을 것이 없다. 안 고치면 `verify_proof`가 조용히 실패한다 |
| "도메인 분리는 과한 방어다" | 없으면 **내부 노드를 리프인 척** 제시하는 증명이 통과한다. CT(RFC 6962)가 표준으로 채택한 방어다 |
| "루트 계산만 고치면 끝" | 랩 §3의 과제는 **세 개**다: 머클 교체 + `txs` 제거 + **검증의 머클 재계산** |
| "기존 테스트가 전부 빨개졌다, 뭔가 잘못했다" | **정상이다.** `merkle_root` 정의를 바꿨으니 블록 해시가 전부 바뀐다. 픽스처를 갱신하라 |

#### 3줄 요약 (B)

1. 짝 없는 리프를 **복제하면** 서로 다른 글 목록이 같은 루트를 낸다. 해시가 아니라 **구조의 결함**이다 (CVE-2012-2459)
2. 비트코인은 **호환성 때문에 못 고치고** 우회 검사로 산다. 우리는 신규 체인이라 **promote로 고칠 수 있다**
3. `Block.hash`에서 `txs`를 뺀 순간 고리가 `merkle_root` 하나뿐이다. **검증은 그 값을 반드시 재계산해서 대조해야 한다**

#### 이제 할 일 (B)

- [ ] 홀수 처리를 promote로 바꾸고, 반례 테스트가 초록이 되는 걸 확인한다
- [ ] **증명 코드도 같이 고친다.** 승격된 노드는 경로에 넣을 짝이 없다
- [ ] `Block.hash` 입력에서 `txs`를 뺀다

<summary>더 깊이 — 2차 역상 공격과 도메인 분리 (랩 §3의 마지막 요구)</summary>

CVE-2012-2459가 **구조가 만드는 충돌**이라면, 이건 **타입 혼동**이다. 원인이 다르고 방어도 다르다.

리프 해시와 내부 노드 해시를 **같은 방식으로** 계산하면 어떻게 되나.
공격자는 **내부 노드의 재료를 리프인 척 제시**할 수 있다.

```
정상:                                공격:
   ROOT = H( H(a), H(b) )              ROOT = H( X )            ← 리프가 하나인 트리라고 주장
           ▲     ▲                             ▲
          리프   리프                    X = H(a) || H(b)  를 "리프 하나"로 제시
                                        → 해시하면 같은 ROOT 가 나온다
```

`merkle_root([a, b])`와 `merkle_root([H(a)||H(b)])`가 같은 값이 되어 버린다.
**원본 리프 집합을 모르는 검증자는 두 주장을 구분할 수 없다.** 이게 2차 역상 공격이다.

**방어는 간단하다 — 리프와 내부 노드에 서로 다른 표식을 앞에 붙인다.**
`leaf_hash(x) = H(0x00 || x)`, `node_hash(l, r) = H(0x01 || l || r)` 식이다.
앞 바이트가 다르면 **리프 해시는 절대 내부 노드 해시가 될 수 없다.** 타입이 갈린다.
이것을 **도메인 분리(domain separation)**라고 부른다.

이 방식은 **Certificate Transparency(RFC 6962)**에서 왔다.
랩의 `test_leaf_and_node_hashes_are_domain_separated`가 정확히 위 공격을 재현해서 검사한다.
**앞 바이트가 아닌 다른 방법으로 구분해도 된다. 정하고 기록하라는 것이 랩의 요구다.**

> **Lab 1.4 읽기 A에서 본 "이어붙이기 충돌"과 같은 계열의 문제다.**
> `["A","B"]`와 `["AB"]`가 헷갈린 것도, 리프와 내부 노드가 헷갈리는 것도,
> **바이트열에 경계·타입 정보가 없기 때문**이다. 해시 입력을 설계할 때 반복해서 나오는 주제다.

## Lab 1.5 — 영속화와 검증 CLI

> **언제 읽나**: 랩의 "1. 먼저 깨져보기"(저장→재시작→`validate()` 실패, 그리고 저장 중 Ctrl+C)를 해본 뒤, "3. 과제" 전에.
> **대응 랩**: [Lab 1.5](../labs/phase-1-chain.md#lab-15--영속화와-검증-cli)

### 한 줄로 말하면

만든 체인을 **파일에 안전하게 저장하고, 껐다 켜도 그대로 되살리는** 랩이다.

### 지금 어디쯤인가

Lab 1.3과 1.4에서 체인과 머클 루트를 만들었다. 그런데 전부 메모리 안에만 있다.
**프로그램을 끄면 사라진다.**

이 랩에서 파일에 저장한다. 그리고 여기서 처음으로 **공격자가 아닌 것이 체인을 깨뜨린다.**
평범한 저장 코드가 깨뜨린다.

### 이 랩이 답하려는 질문

**껐다 켜도 남게 저장하려는데, 저장했다 읽었을 뿐인데 왜 체인이 깨지지?**

### 배경 — 알아야 할 것

#### JSON으로 저장하면 타입이 돌아오지 않는다

파이썬 객체를 파일에 남기는 가장 흔한 방법은 JSON이다. 사람이 읽을 수 있고 어디서나 열린다.

그런데 **JSON은 6가지 타입밖에 모른다**: 객체(dict), 배열, 문자열, 숫자, `true`/`false`, `null`.
파이썬의 나머지는 전부 이 6개 중 하나로 **뭉개지거나**, 아예 나가지 못한다.

가장 흔한 사고가 **튜플이다.**

```
저장 전:  ("글A", "글B")     ← tuple
          ──── json.dump → json.load ────
저장 후:  ["글A", "글B"]     ← list 가 되어 돌아온다
```

JSON에는 튜플이라는 개념이 없다. 배열로 나갔다가 리스트로 돌아온다.
**조용히 바뀐다. 경고도 예외도 없다.**

**이게 왜 체인을 깨뜨리는가.** 되살린 객체가 원본과 다르면 `==` 비교가 실패한다.
그리고 바이트열이 달라지면 **지문도 달라진다.** 아무도 변조하지 않았는데 검증이 실패한다.
랩에서 `first_bad_index=1`이 나오는 이유가 이것이다.

#### 저장 포맷과 해시 입력은 별개다

헷갈리기 쉬운 지점이라 먼저 못 박는다.

- **저장 파일**(`chain.json`)은 사람이 읽기 좋게 들여쓰고 한글을 그대로 써도 된다
- **해시 입력**은 Lab 1.3에서 정한 정규 직렬화 규칙을 따른다

둘은 같을 필요가 없다. **파일에서 객체로 되살린 다음, 그 객체로 해시를 다시 계산**하기 때문이다.
그래서 진짜로 지켜야 할 것은 **"되살린 객체가 원래 객체와 똑같은가"** 하나다.

#### 원자적 쓰기 — 쓰다가 죽어도 파일이 반쯤 망가지지 않게

두 번째 사고는 다른 종류다. **저장 도중에 프로그램이 죽는 경우다.**

파일에 직접 쓰면 이렇게 된다.

```
  [기존 체인 10000 블록] ──write()──▶ [새 체인의 앞 절반만 쓰인 상태] ──💥 Ctrl+C
                                       ↑
                            이 상태가 디스크에 남는다. JSON 문법이 잘려 있다.
                            원본도 사라졌다. ← 이게 최악이다
```

`write()`는 한 번에 끝나지 않는다. 큰 데이터는 여러 번에 나눠 쓰이고, 중간에 죽으면 중간에서 끊긴다.
**그리고 기존 파일을 열어 덮어쓰기 시작한 순간 원본은 이미 사라진 상태다.**

여기서 필요한 성질을 **원자적(atomic)**이라고 부른다.
**"보는 사람에게 중간 상태가 보이지 않는다"**는 뜻이다. 전이거나 후다. 반쯤은 없다.

**해법은 "쓰기"와 "교체"를 분리하는 것이다.**

```
① 같은 디렉터리에 임시 파일을 만들어 전부 쓴다     ← 여기서 죽어도 원본은 무사하다
② flush() + os.fsync(fd)                          ← 내용이 실제로 디스크에 닿게 한다
③ os.replace(tmp, path)                           ← 🔴 이 한 걸음이 원자적이다
```

**③이 핵심이다.** 이름 바꾸기는 파일 시스템이 **원자적으로 보장**한다.
어느 시점에 봐도 그 경로는 **옛 파일 전체이거나 새 파일 전체**다. 중간이 없다.

#### 저장소를 갈아 끼울 수 있게 만든다

Phase 2에서 저장 방식을 SQLite로 바꾼다. 그때 **체인 코드를 고치고 싶지 않다.**

그래서 "저장소는 이런 함수들을 가진 무언가다"라는 **껍데기(인터페이스)**를 먼저 정하고,
체인은 그 껍데기만 알게 만든다. 파이썬에서는 `Protocol`로 표현한다. 질문 3에서 다룬다.

```
Chain ──── 의존 ────▶ Storage (껍데기)
                          △
              ┌───────────┼───────────┐
        JsonFileStorage  SqliteStorage  FakeStorage
          (Phase 1)       (Phase 2)      (테스트)
```

그리고 이 껍데기에는 **`update_block()`도 `delete_block()`도 없다.**
Lab 1.3에서 본 append-only 설계 그대로다.

### 랩과 연결하기

랩 §1에서 네 가지를 해 본다. 아직 안 했다면 이런 결과가 나온다.

```
2) ValidationResult(ok=False, first_bad_index=1, reason='block hash mismatch')
   ← 저장하고 읽었을 뿐인데 체인이 깨졌다. 아무도 변조하지 않았다.
4) json.decoder.JSONDecodeError: Expecting ',' delimiter: line 1 column 48213
   ← 쓰는 도중 Ctrl+C 한 번에 체인 전체를 잃었다.
```

**둘 다 공격이 아니다.** 하나는 타입이 왕복하지 않아서, 하나는 쓰기가 중간에 끊겨서 생긴 일이다.
Phase 1 내내 "공격자"를 상대했는데, 여기서는 **평범한 저장 코드가 체인을 깨뜨린다.**

랩의 세 번째 질문도 중요하다 — *"Phase 2에서 SQLite로 바꾸려면 지금 코드의 어디어디를 고쳐야 하나?"*
대충 만들면 **코어 전체**를 고쳐야 한다. 이 랩의 산출물은 그 답을 **"한 군데"**로 만드는 것이다.

### 질문 1 — JSON에서 왕복하지 않는 파이썬 타입을 3개 이상 대라

| 파이썬 타입 | JSON 왕복 결과 | 체인이 어떻게 깨지나 |
|---|---|---|
| `tuple` | **`list`로 돌아온다** | 🔴 가장 흔한 사고. `Block.txs`가 tuple인데 list로 복원되면 원본과 `!=`다 |
| `bytes` | **저장 불가** (`TypeError`) | 해시를 bytes로 다루면 저장이 아예 안 된다. 그래서 hex 문자열로 다룬다 |
| `datetime` | **저장 불가** (`TypeError`) | 타임스탬프를 `datetime`으로 두면 저장 단계에서 터진다. 그래서 `int`로 고정한다 |
| `set` | **저장 불가** (`TypeError`) | 애초에 순서가 없어서 해시 입력에 부적합하다 |
| `int` vs `float` | 값에 따라 **`1.0`이 되어 돌아온다** | `1`과 `1.0`은 다른 JSON 문자열 → 다른 해시 |
| `dict`의 **int 키** | **문자열 키로 바뀐다** (`{1: "a"}` → `{"1": "a"}`) | 조용히 바뀐다. 경고가 없다 |
| `Decimal` | 저장 불가 (기본 인코더에서) | 금액을 Decimal로 두면 터진다. 정수 단위로 다룬다 |

**튜플 사고를 정확히 짚어 두자.** 여기서 두 갈래가 나온다.

- **`canonical_bytes`가 tuple과 list를 같은 JSON 배열로 취급하면** → 해시는 **같다.** 문제없다
- **그런데 되살린 dataclass의 `==` 비교는 실패한다** (`(1,2) != [1,2]`). 왕복 테스트가 여기서 빨개진다

**그래서 규칙이 둘 다 필요하다.**

① `canonical_bytes`는 시퀀스를 **한 가지로 통일**해 해시가 흔들리지 않게 하고
  (→ [ADR-0001](../decisions/ADR-0001-canonical-serialization.md) "시퀀스 타입" 행),
② `from_dict`는 **원래 타입으로 정확히 되돌려** 객체 동등성을 복원한다.

두 번째가 랩의 속성 테스트다: **"아무 블록이나 넣어도 `from_dict(to_dict(b)) == b`"**.
왕복이 안 되는 타입은 이 테스트가 전부 잡아낸다.

> **`to_dict`/`from_dict`를 어디 둘 것인가**는 랩이 던지는 설계 질문이다.
> 힌트: Phase 2의 SQLite도, Phase 5의 네트워크 전송도 **같은 변환**이 필요하다.
> 저장소 구현 안에 넣으면 그때마다 복사하게 된다.

### 질문 2 — "원자적 쓰기(atomic write)"란 무엇이고 파일 시스템에서 어떻게 구현하나?

배경에서 본 세 걸음이 답이다. 여기서는 각 걸음이 **무엇을 보장하는지**를 짚는다.

**③ `os.replace`가 원자적인 이유.** 이름 바꾸기는 디렉터리에 적힌 "이 이름은 저 파일" 기록을
한 걸음에 바꾸는 작업이다. 중간 상태가 없다. 그래서 파일 시스템이 원자성을 보장해 준다.

> **`os.rename`이 아니라 `os.replace`인 이유**: `os.rename`은 Windows에서 대상 파일이
> 이미 있으면 실패한다. `os.replace`는 POSIX와 Windows 양쪽에서 원자적으로 덮어쓴다.

**② `fsync`를 빼먹으면 미묘한 사고가 난다.** `write()`가 돌아왔다는 건 "OS 버퍼에 들어갔다"는 뜻이지
"디스크에 닿았다"는 뜻이 아니다. `fsync` 없이 `replace`하면 **교체는 됐는데 새 파일 내용이 아직
디스크에 없는** 순간이 생길 수 있고, 그때 전원이 나가면 빈 파일이 남는다.

파일 시스템이 무엇까지 보장하는지 정리하면 이렇다.

| | 보장하나 |
|---|---|
| `os.replace` 후 경로가 옛 파일 **또는** 새 파일을 가리킨다 | ✅ 보장 |
| 파일 **내용**이 디스크에 있다 | ❌ `fsync(파일)` 해야 한다 |
| **이름 변경**이 디스크에 반영됐다 | ❌ **부모 디렉터리도 `fsync`해야 한다** |
| 파일 **두 개**를 같이 바꾸는 것이 원자적이다 | ❌ 불가능하다. 파일 하나까지다 |
| 쓰다가 죽었을 때 **부분 갱신**이 없다 | ❌ 위 ①②③ 순서를 지켜야 얻는다 |

**마지막 두 줄이 Phase 2로 이어진다.**
`fsync`까지 해도 **여러 파일에 걸친 변경**은 원자적으로 못 만든다.
Phase 5의 reorg는 "블록 여러 개를 되돌리고 여러 개를 붙이는" 작업이고, **중간 상태가 보이면 안 된다.**
파일 저장소로는 손으로 구현해야 하는데, **SQLite는 트랜잭션으로 공짜로 준다.**

> **원자성을 테스트로 어떻게 확인하나**가 랩의 `test_atomic_write_survives_interruption`이다.
> 쓰기 도중 예외를 주입하고 **원본이 그대로인지**를 본다.

### 질문 3 — `Protocol`(구조적 서브타이핑)과 ABC(명목적 상속)의 차이는? 여기선 왜 Protocol이 나은가?

평범한 말로 하면 이렇다.

- **ABC**는 **"이 집안 사람이냐"**를 묻는다. `class X(Storage):`라고 **상속을 선언**해야 Storage다
- **Protocol**은 **"생긴 게 맞냐"**를 묻는다. 필요한 메서드만 갖고 있으면 그게 Storage다

| | ABC (`abc.ABC`) | `Protocol` (PEP 544) |
|---|---|---|
| **판정 기준** | **상속했는가** (명목적) | **모양이 맞는가** (구조적) |
| **구현체가 해야 할 일** | `class X(Storage):`로 명시적 상속 | **아무것도.** 메서드 시그니처만 맞으면 된다 |
| **검사 시점** | 런타임 (인스턴스를 만들 때 미구현이면 에러) | **정적** (mypy가 잡는다) |
| **의존 방향** | 구현체가 인터페이스를 **import 해야 한다** | 구현체가 인터페이스를 **몰라도 된다** |
| **런타임 비용** | 메타클래스가 붙는다 | 없다 |

**여기서 Protocol이 나은 이유는 의존 방향이다.**

ABC면 모든 저장소 구현이 `storage/base.py`를 import해야 한다.
Protocol이면 아무도 import하지 않아도 된다. **모양만 맞으면 Storage다.**

**테스트에서 특히 차이가 난다.** 메모리 위에서만 도는 가짜 저장소(dict 하나짜리)를 쓰고 싶을 때,
ABC면 그것도 `Storage`를 상속해야 한다.
Protocol이면 **`append_block`, `get_block`, `tip`, `iter_blocks`, `height`만 있으면 그게 Storage다.**

그리고 이게 랩의 세 번째 질문과 맞물린다.
*"Phase 2에서 SQLite로 바꾸려면 몇 군데를 고쳐야 하나?"*의 답이
**"한 군데 — `Chain`에 어떤 Storage를 넘길지 정하는 곳"**이 되게 만드는 것이 이 랩의 산출물이다.

**`Chain`이 `JsonFileStorage`를 직접 import 하면 그림이 무너진다.**
랩의 `test_chain_does_not_import_the_json_implementation`이 그걸 기계적으로 막는다.

> **그럼 ABC는 언제 쓰나**: 공통 구현을 물려주고 싶을 때, 또는
> `isinstance` 검사를 런타임에 강제하고 싶을 때다. 우리 `Storage`에는 물려줄 공통 구현이 없다.
> **선언만 있는 인터페이스에는 Protocol이 맞다.**

### 손으로 확인하기

```python
import json, datetime

d = {"txs": ("a", "b"), "ts": 1700000000}
back = json.loads(json.dumps(d))
print(type(back["txs"]).__name__, back == d)    # list False ← tuple 이 사라졌다
print(json.dumps({"ts": 1700000000.0}))         # {"ts": 1700000000.0} ← int 가 아니다
print(json.dumps({1: "a"}))                     # {"1": "a"} ← 키가 조용히 문자열이 됐다
json.dumps({"when": datetime.datetime.now()})   # TypeError ← 이건 아예 못 나간다
```

**세 번째 줄이 제일 고약하다.** 앞의 둘은 타입을 보면 알 수 있고 네 번째는 예외가 난다.
그런데 **int 키가 문자열이 되는 건 경고도 예외도 없다.** 이런 변환이 해시 입력에 끼면 찾기 어렵다.
`canonical_bytes`가 **모르는 타입을 만나면 조용히 넘어가지 않고 예외를 던져야 하는** 이유다.

### 자주 하는 오해

| 오해 | 실제 |
|---|---|
| "저장 포맷과 해시 입력은 같아야 한다" | **별개 결정이다.** `chain.json`은 들여쓰고 한글을 그대로 써도 된다. 해시는 **복원된 객체**로 다시 계산한다 |
| "`os.replace`면 데이터가 안전하다" | 교체가 원자적일 뿐이다. **내용이 디스크에 닿는 것은 `fsync`가 보장**한다 |
| "임시 파일은 `/tmp`에 만들면 된다" | 🔴 **다른 파일시스템이면 `os.replace`가 실패한다.** **같은 디렉터리**에 만들어야 한다 |
| "재시작 후 해시가 달라졌으니 저장이 잘못됐다" | 대개 **왕복 타입**이다. 변조가 아니다. `first_bad_index=1`이 그 신호다 |
| "append-only니까 파일 끝에 붙이면 된다" | JSON 배열은 끝에 못 붙인다(닫는 `]`). JSON Lines를 쓰거나 전체를 다시 쓴다 — **랩이 고르라는 설계 결정이다** |
| "`tamper` 명령은 경고만 찍으면 된다" | 🔴 **환경변수 게이트가 필요하다.** 이대로 Phase 7에 가면 배포된 노드에서 아무나 체인을 깨뜨린다 |
| "`tamper`도 `Storage`로 구현하자" | **구현할 수 없다.** append만 있다. 그리고 **그게 설계다** — 우회해야만 가능하다는 사실 자체가 방어다 |
| "매번 전체 재작성은 비효율이니 지금 고치자" | 블록이 몇 개 안 된다. **Phase 2에서 SQLite가 푸는 문제다.** 지금 최적화하면 랩 하나가 세 배가 된다 |

### 3줄 요약

1. JSON은 타입을 온전히 되돌려 주지 않는다. **튜플이 리스트가 되고, int 키가 문자열이 된다**
2. 해시가 맞으려면 **"되살린 객체 == 원래 객체"**가 성립해야 한다. 왕복 테스트가 이걸 지킨다
3. 저장은 **임시 파일에 쓰고 → fsync → replace**로 한다. 쓰다가 죽어도 원본이 남는다

## SQ 1.6 — Sepolia 맛보기 (사이드 퀘스트)

> **언제 읽나**: 랩의 "1. 먼저 깨져보기"(`chain.json`을 삭제하고 `bbschain verify`)를 해본 뒤.
> **대응 랩**: [SQ 1.6](../labs/phase-1-chain.md#sq-16--sepolia-맛보기-사이드-퀘스트)

### 한 줄로 말하면

내가 만든 체인과 **진짜 공개 체인**이 무엇이 다른지, 한 번 직접 올려 보며 확인하는 곁가지 퀘스트다.

### 지금 어디쯤인가

Lab 1.5까지 오면 체인이 완성된다. 글을 쓰면 블록이 되고, 변조하면 탐지된다.

그런데 그 전부가 **내 노트북 안에서만 돈다.**
체인 파일도 내 것, 검증하는 프로그램도 내 것, 돌리는 사람도 나다.
**내가 거짓말을 하기로 하면 아무도 모른다.**

이 퀘스트는 기술을 배우는 게 아니라 **기준선을 잡는 것**이다.
"진짜 체인은 무엇이 다른가"를 모른 채 Phase 7의 앵커링을 만나면 늦다.

### 이 랩이 답하려는 질문

**내가 만든 체인과 이더리움은 정확히 무엇이 다른가?**

### 배경 — 알아야 할 것

#### 지금까지 만든 것의 한계

Lab 1.3에서 변조를 탐지했다. 그건 진짜다. 계산은 정직하다.

그런데 **그 계산을 아무도 안 보고 있다.**

- 체인 파일이 내 디스크에만 있다 → 지우면 사라진다
- 검증 프로그램도 내가 고칠 수 있다 → "항상 통과"로 바꾸면 끝이다
- 확인하는 사람이 나뿐이다 → 내 말이 곧 진실이 된다

Lab 1.2 질문 1의 조건 ③("공격자 손이 닿지 않는 곳")이 **하나도 충족되지 않은 상태**다.

**진짜 체인은 이걸 어떻게 푸나.** 답은 기술이 아니라 **숫자와 사람**이다.
같은 데이터를 수만 대가 복제해서 갖고 있고, 그걸 되돌리려면 돈이 든다.
그 "돈이 든다"가 핵심이다. 아래 세 가지가 전부 거기서 나온다.

#### 왜 테스트넷 돈은 공짜인가

이더리움에는 **메인넷**(진짜)과 **테스트넷**(연습용)이 있다.
Sepolia는 테스트넷 중 하나다. 여기서 쓰는 ETH는 **공짜로 받는다.** faucet에서 받으면 된다.

공짜인 이유는 단순하다. **아무도 사지 않기 때문이다.**
faucet이 무제한에 가깝게 나눠 주고, 거래소에서 사고팔 수 없다. 희소성이 없으면 가격이 없다.

**그런데 "가격이 없다"는 것이 곧 "보안이 없다"는 뜻이다.** 여기가 핵심이다.

진짜 체인의 안전은 암호학이 아니라 **경제**에서 온다.
과거를 되돌리려면 엄청난 돈을 걸어야 하고, 부정이 들키면 그 돈이 사라진다.
그래서 아무도 안 한다. **걸린 돈의 가치가 0이면 이 장치가 통째로 사라진다.**

| | 메인넷 | Sepolia |
|---|---|---|
| **ETH의 가치** | 실제 시장가 | 0 |
| **공격 비용** | 수백억 원 규모 | 사실상 없음 |
| **되돌릴 수 있나** | 경제적으로 불가능 | **운영 주체가 마음먹으면 가능** |
| **보장의 성격** | **경제적 보안** | "테스트용이니 협조하자"는 **사회적 합의** |
| **리셋될 수 있나** | 아니다 | **그렇다.** 테스트넷은 폐기·교체된다 |

**즉 Sepolia는 "작동 방식"은 메인넷과 같고 "보장"은 없다.**
호출법·비용 계산·확정 시간을 배우기에는 완벽하고,
**"내 데이터가 여기 있으면 안전하다"는 결론을 내리기에는 부적절하다.**

#### 트랜잭션에 아무 바이트나 실을 수 있다

이더리움 트랜잭션에는 `data`라는 칸이 있다.
원래는 **스마트 컨트랙트를 호출할 때 인자를 싣는 자리**다.
그런데 받는 쪽이 컨트랙트가 아니면 **아무도 해석하지 않는다.**
그냥 **블록체인에 영원히 박히는 바이트열**이 된다.

**이게 가장 단순한 형태의 온체인 기록이고, 이 퀘스트가 하는 일이다.**
컨트랙트도, Solidity도, 배포도 필요 없다. 우리 블록 지문 32바이트를 거기에 넣고 보낸다.

다만 **공짜는 아니다.** 이더리움은 연산과 저장에 **가스(gas)**라는 단위로 값을 매긴다.
`data`도 예외가 아니다. **바이트 수에 정비례해서 비용이 는다.**
그리고 트랜잭션 한 건에는 내용과 무관한 **기본료**가 따로 붙는다.

이 "정비례한다"가 설계에 직접 영향을 준다.
지문 32바이트를 올리는 것과 글 본문 2KB를 올리는 것은 **비용이 60배 넘게 차이 난다.**
Lab 1.2 질문 2에서 본 "해시는 32바이트"가 왜 결정적인지가 여기서 돈으로 확인된다.
(정확한 상수는 아래 접이식에 있다.)

#### 확정(finality)이란 무엇인가

"거래가 완료됐다"를 블록체인은 어떻게 말하나. 생각보다 미묘하다.

**비트코인에는 "완료"라는 상태가 아예 없다.**
내 거래가 블록에 들어가도, 누군가 더 긴 체인을 만들어 오면 그 블록이 통째로 밀려날 수 있다.
다만 위에 블록이 쌓일수록 그럴 확률이 급격히 줄어든다.

```
내 거래가 들어간 블록      #100
그 뒤로 쌓인 블록          #101  #102  #103  #104  #105  #106
                           └─────────── 6 컨펌 ───────────┘
```

"6 컨펌 기다려라"는 말은 법칙이 아니라 **"이 정도면 충분히 낮다"는 경험적 관습**이다.
**확률은 0이 되지 않는다.** 이 확률 계산이 Phase 6의 본체다.

**이더리움은 다르다.** 2022년에 방식을 바꾸면서 `finalized`라는 **상태**가 생겼다.
일정 시간(대략 13분)이 지나면 블록이 확정되고, 그걸 되돌리려면
**규칙을 어긴 쪽이 걸어 둔 돈이 실제로 소각된다.** 확률이 아니라 경제적 약속이다.

| | 비트코인 | 이더리움 |
|---|---|---|
| 확정의 성격 | **확률적** — 영원히 0이 되지 않는다 | **경제적으로 결정적** — `finalized` 상태가 있다 |
| 기다리는 기준 | 컨펌 수 (관습 6개 ≈ 1시간) | 시간 (약 13분) |
| 되돌리는 비용 | 계산력 + 전기 | **소각되는 예치금** |

**그리고 우리 체인의 확정은? 없다.** 글을 쓰는 즉시 블록이 되고 그게 끝이다.

### 랩과 연결하기

랩 §1에서 하는 일은 딱 두 줄이다. 아직 안 했다면 이런 일이 일어난다.

`chain.json`을 지우고 `bbschain verify`를 돌린다.
**체인이 사라졌다. 아무도 모르고, 아무도 복구해 주지 않는다.**

랩의 질문이 아프다. **"탐지할 사람이 너 하나뿐이면, 변조 탐지는 무슨 의미가 있나?"**

Lab 1.3에서 변조는 탐지했다. 그런데 **삭제**는? 탐지할 것 자체가 없어졌다.
이 질문의 답이 Phase 5가 존재하는 이유다.

### 질문 1 — 테스트넷의 ETH는 왜 공짜인가? 그게 메인넷과 무엇이 다른가?

배경에서 본 그대로다. **아무도 사지 않아서 공짜이고, 가격이 없으니 보안도 없다.**

한 가지를 더 짚어 두자. **검증자의 성격도 다르다.**
메인넷은 32 ETH를 예치하면 누구나 검증자가 될 수 있다.
테스트넷은 실질적으로 **허가받은 소수**가 운영한다. 그들이 마음먹으면 되돌릴 수 있다.

> **이게 Phase 7 설계에 직접 반영돼 있다.** 우리는 앵커를 Sepolia에 올린다.
> **학습용이므로 그 앵커의 보안 가치는 0에 가깝다.** 배우는 것은 *메커니즘*이지 보장이 아니다.
> 그리고 **앵커링은 실패해도 로컬 체인이 정상 동작하는 선택적 기능으로 분리**한다
> — faucet 고갈·정책 변경·RPC 한도로 언제든 막힐 수 있기 때문이다.

### 질문 2 — 이더리움 트랜잭션의 `data` 필드에는 아무 바이트나 넣을 수 있나? 비용은 어떻게 매겨지나?

**아무 바이트나 넣을 수 있다. 다만 바이트마다 돈을 낸다.**

비용 구조는 두 덩어리다.

- **기본료** — 트랜잭션 한 건이면 무조건 붙는다. 내용과 무관하다
- **바이트당 요금** — `data`에 실은 바이트 수에 정비례한다. 0인 바이트가 조금 더 싸다

그리고 **실제 지불액 = 가스 × 가스 가격**이다.
가스 가격은 네트워크가 붐비는 정도에 따라 시시각각 변한다.
테스트넷에서는 어차피 공짜지만 **숫자는 메인넷과 같은 규칙으로 계산된다.**

##### 그래서 본문을 온체인에 올리면 얼마인가

이 계산이 **[ADR-0002](../decisions/ADR-0002-on-chain-post-body.md)와 Phase 8 IPFS 트랙의 배경**이다.

- 블록 해시 32바이트 → 기본료를 빼면 **수백 가스**
- 글 본문 2KB → 기본료보다 **큰** 금액
- 글 1만 개를 통째로 → 실제 체인에서는 **불가능한 비용**

**"요약 하나만 올린다"는 발상이 앵커링을 가능하게 만든다.**
Lab 1.2 질문 2의 "크기" 행이 여기서 돈으로 환산된다.

### 질문 3 — "확정(finality)"이 되려면 몇 블록을 기다려야 하나? Sepolia와 메인넷이 다른가?

**비트코인은 "몇 블록"으로 답하고, 이더리움은 "몇 분"으로 답한다.** 배경에서 본 차이다.

- 비트코인: **관습적으로 6 컨펌**(약 1시간). 법칙이 아니라 경험값이고, 확률은 0이 안 된다
- 이더리움: **약 13분 뒤 `finalized`**. 되돌리려면 예치금이 소각된다

**Sepolia와 메인넷은 메커니즘이 같다.** 확정까지 걸리는 **시간도 거의 같다.**

**다른 것은 그 확정이 지키는 값이다.** 질문 1에서 본 그대로다 —
메인넷의 `finalized`는 "되돌리려면 수백억 원이 소각된다"는 뜻이고,
Sepolia의 `finalized`는 **"운영 주체가 안 되돌리기로 했다"**는 뜻이다.

> **개발할 때 실질적으로 다른 것**: 테스트넷은 **리셋되거나 폐기될 수 있다.**
> 그리고 faucet·RPC 한도 때문에 **언제든 트랜잭션을 못 보낼 수 있다.**
> 그래서 우리 앵커링은 **실패해도 로컬 체인이 도는 선택적 기능**으로 분리한다.

##### 우리 체인의 확정은?

**없다.** 글을 쓰는 즉시 블록이 되고, 그게 끝이다. 되돌릴 사람도 확인할 사람도 없다.

- **Phase 4**에서 PoW가 붙으면 "되돌리는 데 비용이 든다"가 생긴다
- **Phase 5**에서 포크 선택이 붙으면 **컨펌 수라는 개념 자체가 비로소 의미를 갖는다**
- **Phase 6**에서 컨펌 수 대비 공격 성공 확률을 직접 계산한다

### 이 퀘스트의 진짜 산출물은 코드가 아니다

**트랜잭션 하나 보내는 건 30분이면 끝난다. 그게 목적이 아니다.**
Etherscan 링크도 산출물이 아니다. **산출물은 랩 §3의 비교 표다.**

| 항목 | 내 체인 | Sepolia |
|---|---|---|
| 블록 생성 간격 | | |
| 블록 하나를 만드는 비용 | | |
| 내 글이 저장된 컴퓨터 수 | | |
| 내가 파일을 지우면 | | |
| 변조를 탐지할 수 있는 사람 | | |
| 글을 쓰는 데 드는 돈 | | |
| 확정까지 기다려야 하는 시간 | | |
| 누가 규칙을 바꿀 수 있나 | | |

**이 8행을 직접 채우는 것이 Phase 2~7 전체의 로드맵이 된다.**
각 행의 "내 체인" 칸이 부끄러운 이유가 곧 다음 Phase가 존재하는 이유다.

| 행 | 이 간극을 메우는 Phase |
|---|---|
| 블록 하나를 만드는 비용 | **Phase 4** (PoW) |
| 내 글이 저장된 컴퓨터 수 · 내가 파일을 지우면 | **Phase 5** (P2P·복제) |
| 변조를 탐지할 수 있는 사람 | **Phase 5 + Phase 7** (앵커) |
| 확정까지 기다려야 하는 시간 | **Phase 4 + Phase 6** (컨펌·확률) |
| 누가 규칙을 바꿀 수 있나 | **끝까지 안 줄어든다** — 내가 코드를 고치면 끝이다 |

**마지막 행이 이 프로젝트의 정직한 한계다.** 그리고 **그래서 Phase 7에서 앵커링으로
"실제 체인의 힘을 빌린다."** 내 체인의 상태 요약을 남의 체인에 박아 두면,
**내가 서버를 완전히 장악해도 과거를 조용히 못 지운다.**

### 손으로 확인하기

```python
blk_hash = bytes.fromhex("a3f1" * 16)               # 32바이트 블록 해시
z = blk_hash.count(0)
print(21_000 + z * 4 + (len(blk_hash) - z) * 16, "가스")    # 21,512 — 해시 하나 올리기

body = "오늘 점심 뭐 먹지" * 100                      # 본문 약 2KB
print(21_000 + len(body.encode()) * 16, "가스 ← 본문 길이에 정비례한다")
```

(쓰인 상수 21,000 / 4 / 16이 무엇인지는 아래 접이식에 있다.)

**두 숫자의 차이가 ADR-0002와 Phase 8 IPFS 트랙의 전부다.**
네트워크가 없어도 돌아가는 계산이니, faucet을 기다리는 동안 먼저 해 봐라.

### 자주 하는 오해

| 오해 | 실제 |
|---|---|
| "테스트넷 ETH는 나중에 가치가 생길 수도" | **없다.** 거래소에 상장되지 않고 테스트넷은 폐기된다. 파는 사람이 있으면 사기다 |
| "테스트넷에서 됐으니 메인넷에서도 된다" | 코드는 대개 그렇다. **보안 가정은 전혀 다르다** |
| "`data`에 넣은 건 암호화된다" | **아니다. 전 세계에 평문으로 공개된다.** 비밀은 절대 넣지 마라 |
| "가스는 트랜잭션당 고정이다" | 기본료 + **바이트/연산당 추가**다 |
| "컨펌 6개면 100% 안전" | 확률이 낮아질 뿐이다. **0이 되지 않는다** (비트코인의 경우) |
| "이더리움도 6 컨펌 기다려야 한다" | 이더리움에는 **`finalized` 상태**가 있다. 개념이 다르다 |
| "메인넷 키를 테스트넷에서 써도 안전하다" | 🔴 **절대 금지.** 테스트용 키를 따로 만든다. 실수로 커밋하면 그 키는 버려라 |
| "앵커를 올렸으니 내 체인이 안전해졌다" | 앵커는 **대조 기준**일 뿐이다. 탐지가 강해진 것이지 변조가 막힌 게 아니다 |
| "Etherscan이 보여주니까 진실이다" | Etherscan도 하나의 노드다. **여러 곳에서 대조할 수 있다는 것**이 가치다 |

### 3줄 요약

1. 테스트넷 돈이 공짜인 이유는 **아무도 사지 않아서**이고, 그래서 **경제적 보안이 없다**
2. 트랜잭션에 아무 바이트나 실을 수 있지만 **바이트 수에 정비례해 돈이 든다.** 그래서 요약만 올린다
3. 내 체인에는 확정도, 복제본도, 제3자 검증도 없다. **그 목록이 Phase 2~7의 로드맵이다**

##### 이더리움의 확정이 13분인 이유

```
슬롯(12초) × 32 = 에폭(6.4분)

  에폭 N      ──▶  에폭 N+1  ──▶  에폭 N+2
    │                 │               │
    └── 투표 ─────────┘               │
         justified                    │
              └──── 투표 ─────────────┘
                     finalized  ← 여기부터는 "되돌리려면 예치금이 소각된다"
```

**두 에폭(약 12.8분)이 지나면 블록이 `finalized` 상태가 된다.**
되돌리려면 전체 예치금의 **1/3 이상**이 명백히 규칙을 어겨야 하고,
그러면 **그 예치금이 소각(slashing)된다.**

##### 비트코인의 확정이 확률인 이유

공격자가 #100을 되돌리려면 **#100부터 현재까지를 다시 채굴해서 더 긴(정확히는 누적 난이도가 큰)
체인**을 만들어야 한다. 쌓인 블록이 많을수록 따라잡을 확률이 급격히 떨어진다.
공격자의 계산력이 크면 6 컨펌으로는 부족하다. 이 계산이 **Phase 6의 본체**다.

## Phase 1을 마치며

랩의 [Phase 1 마무리](../labs/phase-1-chain.md#phase-1-마무리)에 자가 점검 질문 7개가 있다.
**막힘없이 답할 수 있으면 이 튜토리얼은 제 역할을 한 것이다.**

한 문장으로 요약하면 Phase 1은 이렇다.

> **해시는 내용을 커밋하고, 체인은 과거를 커밋하고, 머클 루트는 집합과 순서를 커밋한다.
> 그리고 그 전부가 "무엇을 바이트열로 만드는가"라는 한 가지 규칙 위에 서 있다.**

**여기서 만들지 못한 것도 분명히 알고 가라.**

| 없는 것 | 어떤 공격이 통하나 | 어디서 푸나 |
|---|---|---|
| 재계산 비용 | 공격자가 3번부터 끝까지 재계산하면 통과한다 | **Phase 4** (PoW) |
| 복제본 | 파일 하나를 지우면 체인 전체가 사라진다 | **Phase 5** (P2P) |
| 제3자 검증 | 탐지할 사람이 나 하나뿐이다 | **Phase 5 + 7** (앵커) |
| 작성자 인증 | 남의 이름으로 글을 쓸 수 있다 | **Phase 3** (서명) |

**Phase 1이 만든 것은 "변조 탐지"이지 "변조 방지"가 아니다.**
이 문장을 [PROGRESS.md](../PROGRESS.md)에 적고 다음으로 가라.
