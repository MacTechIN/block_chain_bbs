## 1. 목표와 원칙

### 목표
블록체인을 **직접 만들면서** 배운다. 최종 산출물은 글이 블록에 담기고, 채굴되고, 여러 노드가 합의하는
**불변 게시판 + 블록 탐색기 웹앱**이다.

### 관통하는 5가지 원칙

1. **Break-First.** 방어부터 만들지 않는다. 취약한 버전을 먼저 만들고, 내 손으로 공격해서 깨뜨린 다음에야 방어를 도입한다.
   "왜 이게 중요한가"는 설명으로 주입되는 게 아니라 깨져본 뒤에 남는다.
2. **매 Phase 끝에 눈으로 보는 장면이 있다.** 각 Phase 항목의 **"이 단계가 끝나면 네가 직접 보게 되는 것"** 블록이
   그 Phase의 존재 이유다. 화면에 보여줄 장면이 없는 Phase는 쪼개거나 합친다.
3. **기간이 아니라 DoD로 진행한다.** 날짜·주차 계획을 쓰지 않는다. 체크박스가 유일한 진척 신호다.
   각 Phase 머리의 소요(괄호)는 **참고용 감각**일 뿐 약속이 아니다.
4. **손으로 짜는 것과 가져다 쓰는 것을 미리 갈라놓는다.** 5절의 경계표가 기준이다.
   블록체인의 본체(검증 규칙·합의)는 전부 직접, 곡선 수학·전송 계층은 라이브러리.
5. **에이전트는 대신 풀지 않는다.** 랩 대상 모듈은 사용자가 구현한다. 에이전트는 테스트·리뷰·스캐폴딩만 한다.
   (규칙 전문은 [CLAUDE.md](../CLAUDE.md))

### 사용자가 손대지 않는 것
반응형 웹앱 하나만 만든다. PWA·네이티브 앱·모바일 빌드는 범위 밖이다.
합의는 PoW를 본선으로 하고, PoS는 Phase 8 확장 트랙으로 미룬다.

## 3. 이 순서를 고른 이유 (설계 판단)

계획을 그대로 따르기보다 **왜 이 순서인지**를 알아야 중간에 스스로 조정할 수 있다.
아래 네 가지는 여러 배치 중에서 의식적으로 고른 것이다.

### (a) 지갑·서명(Phase 3)을 P2P(Phase 5)보다 앞에 둔다

직관적으로는 "네트워크부터 붙이고 보안은 나중에"가 자연스러워 보인다. 그렇게 하면 다시 짜야 한다.

남의 노드가 보낸 블록을 **받아들일지 말지 판단하려면, 그 안에 든 트랜잭션이 정당한지 판별할 기준이 먼저 있어야 한다.**
그 기준이 곧 서명 검증이다. 서명 없이 P2P를 먼저 만들면 "일단 받고 본다"는 수용 로직이 박히고,
나중에 서명을 넣는 순간 전파·수용·거부 경로를 전부 다시 쓰게 된다.
게다가 Phase 3의 위조 실습(남의 이름으로 글쓰기)은 단일 노드에서 훨씬 빨리 돌려볼 수 있다.

### (b) 탐색기 UI는 Phase 2에서 최소형으로 시작해 매 Phase마다 패널 하나씩 키운다

"UI는 마지막에 몰아서"는 이 프로젝트에서 최악의 선택이다. 두 가지 이유다.

1. 그러면 Phase 3~6 내내 **눈으로 보는 순간이 없다.** 이 프로젝트의 핵심 요구가 바로 그 순간인데 그걸 마지막으로 미루는 셈이다.
2. 조회 API를 일찍 만들면 **코어 모델이 조기에 정리된다.** "블록 하나를 JSON으로 내보내려면 뭐가 필요한가"라는
   질문이 Block 자료구조의 빈 구멍을 즉시 드러낸다.

그래서 탐색기는 Phase 2에서 리스트+상세+배지만 만들고, 이후 Phase마다 패널을 하나씩 추가한다.
지갑 패널(P3) → 채굴 패널(P4) → 네트워크 패널(P5) → 공격 콘솔(P6) → 앵커 패널(P7).

### (c) 공격 실습은 이중 배치한다

공격을 Phase 6에 전부 모으면, Phase 1~4에서 만든 방어가 **무엇을 막는지 모르는 채로** 쌓인다.
그래서 **단일 노드에서 재현 가능한 공격은 해당 Phase 끝에 즉시** 배치하고
(파일 변조 P1, DB 직접 UPDATE P2, 사칭·리플레이 P3, 무한 블록 생성 P4),
**다중 노드가 있어야 가능한 공격만 Phase 6에 모은다** (이중 지출, 포크 경쟁, 51%, 시빌).

### (d) 공개 테스트넷도 이중 배치한다

Phase 7까지 실제 블록체인을 한 번도 안 만지면, 내가 만든 장난감이 진짜와 얼마나 같고 다른지 감이 없다.
그래서 **Phase 1 직후에 짧은 사이드 퀘스트**를 넣는다 — 지갑 만들고, faucet에서 테스트 ETH 받고,
Sepolia에 `data=내 글 해시`인 트랜잭션 1건을 보내고, Etherscan에서 확인한다.
여기서 얻는 건 기술이 아니라 **기준선**이다. "내 체인은 1초에 블록이 생기는데 저긴 12초구나",
"내 체인은 내가 지우면 없어지는데 저긴 안 없어지는구나". 본편 앵커링(**`(높이, 블록 해시)`를 컨트랙트에 기록**)은 Phase 7이다.

### Phase 0 — 기반 세팅 (0.5일)

**목표**: 하루 안에 테스트가 도는 빈 파이썬 패키지와 GitHub 연결을 끝낸다.

**만들 것**
- `git init` + origin 연결 (기본 브랜치 `main`)
- `pyproject.toml` (uv), `src/bbschain/` 레이아웃
- 통과하는 pytest 1개 (실패하는 테스트 1개를 먼저 보고 고치는 순서로)
- ruff + mypy 설정
- `.github/workflows/ci.yml` — push마다 pytest + ruff
- `README.md`, `.gitignore`, `LICENSE`

**배우는 개념**: (블록체인 아님) 반복 가능한 개발 루프.
이후 **모든 Phase의 DoD가 "테스트 통과"로 검증되므로** 이게 없으면 나머지 전부가 검증 불가능해진다.
Phase 0을 건너뛰고 Phase 1로 가면, 체인이 깨졌는지 매번 눈으로 확인하게 된다.

> #### 이 단계가 끝나면 네가 직접 보게 되는 것
> 터미널에서 `uv run pytest`가 **초록색 1 passed**를 찍고,
> GitHub 저장소 커밋 옆에 **초록 체크 표시**가 붙는다.
> 별것 아닌 것 같지만, 이 두 신호가 앞으로 모든 Phase의 합격 판정기다.

**DoD**
- [ ] `uv run pytest` 통과
- [ ] `uv run ruff check` 무경고
- [ ] origin에 push 성공 (커밋은 사용자가 직접)
- [ ] GitHub Actions CI 초록
- [ ] CLAUDE.md의 빌드/테스트 명령 섹션 갱신

**랩**: [phase-0-setup.md](labs/phase-0-setup.md)

### Phase 1 — 단일 노드 체인 + 게시판 코어 (2~4일)

**목표**: 글이 블록에 담기고, **한 글자만 바꿔도 체인 검증이 깨지는 것**을 만든다.

**만들 것**
- `Block` / `Post(Tx)` 자료구조
- `canonical_bytes()` — 해시 입력 정규화 (→ [ADR-0001](decisions/ADR-0001-canonical-serialization.md))
- SHA-256 블록 해시, 제네시스 블록
- `add_post()` → 블록 생성 (이 단계에선 글 1개당 블록 1개로 단순하게)
- `validate_chain()` → **파손 지점을 반환** (bool 아님)
- 머클 루트 계산
- JSON 파일 영속화 + `Storage` 프로토콜 **선언만**
- CLI: `post` / `dump` / `verify` / `tamper`

**배우는 개념**: 해시의 결정성과 눈사태 효과, prev_hash 연결, 머클 트리, append-only 불변성,
**직렬화 방식이 해시를 바꾼다는 사실**(키 순서·공백·인코딩).

> #### 이 단계가 끝나면 네가 직접 보게 되는 것
> 저장된 `chain.json`을 **텍스트 에디터로 열어서** 3번 블록의 글 내용에서 글자 하나를 바꾸고 저장한다.
> 터미널에서 `verify`를 실행하면:
> ```
> INVALID: block #3 hash mismatch — recomputed 9f2a... != stored 4c81...
>          blocks #4..#10 invalidated (chain broken from #3)
> ```
> 여기서 멈추고 스스로 답해야 하는 질문: **왜 #3만 깨지지 않고 뒤가 전부 깨지는가?**
> 이 한 장면이 "블록체인이 왜 변조에 강한가"의 전부다.

**DoD**
- [ ] **고정 시각을 주입했을 때**, 글 10개를 넣으면 체인 길이와 각 블록 머클 루트가 **재실행해도 동일하게** 재현됨
      (`Post.ts`·`Block.timestamp`에 현재 시각이 들어가면 재현되지 않는 것이 정상이다 — 판정은 시각을 주입한 테스트로 한다)
- [ ] 임의 필드를 변조하면 `validate_chain`이 실패를 반환하고 **최초 파손 인덱스**를 보고함
- [ ] 프로세스를 껐다 켜도 체인이 파일에서 그대로 복원됨
- [ ] hypothesis property 테스트 통과 (임의 입력에 대해 불변식 유지)
- [ ] `canonical_bytes` 규칙이 ADR-0001로 기록됨

**사이드 퀘스트 (0.5일)**: Sepolia 맛보기 — 지갑 생성 → faucet → web3.py로 `data=글해시` tx 1건 → Etherscan 확인.
→ 랩 본문의 사이드 퀘스트 절 참고.

**랩**: [phase-1-chain.md](labs/phase-1-chain.md)

### Phase 2 — 블록 탐색기 v1 + 저장소 교체 (3~5일)

**목표**: 브라우저에서 내 체인을 보고, **화면 버튼으로 체인을 깨뜨려 본다.**

**만들 것**
- FastAPI 앱 + uvicorn
- 조회 API: `/api/chain`, `/api/blocks/{hash_or_index}`, `/api/posts`, `/api/status`
- Jinja2 + HTMX 탐색기: 블록 리스트 / 블록 상세 / 글 목록 / **상단 체인 유효성 배지**
- 글쓰기 폼
- `/admin/tamper` 패널 (환경변수로 켜고 끔)
- JSON 파일 → SQLite 마이그레이션 (`Storage` 프로토콜의 두 번째 구현체)

**배우는 개념**: 체인 상태를 외부에 노출하는 인터페이스, 블록 인덱싱·조회 패턴,
저장 계층 추상화(같은 테스트가 두 백엔드를 모두 통과해야 하는 이유).

> #### 이 단계가 끝나면 네가 직접 보게 되는 것
> 브라우저 상단에 **초록색 `CHAIN VALID` 배지**. 글을 쓰면 새 블록이 목록 맨 위에 나타난다.
> `/admin` Tamper 패널에서 과거 글 하나를 수정하고 새로고침하면:
> 배지가 **즉시 빨강 `CHAIN BROKEN at #3`**으로 바뀌고,
> 블록 리스트에서 **3번부터 끝까지 전부 빨간 줄**이 그어진다. Restore를 누르면 원상복구.
> Phase 1에서 터미널 글자로만 봤던 것이 이제 **눈으로 한눈에 보인다.**

**DoD**
- [ ] 브라우저에서 글을 쓰면 새 블록이 목록 최상단에 나타남
- [ ] 블록 상세에 해시 / 이전 해시 / 머클 루트 / nonce / 타임스탬프 / 포함된 글이 모두 표시됨
- [ ] 변조 시 파손 블록부터 끝까지 빨강으로 표시되고 배지가 파손 인덱스를 보고함
- [ ] SQLite 백엔드로 바꿔도 **Phase 1의 코어 테스트가 한 줄도 수정 없이** 전부 통과
- [ ] `/admin/*`이 환경변수 없이는 404 또는 403

### Phase 3 — 지갑 · 서명 · 트랜잭션 (4~6일)

**목표**: **개인키를 가진 사람만** 자기 이름으로 글을 쓸 수 있게 만든다.

**만들 것**
- secp256k1 키 생성, 키 파일 저장/로드 (keystore)
- 주소 파생: 공개키 → 해시 → base58check (체크섬 직접 구현)
- `Transaction` + 서명·검증 — **필드를 추가하는 것이 아니라 Phase 1에 자리만 잡아 둔 `Post(author, body, ts, nonce, sig)`에 값을 채우는 것**이다
  (`from`/`payload`는 `author`/`body`의 다른 이름일 뿐이다. 키 이름이 바뀌면 `canonical_bytes`의 출력이 바뀐다 → 6절 고정 계약 5번)
- nonce 기반 리플레이 방지
- 멤풀 — 아직 블록에 안 들어간 tx 대기열
- 서명 검증을 통과한 tx만 블록에 포함
- 탐색기에 **지갑 패널** + tx 서명 상태 아이콘
- **서명 백엔드 추상화 + `coincurve` 교체** (Phase 3의 마지막 과제)
  `ecdsa`로 원리를 익힌 뒤, **개인키를 다루는 경로만** `coincurve`로 갈아끼운다.
  `ecdsa`는 **검증 오라클로만 남긴다** — CVE-2024-23342(패치 없음) 때문이다. 근거는 5절의 보안 제약 절.

**배우는 개념**: 공개키 암호, **서명 ≠ 암호화**, 주소가 왜 공개키 자체가 아니라 공개키의 해시인가,
체크섬이 오타를 어떻게 잡는가, nonce와 리플레이 공격, 멤풀(확정 전 상태)과 블록(확정 상태)의 차이.

> #### 이 단계가 끝나면 네가 직접 보게 되는 것
> 두 개의 지갑 A, B를 만든다. B의 개인키 없이 **B의 주소를 작성자로 찍어 글을 전송**해 본다.
> 화면에 빨간 글씨로 **`rejected: invalid signature`**.
> 이어서 A가 이미 보낸 정상 tx를 그대로 복사해 다시 보낸다 → **`rejected: nonce already used`**.
> 마지막으로 A의 키 파일을 지운다. 이제 A의 주소로는 **영원히 아무도 글을 못 쓴다.**
> 백업도, 리셋 링크도, 관리자 문의도 없다. 이게 "키를 잃으면 끝"의 실물이다.

**DoD**
- [ ] 키 생성 / 저장 / 로드가 동작하고, 같은 키에서 같은 주소가 나옴
- [ ] 4가지 거부가 전부 동작: ① 서명 없는 tx ② 내용이 변조된 tx ③ 남의 서명을 붙여 재사용 ④ 같은 nonce 재전송
- [ ] 블록 검증이 **포함된 모든 tx의 서명을** 확인함 (하나라도 불량이면 블록 거부)
- [ ] 탐색기에서 주소를 클릭하면 그 주소가 쓴 글 목록이 나옴
- [ ] 잘못된 체크섬 주소를 입력하면 전송 전에 거부됨
- [ ] **서명 백엔드가 인터페이스 뒤로 분리되어 있고, 두 백엔드(`ecdsa` / `coincurve`)의 출력이
      동일 인코딩(DER) + low-S 정규화 후 임의 입력에서 일치함** (property 테스트)
      — **날것 그대로는 일치하지 않는다.** `coincurve.PrivateKey.sign()`은 **DER + low-S 정규화** 출력이고,
      `python-ecdsa`의 `sign_deterministic()` **기본값은 raw `r‖s` + S 미정규화**다.
      RFC 6979로 `k`와 `r`이 같아도 **약 절반의 입력에서 `s`가 `n-s`로 갈려** 바이트 비교가 실패한다.
      `ecdsa` 쪽에 **`sigencode=sigencode_der_canonize`**를 반드시 넘겨라 (`canonize` = low-S 정규화).
- [ ] **개인키를 다루는 프로덕션 경로에 `ecdsa`가 남아 있지 않음** (Phase 4 진입 전 필수 — CVE-2024-23342)
      — **위 대조 테스트에서 쓰는 테스트 전용 키는 예외**다. 두 백엔드를 비교하려면 테스트는 `ecdsa`로도 서명해야 한다.
      금지되는 것은 `src/bbschain/` 안의 키 생성·서명 경로이지 `tests/` 안의 오라클이 아니다.
- [ ] README에 "프로덕션용 아님" 경고가 있음

### Phase 4 — 작업증명(PoW)과 채굴 (3~5일)

**목표**: 블록 생성 권한에 **비용**을 붙인다.

**만들 것**
- nonce 탐색 채굴 루프
- 목표값(target) 비교 — **`Block.difficulty`의 의미는 compact target(nBits)**이다 (6절 고정 계약 2번).
  블록 해시를 256비트 정수로 읽어 target 이하인지 본다. **"선행 0비트 N개"는 직관 설명과 화면 표시용 어휘일 뿐 저장 형식이 아니다** — 아래 별도 항목
- **난이도 재조정 — ASERT(aserti3-2d) 방식** (아래 별도 항목)
- **타임스탬프 검증 3종** (아래 별도 항목)
- 탐색기에 **채굴 패널** — 난이도, 해시레이트, 진행 중인 nonce를 SSE로 실시간 표시

#### `difficulty`는 compact target(nBits)이다 — "선행 0비트 개수"가 아니다

**저장 형식을 여기서 못 박는다.** `Block.difficulty`는 **compact target(nBits)**이고, 선행 0비트 개수를 담는 정수가 아니다.
이유는 취향이 아니라 아래 두 가지가 실제로 깨지기 때문이다.

- **ASERT의 출력은 연속적인 256비트 target이다.** 정수 비트 수로 저장하면 매 블록 반올림되고,
  *"halflife만큼 늦으면 target이 정확히 2배"* 라는 property 테스트가 **통과하지 못한다.**
- **Phase 5의 chainwork는 `2**256 // (target + 1)`로 target을 요구한다.** 비트 수만 있으면 chainwork가
  계단식으로만 증가해 **포크 선택 실험이 뭉개진다.**

**표시와 저장은 다른 문제다.** 탐색기 화면에는 "난이도 22비트"처럼 익숙한 표기를 써도 되고,
랩의 직관 설명과 수동 데모에서도 "선행 0이 몇 개 붙어야 하는가"로 말해도 된다.
**내부에 저장하고 해시 입력에 들어가는 값만은 compact target 하나로 고정한다.**
→ nBits 인코딩 해설은 [기술리서치 #블록헤더](02-기술리서치.md#블록헤더)

#### 난이도 재조정은 ASERT로 한다 (비트코인 방식이 아니다)

**비트코인의 2016블록 방식을 그대로 쓰면 안 된다.** 이유는 학문적인 게 아니라 산술이다:
**2016블록 × 10초 = 5.6시간.** 난이도가 5.6시간에 한 번 조정된다는 뜻이고, 그러면

- 피드백 루프가 너무 길어 **"난이도를 올렸더니 느려지더라"를 관찰할 수가 없다.** 이 Phase의 목적 자체가 사라진다.
- **채굴 노드 하나가 이탈하면 체인이 수 시간 멈춘다.** 노트북에서 실험하는 체인이 다음 조정까지 죽어 있는다.

그래서 **ASERT(aserti3-2d)를 채택한다.** 이 프로젝트에 맞는 이유는 세 가지다.

1. **상태가 `(anchor_height, anchor_time, anchor_target)` 3개뿐이다.** rolling window가 없어 SQLite 스키마가 단순하고,
   reorg가 나도 앵커만 유지하면 된다. LWMA처럼 직전 N블록을 들고 다닐 필요가 없다.
2. **공식이 순수 함수다.** 입력 3개 + 현재 높이·시각 → 출력 1개. **property 기반 테스트에 최적이다.**
   예: *"time_delta가 커지면 target은 단조 증가한다"*, *"정확히 halflife만큼 늦으면 target이 정확히 2배가 된다"* 를 그대로 불변식으로 쓸 수 있다.
3. **매 블록 반응하면서 진동이 없다.** 10초 블록에 halflife를 짧게(10~30분) 잡으면 체감이 즉시 온다.

**비트코인 방식은 "정확한 규칙을 이해하기 위해 읽되, 구현은 ASERT로" 한다.**
`src/pow.cpp`의 4배 clamp와 off-by-one(2016블록 구간인데 2015 간격을 재는 버그)은 **읽고 이해할 가치가 있다** —
특히 off-by-one은 timewarp 공격의 구조적 원인이기도 하다. **읽되 베끼지는 마라.**
→ 공식·수치·원문 링크는 [기술리서치 #35-합의--난이도--포크-선택--reorg](02-기술리서치.md#35-합의--난이도--포크-선택--reorg)

#### 타임스탬프 검증 3종을 처음부터 넣는다

블록 타임스탬프는 채굴자가 **자유롭게 써넣는 값**이다. 검증이 없으면 난이도 조정 전체가 조작 대상이 된다.
세 가지를 **전부** 넣는다. 하나라도 빠지면 Phase 6의 timewarp 데모가 성립하지 않는다.

| # | 검사 | 규칙 | 비트코인 대응 |
|---|---|---|---|
| 1 | **하한 — 중앙값** | 블록 시각이 **직전 N블록 timestamp의 중앙값(MTP)보다 커야** 한다 | **BIP113.** 비트코인은 N=11. 단일 채굴자가 중앙값을 흔들 수 없다는 게 요점 |
| 2 | **상한 — 미래** | 노드의 현재 시각 + 허용치보다 **미래인 블록은 거부** | 비트코인은 2시간. **10초 블록에 2시간은 터무니없다 — 60~120초로 줄인다** |
| 3 | **조정 구간 timewarp 방어** | 난이도 조정 구간의 **첫 블록**이 이전 블록보다 일정 시간(예: 600초) 이상 **과거일 수 없다** | **BIP94** (testnet4, Core 28.0). 메인넷은 아직 논의 중(BIP54) |

3번이 특히 중요하다. 1번(MTP 하한)만으로는 timewarp를 못 막는다 — **"MTP보다 크기만 하면 된다"는 제약뿐이라 반복 가능**하기 때문이다.

**Phase 1의 단조 증가 규칙은 여기서 ①(MTP 하한)으로 대체된다 — 즉 토글 대상 ①이다.**
Lab 1.3의 링크 검증에 박아 둔 `cur.timestamp >= prev.timestamp`는 **머클도 난이도도 없던 시점의 임시 규칙**이었다.
여기서 그 줄을 **지우고** MTP 하한으로 바꾼다. 둘을 함께 두면 안 된다 —
**MTP 규칙의 요점이 "개별 블록은 부모보다 과거일 수 있다"는 것**이라서 단조 증가와 양립하지 않는다.
남겨 두면 Phase 6에서 세 검사를 전부 꺼도 **토글 대상이 아닌 그 규칙이 과거 시각 블록을 거부**해
timewarp 공격이 재현되지 않고, Phase 6 DoD("OFF에서 난이도가 실제로 하락")를 달성할 수 없다.

**이 세 검사는 껐다 켤 수 있게 만들어라.** Phase 6에서 끄고 공격을 성공시킨 뒤 켜서 막는 데모에 그대로 쓴다.

**배우는 개념**: PoW의 의미, 난이도와 기대 시도 횟수의 관계, 해시레이트,
**"비싼 것"이 어떻게 보안이 되는가**, **난이도 조정은 제어 문제라는 것**(반응 속도 vs 진동의 트레이드오프),
타임스탬프가 왜 공격 표면인가와 그 방어.

> #### 이 단계가 끝나면 네가 직접 보게 되는 것
> 채굴 패널의 난이도 슬라이더를 16 → 18 → 20 → 22비트로 올려 본다.
> (움직이는 값은 내부적으로 compact target이지만, **화면에는 익숙한 "몇 비트"로 표시해도 된다.**)
> **한 단계(2비트)마다 채굴 시간이 4배씩** 늘어나는 것을 카운터로 직접 본다 — 1비트마다 2배이므로 2비트면 4배다.
> 그리고 블록 상세 화면에 이런 줄이 뜬다:
> ```
> 이 블록을 재작성하려면: 약 4.2M 해시 × 남은 블록 7개 ≈ 29.4M 해시 (현재 해시레이트로 약 14분)
> ```
> Phase 1에서는 에디터로 3초면 고칠 수 있던 블록이, 이제 고치려면 **돈과 시간이 든다.**

**주의 — 이건 버그가 아니라 학습 소재다**: 순수 파이썬 채굴 루프를 그냥 돌리면
asyncio 이벤트 루프를 블로킹해서 **노드가 웹 요청에 응답하지 않는다.**
이 현상을 먼저 겪은 다음 멀티프로세싱으로 분리하는 것이 이 Phase의 랩에 포함된다.

**DoD**
- [ ] 목표 난이도를 충족하는 해시를 가진 블록만 유효로 인정됨
- [ ] **ASERT 재조정이 목표 블록 간격에 수렴함** (해시레이트 급변 시나리오를 주입한 시뮬레이션 테스트로 검증)
- [ ] **ASERT가 순수 함수로 분리되어 있고 property 테스트를 통과함**
      — 최소 두 가지: *"time_delta 증가 → target 단조 증가"*, *"halflife만큼 늦으면 target이 정확히 2배"*
- [ ] **타임스탬프 검증 3종이 전부 동작하고, 각각 개별로 껐다 켤 수 있음**
  - [ ] ① 중앙값(MTP) 하한 — 중앙값 이하인 블록 거부. **Phase 1의 단조 증가 규칙이 이걸로 교체되어 사라졌을 것**
  - [ ] ② 미래 상한 — 허용치(60~120초) 초과 미래 블록 거부
  - [ ] ③ 조정 구간 첫 블록의 timewarp 방어 — 이전 블록보다 과도하게 과거면 거부
- [ ] 채굴을 중단했다 재개할 수 있음
- [ ] 채굴 중에도 노드가 웹 요청에 응답함 (블로킹 해소)
- [ ] 블록 상세에 "재작성 비용"이 표시됨

### Phase 5 — P2P 네트워크와 합의 (7~10일)

**가장 큰 Phase다. 반드시 5a → 5b → 5c로 쪼개서 진행하고, 각각 따로 DoD를 만족시킨다.**
한 번에 다 하려 들면 여기서 프로젝트가 멈춘다.

#### 5a — 피어 발견과 전파
- **`Transport` 프로토콜 — 노드가 소켓을 모르게 만든다** (아래 별도 항목. **5a의 첫 작업이다**)
- 피어 등록, 핸드셰이크(체인 ID·버전·팁 해시 교환), 하트비트
- 블록·tx gossip (1단계 HTTP+httpx → 2단계 WebSocket 상시 연결)
- 노드 간 API 접두사 `/p2p/*`

##### `Transport` 프로토콜과 결정적 시뮬레이션 테스트

**이것이 Phase 5의 가장 중요한 설계 결정이다.** 코드를 짜기 전에 먼저 읽어라.

P2P 테스트는 방치하면 반드시 **flaky**해진다. 원인은 늘 같다 —
실제 소켓, 실제 시계, 실제 스케줄러가 매 실행마다 다르게 움직이는데 **그 비결정성이 코드 전체에 흩어져 있기** 때문이다.
그래서 "가끔 실패하는데 재현이 안 되는" 테스트가 생기고, 결국 **아무도 안 믿는 테스트**가 된다.

해법은 **모든 비결정성(시간 · 난수 · I/O · 메시지 순서)을 한 지점으로 모으고 시드 하나로 제어하는 것**이다.
FoundationDB가 원조이고 TigerBeetle의 VOPR이 현대적 구현이다. 여기서는 그 축소판을 만든다.

**규칙 네 가지**

1. **노드는 실제 소켓을 모른다.** `Transport` 프로토콜에만 의존한다.
   구현체는 둘: 프로덕션 **`TcpTransport`**, 테스트 **`SimTransport`**.
2. **`SimTransport`는 메시지를 `(도착시각, seq, src, dst, payload)` 힙에 넣고 시각 순으로 배달한다.**
   `seq`는 같은 도착시각에서의 결정적 tie-break용이다 — 이게 없으면 힙 순서가 실행마다 달라진다.
3. **드롭 · 중복 · 재정렬 · 지연은 주입된 `random.Random(seed)`로만 결정한다.**
   전역 `random` 사용 금지. 노드마다 자기 RNG를 주입받는다.
4. **`time.time()` 호출 금지. `clock.now()`를 주입한다.**
   `asyncio.sleep()`도 마찬가지로 주입된 슬립을 거친다 — **시간 조작 라이브러리로는 `asyncio.sleep()`이 빨라지지 않기 때문이다.**

**얻는 것**: 테스트가 실패하면 **시드 하나만 출력하면 된다.** 그 시드로 다시 돌리면 **드롭·재정렬·타이밍까지 완전히 같은 실행이 재현된다.**
파티션 실험도 Docker 없이, 초 단위가 아니라 밀리초 단위로 돌아간다.

**그 위에 hypothesis `RuleBasedStateMachine`을 얹으면** 시드 탐색과 **최소 반례 축소(shrinking)를 공짜로** 얻는다.
"블록 3개 + 재구성 1회"처럼 줄어든 반례가 나오므로 디버깅이 사람이 할 수 있는 크기가 된다.
**Phase 6의 공격 시나리오(이중지불, 포크 경쟁, 셀피시 마이닝)가 이 위에서 자동 탐색된다** — 손으로 시나리오를 짜지 않아도 된다.

**코드 배치**
- `src/bbschain/p2p/transport.py` — `Transport` 프로토콜 + `TcpTransport`
- `tests/sim/` — `SimTransport`, 가상 시계, 불변식 체커, 상태기계
  (`SimTransport`는 프로덕션 코드가 아니므로 `src/` 아래에 두지 않는다)

**Docker 장애 주입과 역할을 나눈다**: **Docker(`network disconnect`, toxiproxy)는 "눈으로 보는 데모",
`tests/sim/`은 "CI가 매번 돌리는 검증"**이다. 둘 다 필요하고, 서로를 대체하지 않는다.
→ 도구와 설계 원본은 [기술리서치 #pytest](02-기술리서치.md#pytest)의 DST 절, [#장애주입](02-기술리서치.md#장애주입)

#### 5b — 동기화
- 초기 블록 다운로드(IBD) — 빈 노드가 네트워크에 붙었을 때 전체를 받아오기
- 고아 블록 풀 — 부모를 아직 못 받은 블록을 버리지 않고 보관

#### 5c — 포크와 재구성
- 포크 선택 규칙: **"최장 체인"이 아니라 누적 난이도(chainwork)가 최대인 체인**
- **동점 처리: chainwork가 같으면 먼저 받은 것(first-seen)을 유지한다** (아래 별도 항목)
- reorg — 패배한 분기의 블록을 되돌리고 그 tx를 멤풀로 복귀
- 탐색기 **네트워크 패널** — 피어 목록, 각 피어의 팁 해시, 포크 시각화

##### 포크 선택에서 틀리기 쉬운 두 지점

**(1) 길이가 아니라 chainwork다.**
공격자가 낮은 난이도 구간을 악용하면 **블록 수는 더 많지만 누적 작업량은 훨씬 작은** 체인을 만들 수 있다.
"최장 체인"은 **모든 블록의 난이도가 같을 때만** chainwork와 일치하는, 부정확한 축약어다.
한 블록의 작업량은 대략 `2**256 // (target + 1)`이고, Python은 `int`가 임의정밀도라 그대로 계산된다.
`blocks` 테이블에 `chain_work` 컬럼을 두고 tip 선택은 **그 값의 최대**로 한다.

> **반례로 읽어 둘 것**: 별 8천 개가 넘는 유명 튜토리얼 저장소 `dvf/blockchain`이
> 포크 선택을 **`if length > max_length` 한 줄**로 구현해 놓았다. **이게 정확히 피해야 할 "최장 체인" 오해다.**
> (그 저장소는 서명도 머클도 없고 PoW가 블록 내용과 무관하다.)
> → [기술리서치 #언제-블록체인이-필요한가](02-기술리서치.md#언제-블록체인이-필요한가)

**(2) 동점일 때는 first-seen이다.**
chainwork가 **정확히 같은** 두 체인이 생기는 일은 흔하다 — 같은 높이에 같은 난이도로 두 블록이 거의 동시에 나오면 그렇다.
이때 **"해시가 더 작은 쪽" 같은 tie-break를 쓰면 안 된다.**
그럴듯해 보이지만, **나중에 도착한 블록이 기존 tip을 밀어내면서 노드마다 결론이 갈리고 reorg가 불필요하게 튄다.**

**규칙: 동점이면 먼저 받은 것을 유지한다. 새 후보가 이기려면 chainwork가 엄격히 더 커야 한다(`>`, `>=` 아님).**
이걸 구현하려면 **수신 순서를 명시적으로 기록해야 한다** — 블록에 `first_seen_at`(또는 단조 증가 수신 시퀀스 번호)을 저장하고,
그 값이 **디스크에도 남아야** 노드를 재시작해도 같은 판단을 한다. 블록 해시나 타임스탬프로 대신할 수 없다(둘 다 채굴자가 정하는 값이다).

**배우는 개념**: 분산 상태, gossip 전파, **합의 = 검증 규칙 + 포크 선택 규칙**,
reorg와 되돌림, "최장 체인"이 왜 부정확한 표현인가, 네트워크 파티션.

> #### 이 단계가 끝나면 네가 직접 보게 되는 것
> `docker compose up`으로 노드 3개를 띄우고 브라우저 탭 3개에 각각 탐색기를 연다.
> 1. A 탭에서 글을 쓴다 → **몇 초 뒤 B와 C 탭에도 같은 블록이 나타난다.** 팁 해시 3개가 동일.
> 2. C를 네트워크에서 끊고, A와 C 양쪽에서 채굴한다 → **포크 그래프가 Y자로 갈라진다.**
>    두 탭의 팁 해시가 서로 다르고, 같은 높이에 다른 블록이 있다.
> 3. C를 다시 연결한다 → **몇 초 뒤 짧은(누적 난이도가 낮은) 쪽 블록이 화면에서 사라지고**,
>    거기 들어 있던 글이 "멤풀 대기 중"으로 되돌아간다.
>
> 이 3번 장면이 이 프로젝트 전체에서 가장 강렬한 순간이다.
> **"확정된 줄 알았던 내 글이 사라질 수 있다"** — 컨펌 수가 왜 필요한지가 여기서 몸으로 온다.

**주의 — 네트워크 분할 실험의 함정**: `docker network disconnect`로 끊었다가 다시 붙일 때
**DNS alias가 복원되지 않는다.** `docker network connect --alias <서비스명> ...`로 붙여야 한다.
이걸 모르면 재연결 후 reorg가 안 일어나고 원인을 찾느라 며칠을 버린다.
또한 노드는 **`--scale`이나 `deploy.replicas`로 늘리면 안 된다** (7절 위험 참고).

**DoD**
- [ ] 3개 노드가 글 작성 후 60초 이내에 **동일한 팁 해시**에 도달
- [ ] 파티션 후 재연결 시 자동 reorg가 일어나고, **패배한 블록의 tx가 유실 없이 멤풀로 복귀**
- [ ] 잘못된 블록을 보내는 악성 피어를 거부하고 차단
- [ ] 완전히 빈 신규 노드가 네트워크에 붙으면 전체 체인을 동기화
- [ ] 3노드 기동 → 분할 → 재연결 전 과정이 **자동화 테스트로** 재현됨
- [ ] **포크 선택이 chainwork 기준이고, 동점에서는 first-seen이 유지됨** (수신 순서가 재시작 후에도 보존됨)
- [ ] **노드 코드에 `socket` / `time.time()` / 전역 `random` 직접 호출이 없음** — 전부 주입된 `Transport` · `clock` · `rng` 경유
- [ ] **`SimTransport` 위에서 드롭·중복·재정렬·지연을 주입한 시나리오가 돌고, 실패 시 출력된 시드 하나로 완전히 재현됨**
- [ ] **hypothesis `RuleBasedStateMachine`이 `tests/sim/` 위에서 돌고 불변식을 검사함**
      (최소: *"최적 체인의 chainwork는 감소하지 않는다"*, *"높이 감소는 reorg 시에만 일어나고 그때 chainwork는 증가한다"*)

### Phase 6 — 공격 시나리오 실습 (4~6일)

**목표**: 앞에서 만든 방어들이 **무엇을 막고 무엇을 못 막는지** 실측한다.

**만들 것**: `labs/attacks/` 재현 스크립트 + 탐색기 **공격 콘솔**(시나리오 실행 버튼, 결과 로그)
시나리오 대부분은 **Phase 5에서 만든 결정적 시뮬레이터(`tests/sim/`) 위에서 자동 탐색**된다 — 아래 DoD 참조.

| # | 시나리오 | 무엇을 확인하나 |
|---|---|---|
| 1 | 과거 블록 위변조 | 재채굴에 실제로 몇 해시·몇 분이 드는가 (실측) |
| 2 | 이중 지출 / 이중 게시 | 분리된 두 노드에 상충하는 tx를 제출하고 재연결하면 어느 쪽이 남는가 |
| 3 | 포크 경쟁 | 해시파워 비율을 바꿔가며 승률을 측정 — 비율과 승률의 관계 |
| 4 | 51% 공격 | 채굴 노드 과반을 잡고 reorg를 강제. **"N컨펌이면 안전한가"** 를 숫자로 |
| 5 | 리플레이 / 서명 위조 재시도 | Phase 3의 방어가 실제로 막는지 재확인 |
| 6 | 시빌 / 스팸 | 피어 위조, tx 플러딩으로 노드를 다운시킨 뒤 레이트 리밋 도입 |
| 7 | **timewarp 공격** | **Phase 4의 타임스탬프 검사를 껐다 켜며 보여준다.** 조정 구간 첫 블록 시각만 과거로 끌어내려 난이도를 계속 떨어뜨린 뒤, 검사를 켜면 같은 공격이 거부되는 것을 확인 |

**배우는 개념**: 컨펌 수의 의미, **확률적 완결성**(finality가 확률이라는 것), 경제적 보안,
공격 비용 모델, DoS 대응, **"검사 하나를 빼면 무엇이 무너지는가"**(timewarp).

> #### 이 단계가 끝나면 네가 직접 보게 되는 것
> 공격 콘솔에서 **`51% Attack` 버튼**을 누른다.
> 내가 1컨펌을 받아 "확정됐다"고 믿었던 글이, 몇 초 뒤 화면에서 **조용히 사라진다.**
> 그리고 실험 결과를 **이론값과 나란히** 놓게 된다:
> ```
> 공격자 해시파워 30% 기준 reorg 성공률 — 이론값 (예시)
> 1컨펌: 62.8%   3컨펌: 32.5%   6컨펌: 13.2%   12컨펌: 2.4%
> ```
> **이 숫자는 예시이자 이론값이다.** Satoshi 백서 §11 / Rosenfeld 공식으로 계산한 값이고,
> 참고로 해시파워 20%면 같은 순서로 **41.6% / 10.3% / 1.4% / 0.02%**다.
> **네가 실측해서 채우는 표는 따로 있다** — [PROGRESS.md](PROGRESS.md)의 "컨펌 수별 reorg 성공률" 표가 그것이고,
> 거기엔 시뮬레이터로 돌린 값을 적는다. **이론값과 실측값을 같은 칸에 섞지 마라.** 둘의 차이를 보는 것이 이 Phase의 산출물이다.
> "비트코인은 6컨펌 기다리세요"라는 말이 어디서 나온 숫자인지 알게 된다.

**DoD**
- [ ] 7개 시나리오 전부 **재현 스크립트 한 줄로** 실행 가능
- [ ] 각 시나리오에 **"무엇이 막았는가 — 어느 검증 함수인가"** 가 기록됨 (못 막은 것은 못 막았다고)
- [ ] 시빌/스팸 방어를 추가한 뒤 같은 공격이 실패함
- [ ] **timewarp: 검사 OFF에서 난이도가 실제로 하락하고, ON에서 블록이 거부되는 것이 같은 스크립트로 대비됨**
- [ ] 컨펌 수별 reorg 성공률 표를 실측으로 작성
- [ ] **이중지불·포크 경쟁 시나리오가 `tests/sim/` 위에서 hypothesis 상태기계로 자동 탐색되고, 실패 시 시드 하나로 재현됨**

### Phase 7 — 배포 + 공개 테스트넷 앵커링 (4~7일)

**목표**: 인터넷에 올리고, 내 체인의 상태를 **공개 이더리움에 못 박는다.**

**만들 것**
- `Dockerfile` (멀티스테이지), `compose.yml` (3노드 + 탐색기)
- 클라우드 VM 배포, 도메인 + HTTPS, 헬스체크, 시드 노드
- `contracts/Anchor.sol` — **`(height, block_hash)`를 기록하는 최소 컨트랙트**
  머클 루트를 부가 정보로 함께 올려도 되지만 **변조 탐지의 근거는 블록 해시다.**
  머클 루트는 **그 블록의 tx 집합만** 커밋한다 — 공격자가 3번 블록의 글을 고치고 4~42번을 재채굴해도
  **42번 블록의 글 집합은 그대로**라 머클 루트도 그대로이고 길이도 42다. 온체인 값과 일치해 `ANCHOR OK`가 뜬다.
  블록 해시는 `prev_hash`를 타고 **과거 전체를 누적 커밋**하므로 그 우회가 막힌다.
  → [ADR-0003](decisions/ADR-0003-anchor-target.md)
- 주기적 앵커링 잡
- 탐색기 **앵커 패널** — 앵커된 블록 높이 → Etherscan 링크

**배우는 개념**: 노드 운영(부트스트랩·포트·방화벽), 설정 외부화, 가스와 수수료, 컨펌 대기,
컨트랙트 호출, **앵커링이 로컬 체인의 신뢰를 어떻게 보강하는가.**

**배포에서 미리 알고 가야 할 사실** (모르면 시간을 크게 버린다)
- 블록체인 노드는 `docker compose --scale` / `deploy.replicas`로 **늘리면 안 된다.**
  레플리카들이 같은 named volume을 공유해 **체인 데이터가 섞이고**, 컨테이너가 자기 인덱스를 모르며
  (hostname이 랜덤 ID), 포트 배정이 매번 달라진다. → `node1`/`node2`/`node3` **명시 서비스 + 노드별 named volume**.
- `depends_on`에 반드시 `condition: service_healthy`를 붙인다. 그냥 `depends_on`은 "컨테이너 시작"까지만
  기다려서 P2P 핸드셰이크가 깨진다. slim 이미지엔 curl이 없으므로 헬스체크는 `python -c` + `urllib.request`로 한다.
  제네시스 생성 같은 느린 초기화는 `start_period`로 retries 계산에서 빼 둔다.
- 컴포즈 서비스명은 라운드로빈 A 레코드 집합이라 `socket.getaddrinfo("node", 8000)` 한 줄이 피어 목록 부트스트랩이 된다.
  단, 호스트에 search domain(Tailscale 등)이 있으면 조회가 새어나가므로 이름 끝에 점을 찍는다.
- 장애 주입은 **toxiproxy**(TCP 프록시, NET_ADMIN 불필요, 파이썬 클라이언트로 pytest에서 분할을 프로그래밍 제어 가능)가
  자동화 테스트에 가장 잘 맞는다. 호스트 레벨 카오스가 필요하면 pumba.
  → 도구 비교와 링크는 [기술리서치 #장애주입](02-기술리서치.md#장애주입)
- 호스팅: 상시 실행 + 임의 inbound TCP + 영속 디스크를 **동시에** 주는 무료는 Oracle Always Free 하나뿐이다.
  Render / Cloud Run / Vercel / Netlify / PythonAnywhere는 sleep · HTTP 전용 · 읽기전용 FS 중 하나에 막혀
  **구조적으로 불가능**하다. 유료 대안은 Hetzner CX23(약 6유로/월), Fly.io 3머신(약 6달러/월).
  → 비교표는 [기술리서치 #호스팅](02-기술리서치.md#호스팅)
- Oracle Always Free에는 **유휴 회수 정책**이 있다 (7일간 CPU·네트워크·메모리가 모두 20% 미만이면 회수 대상).
  한가한 데모 노드가 정확히 여기 걸린다 → **주기적 더미 트랜잭션 크론**을 배포 체크리스트에 넣는다.

#### 🔴 서명 라이브러리에 붙는 보안 제약 (결정이지 권고가 아니다)

순수 파이썬 `ecdsa`는 **CVE-2024-23342(Minerva, CVSS 7.4 High)**의 영향을 받고, **모든 버전에 패치가 없다(won't fix).**
메인테이너 입장은 "순수 Python을 유지하는 한 constant-time 구현이 불가능하므로 범위 밖"이다. 즉 **기다려도 고쳐지지 않는다.**

| 구분 | 영향 |
|---|---|
| **서명 생성 · 키 생성 · ECDH** | **영향 있음** — 개인키를 다루는 연산 전부 |
| **서명 검증** | **영향 없음** — 개인키를 안 쓰므로 안전하다 |

그래서 이 프로젝트의 규칙은 다음과 같다.

- **개인키를 다루는 경로(키 생성 · 서명)는 Phase 4 이전에 `coincurve`로 교체한다.** Phase 3의 마지막 과제가 이 교체다.
- **`ecdsa`는 서명 *검증* 오라클로만 남긴다.** 내 구현이 맞는지 대조하는 용도로는 계속 유용하다.
  단 **결정성은 기본 동작이 아니다** — `SigningKey.sign()`은 **랜덤 nonce**를 쓴다.
  같은 입력에 같은 서명을 얻으려면 **`sign_deterministic()`**(RFC 6979)을 호출해야 한다.
  (백엔드 대조 테스트에서 `ecdsa`로 서명을 생성하는 것은 **테스트 전용 키에 한해 허용**된다. 금지 대상은 프로덕션 경로다.)
- 교체는 **백엔드 추상화 인터페이스를 먼저 만들고** 그 뒤에 갈아끼운다. 그래야 **두 백엔드의 출력이 임의 입력에서 항상 일치하는지**를 property 테스트로 검증할 수 있다.
  **단, 날것 그대로는 일치하지 않는다.** `coincurve`는 **DER + low-S 정규화** 출력이고 `ecdsa`의 `sign_deterministic()` 기본값은 **raw `r‖s` + S 미정규화**다.
  `r`이 같아도 **약 절반의 입력에서 `s`가 `n-s`로 갈린다.** 비교 전에 **인코딩(DER)과 low-S를 맞춰라** — `ecdsa` 쪽은 `sigencode=sigencode_der_canonize`.
- 로컬 학습용이라도 **README에 "프로덕션용 아님"을 명시한다.** 그것 자체가 학습 산출물이다.

→ 경고 원문·CVSS·영향 범위·성능 수치는 [기술리서치 #51-암호--서명](02-기술리서치.md#51-암호--서명)

### 직접 구현 vs 라이브러리 경계

이 경계를 흐리면 학습 프로젝트가 아니라 조립 프로젝트가 된다.

| 반드시 직접 구현 | 라이브러리로 해결 | 이유 |
|---|---|---|
| 블록 / tx 자료구조, 정규화 직렬화 | SHA-256 원시 함수 | 해시 **입력을 어떻게 만드느냐**가 핵심이지 해시 함수 자체가 아님 |

| 체인 검증 규칙 전체 | HTTP / WS 전송 계층 | **검증 규칙이 곧 블록체인이다** |
| PoW 채굴 · 난이도 재조정 | JSON / SQLite I/O | 난이도는 숫자로 아는 게 아니라 기다려 봐야 앎 |
| 포크 선택 · reorg | 웹 프레임워크 라우팅 | 합의의 본체 |
| 멤풀 · nonce 관리 | web3.py | 외부 체인은 소비자 입장이면 충분 |
| base58check 주소 | Docker 런타임 | 짧고 교육적 |

### Phase 1에 고정할 핵심 계약

아래 5가지는 **Phase 1에서 정하면 끝까지 안 바꾼다.** 나중에 바꾸면 기존 체인이 전부 무효가 되거나
뒤 Phase 전체를 다시 쓰게 된다. 시그니처와 불변식만 고정하고, 구현은 사용자가 한다.

1. **`canonical_bytes(obj) -> bytes`**
   해시 입력 정규화 — 키 정렬, UTF-8, 구분자 고정. **모든 해시는 예외 없이 이 함수만 통과한다.**
   → 결정 근거와 결과는 [ADR-0001](decisions/ADR-0001-canonical-serialization.md)

2. **`Block(index, prev_hash, timestamp, merkle_root, nonce, difficulty, txs) -> .hash: str`**
   필드 집합을 Phase 1에 고정한다. `difficulty`와 `nonce`는 Phase 4까지 쓰이지 않지만
   **지금 자리를 비워 두지 않으면 Phase 4에서 모든 블록 해시가 바뀐다** (= 기존 체인 전부 무효).
   - **`difficulty`의 의미도 지금 고정한다 — compact target(nBits)**이다. "선행 0비트 개수"가 아니다.
     비트 수로 저장하면 Phase 4의 ASERT가 낸 연속 target을 표현할 수 없고 Phase 5의 chainwork가 계단식이 된다
     ([Phase 4 상세](#phase-4--작업증명pow과-채굴-35일)).
   - **`hash`의 입력은 최종적으로 헤더 6개 필드**(`index`, `prev_hash`, `timestamp`, `merkle_root`, `nonce`, `difficulty`)**다.**
     `txs`는 `merkle_root`를 통해 간접 커밋된다. Lab 1.3에서는 머클이 아직 없어 `txs`를 직접 넣지만,
     **Lab 1.4에서 `merkle_root`로 교체하는 것이 의도된 순서**다 (Phase 1 안에서 체인을 버리고 다시 만든다).

3. **`Chain.validate() -> ValidationResult{ok, first_bad_index, reason}`**
   **bool이 아니라 파손 지점을 반환한다.** Phase 2에서 탐색기에 "3번부터 빨간 줄"을 그리려면
   어디서부터 깨졌는지를 알아야 하기 때문이다. bool로 만들면 Phase 2에서 전부 고쳐야 한다.
   - **블록 자기검사는 `txs`로부터 `merkle_root`를 재계산해 대조하는 것을 포함한다.** 헤더 해시 전환(Lab 1.4)
     이후 `merkle_root`가 글 집합을 커밋하는 **유일한 고리**이므로, 검증이 이 고리를 확인하지 않으면
     본문을 고쳐도 헤더 해시가 그대로여서 변조가 탐지되지 않는다.

4. **`Storage` 프로토콜**: `append_block`, `get_block(hash|index)`, `tip()`, `iter_blocks(from, to)`, `height()`
   Phase 1에서는 JSON 구현 하나뿐이지만 **인터페이스는 Phase 1에 선언한다.**
   Phase 2의 SQLite 전환이 코어 테스트를 한 줄도 건드리지 않게 하기 위해서다.

5. **`Post`(= Phase 3의 `Transaction`)의 필드 집합: `(author, body, ts, nonce, sig)`**
   **`Block`에 `nonce`/`difficulty`를 미리 넣는 것과 정확히 같은 이유다.** 글은 블록 해시의 입력에 들어간다
   (Lab 1.3에서는 직접, Lab 1.4 이후에는 `merkle_root`를 통해). Phase 3에서 `nonce`와 `sig`를 **추가하는 순간**
   그때까지 쌓인 모든 블록의 머클 루트와 해시가 바뀌어 `validate()`가 `first_bad_index=1`을 반환한다.
   - **Phase 3까지 `sig`는 `None`, `nonce`는 `0`으로 자리만 잡아 둔다.** 값을 쓰지 않을 뿐 필드는 지금 있다.
   - **키 이름도 지금 고정한다.** `canonical_bytes`는 딕셔너리 키를 그대로 직렬화하므로
     `author` → `from`처럼 이름만 바꿔도 해시가 전부 바뀐다. Phase 3 항목의 `Transaction{from, payload, nonce, sig}`는
     **개념 표기**이고, 실제 필드명은 `author`/`body`/`ts`/`nonce`/`sig`로 간다.

**API 접두사도 Phase 2에서 고정한다**: 조회 `/api/*`, 노드 간 `/p2p/*`, 실습용 파괴 `/admin/*`(환경변수로 꺼짐).

#### `Transport`는 Phase 1에 선언하지 않는다 (의도적 판단)

`Storage`와 대비되어 헷갈리기 쉬우므로 근거를 남긴다.

- **`Storage`를 Phase 1에 선언하는 이유**: Phase 2에서 **구현체가 실제로 교체되기 때문**이다.
  인터페이스가 먼저 없으면 코어가 JSON 구현에 직접 붙어 버리고, 교체할 때 코어 테스트를 다 고쳐야 한다. **P1에 소비자가 이미 있다.**
- **`Transport`를 Phase 5로 미루는 이유**: **Phase 1~4에는 소비자가 없다.**
  메시지 종류(`version` / `inv` / `getdata` / `block` …)가 정해지지 않은 상태에서 시그니처만 먼저 박으면
  **Phase 5에서 어차피 다시 쓴다.** 구현도 호출자도 없는 인터페이스는 계약이 아니라 잡음이다.

대신 **원칙 한 줄만 Phase 1부터 지킨다**: **시간과 난수는 주입한다.**
`time.time()`과 전역 `random`을 코어에서 직접 부르지 않는 습관을 Phase 1에 들여 놓으면,
Phase 5에서 `Transport`를 넣을 때 **바꿀 것이 전송 계층 하나뿐**이 된다.
반대로 Phase 1~4 내내 `time.time()`을 흩뿌려 놓으면 Phase 5에서 그걸 다 걷어내는 작업이 먼저 온다.

## 7. 순서 제약

아래는 **지켜야 하는 선후 관계**다. Phase 번호와 별개로, 이것을 어기면 되돌아와 다시 써야 한다.

1. **Phase 0 → 전부.** 테스트 러너와 CI가 있어야 이후 모든 DoD가 검증 가능하다.
2. **`canonical_bytes` 규칙 확정 → 블록 해시 구현.** Phase 1 첫 랩에서 정하고 ADR로 남긴다.
3. **`Storage` 프로토콜 선언(P1) → SQLite 구현(P2).**
4. **서명·tx 검증(P3) → P2P 블록 수용(P5).** (3절 (a)의 이유)
5. **PoW·난이도(P4) → 포크 선택(P5).** 누적 난이도로 포크를 고르려면 난이도가 먼저 있어야 한다.
6. **다중 노드(P5) → 공격 실습 대부분(P6).**
7. **머클 루트(P1) → 블록 해시 → 앵커링(P7).** 앵커에 올리는 값은 **블록 해시**다 (→ [ADR-0003](decisions/ADR-0003-anchor-target.md)).
   다만 **블록 해시의 입력에 `merkle_root`가 들어가므로 머클(P1)이 먼저여야 한다는 선후 관계 자체는 그대로다.**
8. **문서 순서**: 개발계획서 → 기술리서치 → 학습계획서. 리서치가 스택 결정을 뒤집으면 ADR을 쓰고 이 문서를 고친다.
9. **git init + origin 연결 → 첫 커밋은 사용자가 직접.** 에이전트는 커밋·푸시하지 않는다.

## 8. 위험과 대응

| 위험 | 왜 위험한가 | 대응 |
|---|---|---|
| **문서 3종 경계 붕괴** | 같은 내용이 세 곳에 갈라져 서로 어긋나기 시작하면 문서를 아무도 안 믿게 됨 | 중복 방지 규칙을 각 문서 상단에 박아 둠. 중복이 생기면 링크로 접음 |
| **Phase 5가 절벽** | 분량이 다른 Phase의 2배 + asyncio 동시성 + 부분 실패 + 타이밍 버그가 한꺼번에 | **5a / 5b / 5c로 분할**하고 각각 DoD를 따로 만족. 한 번에 다 하려 들지 않음 |
| **P2P 테스트가 flaky해짐** | 실제 소켓·실제 시계 위에서 테스트하면 가끔 실패하고 재현이 안 된다. 그런 테스트는 결국 아무도 안 믿게 되고, **Phase 6의 공격 실험 결과도 믿을 수 없게 된다** | 비결정성을 한 지점으로 모은다 — **`Transport` 주입 + `SimTransport` + 주입 시계 + 시드 RNG**(Phase 5a 첫 작업). 실패는 **시드 하나로 재현**. `asyncio.sleep`으로 동기화 금지, `anyio.fail_after()`로 상한 |
| **탐색기 점진 확장 비용** | Phase마다 UI를 고치다 보면 UI 코드가 코어에 얽혀 코어 수정이 어려워짐 | 템플릿을 **패널 단위 partial**로 나누고, 데이터는 반드시 `/api/*` JSON을 경유 (UI-코어 직접 결합 차단) |
| **`/admin/tamper`와 CLI `tamper`가 공개 노드에 노출** | 실습용 파괴 엔드포인트가 인터넷에 열려 있으면 누구나 내 체인을 깨뜨림. **CLI 쪽이 더 위험하다** — 배포 이미지에 그대로 들어가는데 경고 문구만 출력하고 실행은 되기 때문 | 둘 다 기본 비활성 + **같은 환경변수 게이트**로만 활성 + **배포 전 체크리스트를 Phase 7 DoD에 두 항목으로 명시** |
| **공개 노드 남용** | 스팸·불법 게시물이 들어오면 **삭제할 수단이 없다** (설계상 불변) | 레이트 리밋 + 글 길이 제한. **"불변 게시판에 개인정보를 쓰면 삭제 불가"** 경고를 README와 글쓰기 UI 양쪽에 표기 |
| **Sepolia 의존** | faucet 고갈, 정책 변경, RPC 한도 초과로 앵커링이 막힐 수 있음 | 앵커링을 **선택적 기능으로 분리**. 실패해도 로컬 체인은 정상 동작해야 함 (DoD에 포함) |
| **`ecdsa`의 미패치 취약점(CVE-2024-23342)** | 순수 파이썬 `ecdsa`는 **모든 버전에 패치가 없다(won't fix).** 서명 생성·키 생성·ECDH가 영향 범위이고, 부채널로 **개인키가 복원될 수 있다**. 학습용이라도 "쓰면 안 되는 걸 쓴 채로 배우는" 상태가 된다 | **개인키를 다루는 경로는 Phase 4 이전에 `coincurve`로 교체**하고 `ecdsa`는 **검증 오라클로만** 남긴다 (검증은 영향 없음). 교체를 Phase 3 DoD에 항목화. README에 프로덕션용 아님 명시 |
| **개인키가 저장소에 커밋됨** | 한번 푸시되면 히스토리에서 지워도 남음. 공개 저장소라면 즉시 탈취 | `.gitignore`에 `*.key`, `keystore/`, `.env`를 **Phase 0에 선등록** (사후가 아니라 사전) |
| **"직접 구현" 원칙과 에이전트 충돌** | implementer 에이전트가 사용자가 풀어야 할 랩 과제를 대신 풀어버림 | CLAUDE.md에 **"학습 랩 대상 모듈은 사용자가 구현, 에이전트는 테스트·리뷰·스캐폴딩만"** 규칙을 명시 |
| **기간 미정 + 범위 큼 → 중도 이탈** | 끝이 안 보이면 멈춘다 | 각 Phase 끝에 **"보여줄 수 있는 한 장면"**(스크린샷/GIF)을 남기는 것을 DoD에 포함. 성취가 눈에 보여야 다음이 있음 |
| **Docker 멀티노드 함정** | `--scale`로 노드를 늘리면 볼륨 공유로 체인이 섞이고, 재연결 시 DNS alias가 안 돌아와 reorg 실험이 통째로 실패 | 명시 서비스 + 노드별 볼륨, `condition: service_healthy`, `network connect --alias`. Phase 7 항목에 사전 명시 |
| **Oracle 무료 인스턴스 회수** | 한가한 데모 노드는 유휴 회수 정책(7일간 사용률 20% 미만)에 정확히 걸림 | 주기적 더미 트랜잭션 크론을 배포 체크리스트에 포함 |
