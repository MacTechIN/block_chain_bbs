# ADR-0002 — 글 본문 전체를 블록에 저장한다

| 항목 | 값 |
|---|---|
| 상태 | 채택 (Accepted) |
| 결정 시점 | Phase 1 |
| 영향 범위 | `core/block.py`, `core/transaction.py`, 저장소 전체, Phase 8 IPFS 트랙 |
| 관련 | [개발계획서 Phase 1](../01-개발계획서.md#phase-1--단일-노드-체인--게시판-코어-24일), [Phase 8+](../01-개발계획서.md#phase-8--확장-트랙-메뉴식-순서-자유) |

---

## 맥락

블록체인 BBS에서 "글 본문"을 어디에 둘지는 두 갈래다.

```
(A) 온체인 본문           (B) 해시만 온체인
┌──────────────┐         ┌──────────────┐      ┌──────────┐
│ Block        │         │ Block        │      │ 별도 DB   │
│  txs: [      │         │  txs: [      │      │          │
│   {author,   │         │   {author,   │      │ post_id  │
│    body:     │         │    body_hash}│─────▶│ body     │
│    "전문..."} │         │  ]           │      │          │
│  ]           │         └──────────────┘      └──────────┘
└──────────────┘
```

(B)는 실무에서 흔한 패턴이다. 블록에는 해시만 넣고 본문은 IPFS나 일반 DB에 둔다.
블록 크기가 작아지고, 본문 저장 비용이 싸다. 실제 NFT 메타데이터, 문서 공증 서비스가 이렇게 한다.

그런데 이 프로젝트의 목적은 **서비스를 잘 만드는 것이 아니라 블록체인을 체감하는 것**이다.
그 관점에서 두 방식은 완전히 다르다.

## 결정

**Phase 1부터 Phase 7까지, 글 본문 전체를 블록 안에 저장한다.**
대신 **글 길이에 상한을 둔다** (예: 본문 2KB. 정확한 값은 Phase 2 글쓰기 폼과 Phase 6 스팸 방어에서 확정).

오프체인(IPFS) 전환은 **Phase 8 확장 트랙의 실습 과제**로 미룬다. 없애는 것이 아니라 순서를 미루는 것이다.

## 대안과 기각 사유

### 대안 B — 해시만 온체인 + 본문은 별도 DB

**기각한 핵심 이유: 처음부터 간접층이 생기면 불변성이 체감되지 않는다.**

구체적으로 무엇이 약해지는가:

| 랩 / 장면 | (A) 온체인 본문 | (B) 해시만 온체인 |
|---|---|---|
| [Lab 1.2](../labs/phase-1-chain.md#lab-12--취약한-게시판과-변조) — 파일 열어 글 교체 | 블록 안의 글자를 직접 고친다. **"이게 블록이구나"** | 블록에는 해시뿐이라 고칠 게 없다. DB의 본문을 고친다 → **"그냥 평범한 DB네"** |
| [Lab 1.3](../labs/phase-1-chain.md#lab-13--블록과-체인) — 변조 탐지 | 블록 해시가 안 맞는다. 끝 | 블록은 멀쩡하다. **별도로 본문 해시를 대조하는 코드를 따로 짜야** 탐지된다 |
| Phase 2 탐색기 블록 상세 | 블록을 열면 **글이 거기 있다** | 블록을 열면 해시뿐. 글을 보려면 다른 데서 조인해 온다 |
| Phase 5 노드 간 전파 | 블록이 전파되면 글도 전파된다. **글이 복제되는 걸 본다** | 블록만 전파된다. 본문은 각자 알아서 받아 온다 → 배우려던 게 흐려진다 |
| 삭제 불가 체감 | 지울 방법이 없다. 블록 안에 있다 | **DB에서 지우면 본문이 없어진다.** "불변"이 말뿐이 된다 |

마지막 행이 결정적이다. (B)에서 본문을 DB에서 지우면 블록의 해시는 그대로 남지만 **글은 사라진다.**
읽을 수 없는 해시만 남은 체인을 보면서 "이건 삭제할 수 없습니다"라고 말하는 것은 공허하다.
이 프로젝트가 게시판을 소재로 고른 이유 자체가 **"지울 수 없다"를 눈으로 보여주기 위해서**인데,
(B)는 그 장면을 없앤다.

### 대안 C — 처음부터 IPFS

**기각 사유**: Phase 1에서 IPFS 노드 운영, CID, pinning, 게이트웨이를 동시에 배우게 된다.
블록체인을 배우러 왔는데 분산 파일 시스템 튜토리얼을 하게 된다.
[개발계획서 5절 스택 표](../01-개발계획서.md#5-기술-스택)가 도구를 고를 때 쓰는 기준인 **"학습 외 마찰이 최소"**에 정면으로 어긋난다.
[원칙 4](../01-개발계획서.md#관통하는-5가지-원칙)("손으로 짜는 것과 가져다 쓰는 것을 미리 갈라놓는다")로 봐도 같은 결론이다 —
IPFS는 **배울 대상이 아니라 가져다 쓸 것**인데, Phase 1에 넣으면 그 운영까지 직접 떠안게 되어 경계가 무너진다.

### 대안 D — 본문을 압축해서 온체인

**기각 사유**: 압축 알고리즘·버전이 해시 입력에 영향을 준다 → [ADR-0001](ADR-0001-canonical-serialization.md)이
고정한 규칙에 변수가 하나 더 붙는다. 얻는 것(용량)에 비해 잃는 것(단순성)이 크다.
Phase 8의 "블록 압축·프루닝" 트랙에서 다룬다.

## 결과

### 좋은 것
- 블록 하나가 **자기완결적**이다. 블록을 받으면 글을 읽을 수 있다. 다른 저장소가 필요 없다.
- Lab 1.2 → Lab 1.3의 Break-First 대비가 선명하다. 같은 파일, 같은 공격, 다른 결과.
- Phase 5에서 블록 전파 = 글 전파다. 배우려는 것이 그대로 보인다.
- 검증이 단순하다. 블록 해시만 맞으면 본문도 맞다. 별도 대조 로직이 없다.

### ⚠️ 나쁜 것 — 이 결정이 만드는 문제들

**1. 글을 삭제할 수 없다. 진짜로.**
- 한번 블록에 담긴 글은 수정도 삭제도 불가능하다. 정정 글을 뒤에 붙일 수 있을 뿐이다.
- Phase 5 이후에는 다른 노드에 복제되므로, 내 노드의 파일을 지워도 **남의 노드에는 남는다.**
- Phase 7에서 공개 배포하면 **인터넷 누구나** 읽을 수 있다.
- 따라서 **README와 글쓰기 UI 양쪽에 삭제 불가 경고를 표시한다.**
  이건 선택이 아니라 이 ADR의 일부다. ([개발계획서 위험 섹션](../01-개발계획서.md#8-위험과-대응))
- 개인정보·실명·연락처·비밀번호를 쓰면 되돌릴 방법이 없다. 테스트 글만 쓴다.

**2. 블록과 체인이 커진다.**
- 본문 2KB × 글 1만 개 = 약 20MB. 학습 규모에서는 문제없다.
- 그러나 **모든 노드가 모든 글을 영구 보관**한다. 노드 수가 늘어도 용량은 안 줄고, 오히려 복제본이 는다.
- Phase 4 채굴에서 블록이 크면 해시 계산이 느려진다.
  (완화: 머클 루트가 본문을 요약하므로 **블록 헤더만 해시하면 된다.**
  [Lab 1.4](../labs/phase-1-chain.md#lab-14--머클-루트)에서 **`Block.hash`의 입력에서 `txs`를 빼는 것이 명시적 과제**다 —
  준비만 하는 게 아니라 거기서 실제로 헤더 해시가 된다. Phase 4로 미루면 그때 모든 블록 해시가 바뀐다 → [ADR-0001](ADR-0001-canonical-serialization.md))
- Phase 5 전파에서 블록이 크면 대역폭을 먹고 전파가 느려진다 → 포크 확률이 올라간다.
  이건 **실제 블록체인의 블록 크기 논쟁 그 자체**이고, Phase 5에서 직접 겪을 소재다.

**3. 글 길이 제한이 반드시 필요하다.**
- 제한이 없으면 공격자가 10MB짜리 글 하나로 모든 노드의 디스크를 먹인다 (Phase 6 스팸 시나리오).
- 제한값은 정책이다. 정하고 기록하고, Phase 6에서 그 값이 충분한지 공격으로 검증한다.
- 제한은 **검증 규칙의 일부**다. 즉 제한을 초과한 글이 든 블록은 **거부**되어야 한다.
  API에서만 막으면 우회된다.
- **제한값을 나중에 바꾸면?** 늘리는 것은 안전하다(기존 블록은 여전히 유효). 줄이면 기존 블록이 무효가 된다.
  Phase 5 이후라면 하드포크다. → 처음에 넉넉히 잡는 편이 낫다.

**4. Phase 8에서 전환 실습을 한다.**
- "본문 IPFS 오프체인 저장 + 온체인 해시" 트랙이 바로 대안 B로 가는 실습이다.
- 이때 배우는 것: 왜 실무가 그렇게 하는가, 그 대신 **무엇을 잃는가**(본문 가용성이 IPFS pinning에 의존한다).
- **용량 문제를 실제로 겪은 다음에 푸는 것**이 순서다. 겪기 전에 풀면 왜 푸는지 모른다.
- 전환 시점에 기존 블록을 어떻게 할지도 그때 결정한다 (기존은 온체인 본문 유지, 신규만 해시 — 혼합 구조).

### 검증 방법
- Phase 2: 글쓰기 폼에 길이 제한과 **삭제 불가 경고**가 표시된다.
- Phase 6: 초과 길이 글이 든 블록이 거부되는 것을 공격 스크립트로 확인한다.
- Phase 7 DoD: "글 길이 제한과 레이트 리밋이 적용됨" 항목.
