# ADR-0001 — 해시 입력 정규 직렬화 규칙을 Phase 1에 고정한다

| 항목 | 값 |
|---|---|
| 상태 | 채택 (Accepted) |
| 결정 시점 | Phase 1 / Lab 1.3 |
| 영향 범위 | `core/serialize.py`, `core/hashing.py`, 그리고 **해시를 쓰는 모든 것** |
| 관련 | [개발계획서 #phase-1에-고정할-핵심-계약](../01-개발계획서.md#phase-1에-고정할-핵심-계약), [Lab 1.1](../labs/phase-1-chain.md#lab-11--해시-감각-잡기), [Lab 1.3](../labs/phase-1-chain.md#lab-13--블록과-체인) |

## 맥락

블록 해시는 "블록의 내용"을 입력으로 받는다. 그런데 **"내용"은 바이트열이 아니라 객체**다.
객체를 바이트열로 바꾸는 방법은 무수히 많고, 방법이 다르면 해시가 다르다.

Lab 1.1에서 직접 확인한 사실:

| 두 입력 | 논리적으로 | 해시는 |
|---|---|---|
| `{"a":1,"b":2}` / `{"b":2,"a":1}` | 같다 | **다르다** |
| `dumps(x)` / `dumps(x, indent=2)` | 같다 | **다르다** |
| UTF-8 인코딩 / UTF-16 인코딩 | 같다 | **다르다** |
| `{"n": 1}` / `{"n": 1.0}` | (보통) 같다고 여김 | **다르다** |

정규화 규칙 없이 해시를 계산하면 다음이 전부 실패한다.

- **재현성**: 같은 글 10개를 넣었는데 실행할 때마다 다른 체인 해시가 나온다 ([Phase 1 DoD](../01-개발계획서.md#phase-1--단일-노드-체인--게시판-코어-24일)).
- **왕복(round-trip)**: 저장했다 읽으면 `tuple`이 `list`가 되어, 변조하지 않았는데 체인이 깨진 것으로 판정된다 ([Lab 1.5 §1](../labs/phase-1-chain.md#lab-15--영속화와-검증-cli)).
- **합의**: Phase 5에서 내 노드와 남의 노드가 같은 블록에 서로 다른 해시를 매긴다. **두 노드는 영원히 합의하지 못한다.**
- **앵커링**: Phase 7에서 온체인에 올린 블록 해시와 로컬에서 재계산한 해시가 달라, 정상 체인이 변조로 오탐된다
  (앵커 대상이 블록 해시인 이유는 → [ADR-0003](ADR-0003-anchor-target.md)).

이 문제는 뒤로 갈수록 발견이 어려워진다. Phase 1에서는 테스트가 바로 빨개지지만,
Phase 5에서는 "가끔 블록이 거부된다" 같은 모호한 증상으로 나타난다.

## 결정

**해시 입력을 만드는 경로를 `canonical_bytes(obj) -> bytes` 단 하나로 제한하고, 그 규칙을 Phase 1에 고정한다.**

고정하는 규칙:

| 항목 | 규칙 | 고정하지 않으면 |
|---|---|---|
| **키 순서** | 사전순 정렬 (`sort_keys=True`) | 딕셔너리 삽입 순서에 따라 해시가 달라짐 |
| **구분자** | `(",", ":")` — 공백 없음 | 포맷터·라이브러리 버전에 따라 공백이 끼어듦 |
| **들여쓰기** | 없음 | 보기 좋게 저장한 순간 해시가 바뀜 |
| **문자 인코딩** | UTF-8 고정 | 플랫폼 기본 인코딩에 의존하게 됨 |
| **비ASCII 처리** | 한 가지로 고정 (`ensure_ascii` 값을 정하고 기록) | 한글이 든 글의 해시가 환경에 따라 달라짐 |
| **시퀀스 타입** | JSON 배열 하나로 통일 (`tuple`/`list` 구분 없음) | 저장 왕복에서 타입이 바뀌어 해시가 깨짐 |
| **정수/실수** | 타임스탬프 등은 `int`로 고정 | `1`과 `1.0`이 다른 해시를 냄 |
| **미지원 타입** | `set`, `datetime`, `bytes` 등은 **예외를 던진다** | 조용히 문자열로 변환되어 나중에 규칙이 바뀜 |

부수 규칙:
- **`core/serialize.py` 밖에서 `json` 모듈을 해시 목적으로 직접 쓰지 않는다.**
  다른 모듈이 `json.dumps`를 부르는 순간 규칙이 새어 나간다.
- `hash_object(obj)`는 반드시 `canonical_bytes`를 거친다. `str.encode()`를 직접 호출하는 해시 경로를 만들지 않는다.
- **저장 포맷과 해시 입력은 별개다.** `chain.json`은 사람이 읽기 좋게 들여쓰기해도 되고 한글을 그대로 써도 된다.
  해시는 저장된 텍스트가 아니라 복원된 객체에 대해 `canonical_bytes`로 다시 계산한다.
- 머클 트리의 리프/내부 노드 도메인 구분 규칙([Lab 1.4](../labs/phase-1-chain.md#lab-14--머클-루트))도
  정한 뒤 이 문서에 덧붙인다. 그것 역시 해시 입력 규칙의 일부다.

## 대안과 기각 사유

| 대안 | 내용 | 기각 사유 |
|---|---|---|
| **A. 규칙 없이 `json.dumps` 기본값** | 그냥 쓴다 | Lab 1.1에서 확인한 대로 바로 깨진다. 논외 |
| **B. 고정 길이 바이너리 헤더** (비트코인 방식) | 필드를 고정 길이 리틀엔디언으로 직렬화 | 가장 견고하고 실제 체인의 방식이다. 하지만 **디버깅 중 눈으로 읽을 수 없다.** Phase 1~2의 학습 목표는 "해시 입력이 무엇인지 눈으로 보는 것"인데 그걸 정면으로 방해한다. 오프셋 계산 버그가 학습 시간을 잡아먹는다 |
| **C. RLP** (이더리움 방식) | 이더리움의 재귀 길이 접두 인코딩 | 라이브러리 의존이 생기고, 인코딩 자체를 공부하는 비용이 크다. [직접 구현 vs 라이브러리 경계](../01-개발계획서.md#직접-구현-vs-라이브러리-경계)상 학습 가치 대비 비용이 맞지 않는다 |
| **D. CBOR / msgpack** | 바이너리 직렬화 라이브러리 | 정규형(canonical form) 옵션을 제대로 쓰면 B의 장점을 얻지만, 라이브러리 버전이 바뀌면 규칙도 바뀔 수 있다. 우리가 통제하지 못하는 의존성이 해시 규칙을 좌우하는 것은 위험하다 |
| **E. 정규화된 JSON (채택)** | 위 표의 규칙을 적용한 `json.dumps` + UTF-8 | 표준 라이브러리만 쓰고, **`cat`으로 열어 눈으로 읽을 수 있고**, 규칙이 7줄로 설명된다. Phase 1~2의 학습 목표에 정확히 맞는다 |

**B를 완전히 버린 것은 아니다.** Phase 8 확장 트랙에서 "직렬화를 바이너리로 바꾸고 해시 성능을 비교"하는 실습으로 다룰 수 있다.
단, 그때는 **새 체인을 시작해야 한다** (아래 결과 참고).

## 결과

### 좋은 것
- 같은 글 입력 → 항상 같은 체인 해시. [Phase 1 DoD](../01-개발계획서.md#phase-1--단일-노드-체인--게시판-코어-24일)의 "재현 가능"이 성립한다.
- 저장소를 JSON에서 SQLite로 바꿔도(Phase 2) 해시가 바뀌지 않는다. **저장 포맷과 해시 입력이 분리돼 있기 때문**이다.
- 노드 간 전송 포맷이 달라져도(Phase 5, HTTP JSON → WebSocket) 해시는 같다.
- 해시 입력을 눈으로 확인할 수 있어, 디버깅할 때 "무엇을 해시했는지"를 출력해 바로 비교할 수 있다.

### 나쁜 것 / 감수하는 것
- **JSON은 바이너리보다 느리고 크다.** Phase 4 채굴 루프에서 이 비용이 드러난다.
  (완화: 채굴은 블록 헤더 필드만 해시하면 되고, 머클 루트가 본문을 이미 요약한다.
  **이 완화는 저절로 되는 게 아니라 [Lab 1.4](../labs/phase-1-chain.md#lab-14--머클-루트)의 명시적 과제다** —
  거기서 `Block.hash`의 입력에서 `txs`를 빼고 `merkle_root`만 남긴다. 그 교체를 Phase 4로 미루면 아래 ⚠️ 절의 상황이 그대로 벌어진다.
  **그리고 헤더 해시로 바꾸는 순간 검증이 `txs`로부터 머클 루트를 재계산해 대조해야 한다** — `merkle_root`가 글 집합을 커밋하는
  유일한 고리가 되므로, 재계산하지 않으면 본문을 고쳐도 헤더 해시가 그대로여서 변조가 탐지되지 않는다.)
- `bytes`를 직접 담을 수 없어 해시는 hex 문자열로 다룬다. 저장 공간이 2배다. 학습 프로젝트에서는 수용 가능하다.

### ⚠️ 가장 중요한 결과 — 이 규칙은 되돌릴 수 없다

**이 규칙을 나중에 바꾸면, 그 시점까지 쌓인 모든 블록의 해시가 바뀐다. 즉 기존 체인이 전부 무효가 된다.**

구체적으로 무슨 일이 일어나는가:

1. 블록 #0부터 #N까지 전부 해시가 달라진다.
2. 각 블록의 `prev_hash`는 **옛 규칙으로 계산된 값**을 담고 있으므로, 새 규칙으로 재계산한 해시와 이어지지 않는다.
3. `validate()`는 `first_bad_index=1`을 반환한다. 아무도 변조하지 않았는데 체인 전체가 파손 판정을 받는다.
4. Phase 5 이후라면 더 나쁘다. 규칙을 바꾼 노드는 다른 노드가 보낸 블록을 전부 거부하고,
   자기 블록도 전부 거부당한다. **네트워크에서 조용히 떨어져 나간다.** 이것이 하드포크다.
5. Phase 7 이후라면 최악이다. 온체인에 앵커된 **블록 해시**와 로컬 재계산 값이 달라져,
   **정상 체인이 "변조됨"으로 오탐된다.** 앵커링의 신뢰가 무너진다. (→ [ADR-0003](ADR-0003-anchor-target.md))

따라서:

- **규칙 변경은 "설정 바꾸기"가 아니라 "새 체인 시작하기"다.** 기존 데이터를 버리고 제네시스부터 다시 한다.
- Phase 1에서는 이 비용이 싸다 (블록 10개를 버리면 된다). **그래서 지금 고정한다.**
- 같은 이유로 `Block`의 **필드 집합도 지금 고정한다.** `nonce`와 `difficulty`는 Phase 4까지 항상 0이고
  아무 데도 안 쓰이지만, 그때 가서 추가하면 그 시점까지의 모든 블록 해시가 바뀐다.
  **쓰지 않는 필드를 미리 넣는 것은 낭비가 아니라 보험이다.**
- **`Post`(= Phase 3의 `Transaction`)의 필드 집합도 마찬가지다.** 글은 `merkle_root`를 통해 블록 해시에 들어간다.
  Phase 3에서 `nonce`/`sig`를 **추가**하면 그때까지의 모든 머클 루트와 블록 해시가 바뀐다 — `Block.nonce`와 완전히 같은 사고다.
  **Phase 3까지 `sig`는 `None`, `nonce`는 `0`으로 자리만 잡아 둔다.**
  **키 이름도 고정 대상이다.** 이 문서의 "키 순서" 규칙이 말해 주듯 `canonical_bytes`는 딕셔너리 **키 문자열을 그대로** 직렬화한다.
  `author`를 `from`으로 바꾸기만 해도 해시가 전부 바뀐다. → [개발계획서 고정 계약 5번](../01-개발계획서.md#phase-1에-고정할-핵심-계약)
- 규칙을 정말 바꿔야 한다면 이 ADR을 `Superseded`로 표시하고 새 ADR을 쓴다.
  그 ADR에는 **기존 체인을 어떻게 할 것인지**가 반드시 포함돼야 한다.
