# 테스트 실행법 — 한 단계씩

> **언제 읽나**: Phase 0 시트를 시작하기 전에 한 번. 그 뒤로는 막힐 때마다 돌아온다.
> **어느 Phase에서나 쓴다.** 그래서 `phase-0/`이 아니라 워크북 맨 위에 있다.
> 테스트가 **왜** 그렇게 동작하는지는 → [튜토리얼 Phase 0](../docs/tutorial/phase-0.md)

## 명령 한눈에 보기

외울 필요 없다. 필요할 때 여기서 베껴 써라.

| 하고 싶은 것 | 명령 |
|---|---|
| 그냥 다 돌린다 | `uv run pytest` |
| 파일 하나만 | `uv run pytest tests/unit/test_merkle.py` |
| 이름에 특정 단어가 든 것만 | `uv run pytest -k merkle` |
| 첫 실패에서 바로 멈춘다 | `uv run pytest -x` |
| 아까 실패한 것만 다시 | `uv run pytest --lf` |
| 어떤 테스트가 도는지 이름을 본다 | `uv run pytest -v` |
| 테스트 안의 `print`를 본다 | `uv run pytest -s` |
| 돌리지 말고 목록만 본다 | `uv run pytest --collect-only -q` |
| 스타일 검사 | `uv run ruff check` |
| 타입 검사 | `uv run mypy src/` |

플래그는 겹쳐 쓸 수 있다. `uv run pytest tests/unit/test_merkle.py -x -v`처럼.

## 전체 실행

```
uv run pytest
```

```
============================= test session starts ==============================
platform linux -- Python 3.12.13, pytest-9.1.1, pluggy-1.6.0
rootdir: /home/<너>/…/block_chain_bbs
configfile: pyproject.toml
testpaths: tests/test_smoke.py
plugins: hypothesis-6.168.0
collected 2 items

tests/test_smoke.py ..                                                   [100%]

============================== 2 passed in 0.01s ===============================
```

**어디를 읽나.** 위에서부터 셋이다.

1. **`rootdir` / `configfile`** — pytest가 어느 설정을 읽었는지. 엉뚱한 폴더에서 돌렸으면 여기서 티가 난다
2. **`collected 2 items`** — 몇 개를 찾았는지. **`collected 0 items`면 하나도 안 돈 것이다**
3. **맨 아랫줄** — 최종 결과. 초록이면 통과

가운데의 `..` 는 테스트 하나당 한 글자다.

| 글자 | 뜻 |
|---|---|
| `.` | 통과 |
| `F` | 실패 (테스트 본문에서 `assert`가 틀림) |
| `E` | 오류 (테스트를 돌리기도 전에 준비 단계에서 터짐) |
| `s` | 건너뜀 (skip) |
| `x` | 실패할 거라고 미리 표시된 것 (xfail) |

> **`collected 0 items`를 초록으로 착각하지 마라.**
> 빨간 줄이 없으니 통과처럼 보이지만, 실은 아무것도 검사하지 않은 것이다.

## 파일 하나만 실행

지금 만드는 것과 상관없는 테스트까지 돌 필요는 없다. 파일 경로를 뒤에 붙인다.

```
uv run pytest tests/unit/test_merkle.py
```

**경로를 주면 `pyproject.toml`의 기본 범위 설정은 무시된다.**
그래서 지금 이 명령은 Phase 1 테스트 18개를 실제로 돌린다
(→ [왜 2개만 도나](#이-저장소에만-있는-규칙--왜-2개만-도나)).

폴더를 줘도 된다.

```
uv run pytest tests/unit
```

## 함수 하나만 골라 실행

`-k` 뒤에 **테스트 이름의 일부**를 적는다. 그 글자가 들어간 테스트만 돈다.

```
uv run pytest -k version -v
```

```
collecting ... collected 2 items / 1 deselected / 1 selected

tests/test_smoke.py::test_version_is_declared PASSED                     [100%]

======================= 1 passed, 1 deselected in 0.01s ========================
```

**`1 deselected`가 "골라내고 뺀 개수"다.** 이 줄이 `-k`가 먹혔다는 증거다.
`0 selected`가 나오면 이름을 잘못 적은 것이다.

이름을 통째로 지정할 수도 있다. 파일 경로 뒤에 `::`을 붙인다.

```
uv run pytest tests/test_smoke.py::test_version_is_declared
```

`-k`는 `and`, `or`, `not`도 받는다.

```
uv run pytest -k "merkle and not proof"
```

> **테스트 이름은 어디서 보나.** `uv run pytest --collect-only -q <경로>`가 목록만 뽑아 준다.

## 첫 실패에서 멈추기

실패가 20개 쏟아지면 화면을 읽을 수가 없다. **`-x`는 첫 실패에서 즉시 멈춘다.**

```
uv run pytest tests/unit/test_merkle.py -x
```

```
tests/unit/test_merkle.py:24: MissingImplementation
=========================== short test summary info ============================
FAILED tests/unit/test_merkle.py::test_merkle_root_is_deterministic - conftes...
!!!!!!!!!!!!!!!!!!!!!!!!!! stopping after 1 failures !!!!!!!!!!!!!!!!!!!!!!!!!!!
============================== 1 failed in 0.06s ===============================
```

마지막 줄의 `stopping after 1 failures`가 "여기서 멈췄다"는 표시다.

**언제 쓰나.** 구현을 막 시작해서 다 실패하는 상태일 때다.
스무 개를 한꺼번에 고치려 하지 말고, **맨 앞 하나만 보고 고친다.**
`-x`로 고정해 두면 화면이 항상 그 하나만 보여 준다.

두 개까지 보고 싶으면 `--maxfail=2`를 쓴다.

---

## 직전에 실패한 것만 다시

`--lf`는 **last failed**의 약자다. 지난번에 실패한 것만 다시 돌린다.

```
uv run pytest tests/unit/test_merkle.py --lf
```

고치고 → 돌리고 → 고치는 순환을 빠르게 만든다.
테스트가 100개인데 실패가 2개라면, `--lf`는 그 2개만 돈다.

**지난번에 아무것도 실패하지 않았다면 그냥 전부 돈다.** 그 상태는 정상이다.

> 이 기록은 `.pytest_cache/` 폴더에 남는다. 커밋되지 않고, 지워도 된다.

## 이름과 진행을 자세히 보기

`-v`는 `.` 대신 **테스트 이름과 결과를 한 줄씩** 보여 준다.

```
uv run pytest -v
```

```
collecting ... collected 2 items

tests/test_smoke.py::test_package_imports PASSED                         [ 50%]
tests/test_smoke.py::test_version_is_declared PASSED                     [100%]

============================== 2 passed in 0.01s ===============================
```

**언제 쓰나.** "내가 방금 만든 테스트가 진짜 돌긴 했나?"가 궁금할 때다.
이름이 보이면 확인이 끝난다.

반대로 `-q`는 더 조용하게 만든다. 실패 목록만 빠르게 볼 때 쓴다.

## print 출력을 보기

**pytest는 기본적으로 테스트 안의 `print`를 삼킨다.** 통과한 테스트는 특히 그렇다.
`-s`를 붙이면 그대로 보여 준다.

```
uv run pytest tests/unit/test_merkle.py -s
```

**언제 쓰나.** 값이 어떻게 생겼는지 직접 눈으로 보고 싶을 때다.
디버거를 켜기 전에 이게 더 빠른 경우가 많다.

```python
print("여기까지 왔다", root)   # 테스트나 구현 안에 잠깐 넣는다
```

확인이 끝나면 지워라. 남겨 두면 `ruff`가 잡을 수도 있고, 화면이 지저분해진다.

## 실패 메시지 읽는 순서

**빨간 화면이 길다고 겁먹지 마라. 읽는 순서가 정해져 있다.**
위에서부터 읽으면 헤맨다. **아래에서 위로 올라간다.**

실제 화면을 보자. `__version__`이 없을 때 나오는 실패다.

```
=================================== FAILURES ===================================
___________________________ test_version_is_declared ___________________________

    def test_version_is_declared() -> None:
        version = getattr(bbschain, "__version__", None)
>       assert isinstance(version, str), f"__version__ 이 str 이 아니다: {version!r}"
E       AssertionError: __version__ 이 str 이 아니다: None
E       assert False
E        +  where False = isinstance(None, str)

tests/test_smoke.py:6: AssertionError
=========================== short test summary info ============================
FAILED tests/test_smoke.py::test_version_is_declared
========================= 1 failed, 1 passed in 0.11s ==========================
```

**순서대로 읽는다.**

**1단계 — 맨 아래 요약부터.** `short test summary info` 아래가 "무엇이 실패했나"의 목록이다.

```
FAILED tests/test_smoke.py::test_version_is_declared
1 failed, 1 passed
```

여기서 두 가지를 얻는다. **몇 개가 실패했나**, 그리고 **어느 테스트인가.**
실패가 여러 개면 이 목록에서 **맨 위 하나만** 고른다. 나머지는 대개 같은 원인이다.

**2단계 — `>` 표시가 붙은 줄.** 그게 **실제로 터진 코드 한 줄**이다.

```
>       assert isinstance(version, str), ...
```

**3단계 — `E`로 시작하는 줄들.** pytest가 붙여 준 설명이다. 여기에 답이 있다.

```
E       AssertionError: __version__ 이 str 이 아니다: None
E        +  where False = isinstance(None, str)
```

`version`의 실제 값이 `None`이었다고 말하고 있다. **원인이 여기 있다.**

**4단계 — 필요하면 위로 올라간다.** `>` 줄 위쪽은 거기까지 가는 동안 실행된 코드다.
값이 어디서부터 이상해졌는지 되짚을 때 본다.

**5단계 — 파일과 줄 번호.** `tests/test_smoke.py:6` 같은 줄이다. 에디터에서 바로 열 수 있다.

> **`E` 줄을 안 읽고 코드를 고치기 시작하는 것**이 가장 흔한 시간 낭비다.
> pytest는 양쪽 값이 각각 뭐였는지 이미 알려 줬다. 먼저 읽어라.

### failed와 error는 다르다

| 표시 | 어디서 터졌나 | 어디를 보나 |
|---|---|---|
| `FAILED` | 테스트 **본문**. `assert`가 틀렸다 | 내가 만든 구현 |
| `ERROR` | **준비 단계**. 테스트가 시작도 못 했다 | import, 픽스처, 파일 경로 |

`ERROR`가 떴는데 구현을 들여다보고 있다면 방향이 틀렸다. **테스트가 시작조차 못 한 것이다.**

## 이 저장소에만 있는 규칙 — 왜 2개만 도나

`uv run pytest`를 인자 없이 돌리면 **테스트가 2개만 돈다.** 저장소에는 68개가 있는데도 그렇다.

직접 확인해 보자.

```
uv run pytest --collect-only -q | tail -1
```

```
2 tests collected in 0.01s
```

```
uv run pytest --collect-only -q tests | tail -1
```

```
68 tests collected in 0.14s
```

**같은 저장소인데 숫자가 다르다.** 범인은 `pyproject.toml`의 이 두 줄이다.

```toml
[tool.pytest.ini_options]
testpaths = ["tests/test_smoke.py"]
```

`testpaths`는 **"경로 인자를 안 줬을 때 어디를 볼지"** 를 정한다.

**왜 이렇게 해 뒀나.** `tests/unit/`과 `tests/integration/`에는
**Phase 1 구현을 기다리는 테스트가 미리 들어 있다.** 구현이 없으니 지금 돌리면 전부 실패한다.

그대로 두면 `uv run pytest`가 **영원히 빨강**이 된다.
빨강이 기본값이 되는 순간, 빨강은 아무 정보도 주지 못한다.
그래서 기본 범위에서 빼 뒀다.

**그러면 Phase 1 테스트는 어떻게 돌리나.** 경로를 직접 주면 된다.

```
uv run pytest tests/unit/test_merkle.py -v
```

**경로를 주면 `testpaths`는 비켜선다.** 그래서 이 명령은 그대로 동작한다.

> Phase 1 구현이 끝나면 `testpaths`를 `["tests"]`로 되돌린다. 그때가 오면 랩이 알려 준다.

## 아직 구현이 없을 때 뜨는 안내 배너

Phase 1 테스트를 처음 돌리면 이런 화면이 뜬다.

```
E       conftest.MissingImplementation:
E       ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
E        아직 구현이 없다 (이 시점에서는 정상이다)
E       ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
E        대상 : bbschain.core.merkle
E        랩   : Lab 1.4 — 머클 루트   (docs/labs/phase-1-chain.md)
E        필요 : merkle_root(leaves), merkle_proof(leaves, index), verify_proof(leaf, proof, root)
E
E        이 테스트는 위 랩의 과제를 만들면 초록이 된다.
E        원인 : ModuleNotFoundError: No module named 'bbschain.core'
E       ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**이건 고장이 아니다. 할 일 목록이다.**

`tests/conftest.py`에 `require_module`이라는 함수가 들어 있다.
구현 모듈을 import해 보고, 없으면 평범한 `ModuleNotFoundError` 대신 이 박스를 띄운다.
목적은 하나다. **"뭘 만들면 되는지"를 실패 화면이 직접 말해 주게 하는 것.**

**네 줄을 읽으면 된다.**

| 줄 | 무슨 뜻인가 | 네가 할 일 |
|---|---|---|
| `대상` | 만들어야 할 모듈 | `src/bbschain/core/merkle.py`를 만든다 |
| `랩` | 어느 랩의 과제인가 | 그 랩 문서를 연다 |
| `필요` | 그 안에 있어야 할 함수와 인자 | 이 시그니처대로 만든다 |
| `원인` | 진짜 파이썬 에러 | 폴더가 없는지 파일이 없는지 구분한다 |

`원인` 줄을 정확히 읽어라. `No module named 'bbschain.core'`는
**`core` 폴더 자체가 없다**는 뜻이다. `'bbschain.core.merkle'`이면 폴더는 있고 파일이 없다는 뜻이다.
→ [설정 가이드 — 새 모듈을 만들 때](phase-0/설정-가이드.md#새-모듈을-만들-때-하는-일)

**함수 이름이 틀렸을 때도 비슷한 박스가 뜬다.** `대상` 줄이 이렇게 바뀐다.

```
 대상 : bbschain.core.merkle.{merkle_root | root}
```

**`|`로 나뉜 것은 "이 중 아무 이름이나 있으면 된다"** 는 뜻이다.
테스트가 여러 이름을 허용하는 자리다. 하나도 없으면 이 박스가 뜬다.

## 속성 기반 테스트의 반례 읽는 법

**이 프로젝트에서 가장 중요한 실패 화면이다.** 여기만큼은 천천히 읽어라.

### 속성 기반 테스트가 뭔가

보통 테스트는 **예시 하나**를 검사한다. "글 3개를 넣으면 이 값이 나온다."

속성 기반 테스트(property-based test)는 다르다.
**"어떤 입력이든 이 규칙은 항상 성립한다"** 를 검사한다.
그 규칙을 **불변식(invariant)** 이라고 부른다.

입력은 `hypothesis`라는 도구가 **자동으로 수백 개 만들어 낸다.**
빈 문자열, 이모지, 아주 긴 값, 0, 음수 — 사람이 잘 떠올리지 않는 것들이 섞여 있다.
`pyproject.toml`의 dev 의존성에 `hypothesis`가 들어 있는 이유다.

### 규칙을 깨는 입력을 찾으면

hypothesis가 규칙을 깨는 입력을 하나라도 찾으면, 그 값을 화면에 찍어 준다.

```
_______ test_different_post_lists_have_different_summaries _______

a = [], b = ['']

    @given(st.lists(st.text()), st.lists(st.text()))
    def test_different_post_lists_have_different_summaries(a, b) -> None:
        if a != b:
>           assert summarize(a) != summarize(b)
E           AssertionError: assert '' != ''
E            +  where '' = summarize([])
E            +  and   '' = summarize([''])
E           Failing test case: test_different_post_lists_have_different_summaries(
E               a=[],
E               b=[''],
E           )
```

**`Failing test case:` 블록이 핵심이다.**
그 안에 적힌 것이 **규칙을 깨는 실제 입력값**이다. 여기서는 `a=[]`와 `b=['']`이다.

> **이름이 다를 수 있다.** 예전 버전의 hypothesis는 같은 블록을 `Falsifying example:`이라고 찍었다.
> 문서나 검색 결과에서 그 이름을 보면 같은 것이라고 생각하면 된다.
> 이 저장소에 깔린 버전은 `Failing test case:`를 쓴다.

### 왜 값이 이렇게 작고 시시한가

**hypothesis가 일부러 줄여서 준 것이다.**

처음 찾은 반례는 보통 지저분하다. 이런 식이다.

```
a=['글자가 잔뜩', '🙂🙂🙂', ''], b=['글자가 잔뜩', '🙂🙂🙂', '', '']
```

hypothesis는 여기서 멈추지 않는다. **값을 조금씩 줄여 가며 다시 시험한다.**
여전히 실패하면 더 줄인다. 더 줄이면 통과하는 지점에서 멈춘다.
이 과정을 **shrinking(축소)** 이라고 부른다.

그래서 화면에 남는 것은 **여전히 실패하는 가장 작은 입력**이다.

**이게 엄청난 선물이다.** 위 예에서 읽어 낼 것은 하나다.

> **"빈 목록과 [빈 문자열 하나]가 같은 요약을 만든다."**

이모지도 긴 글자도 원인이 아니었다. **구분자를 안 넣은 것**이 원인이다.
지저분한 반례였다면 이 결론에 도달하기까지 한참 걸린다.

### 읽는 순서

1. **`Failing test case:` 블록**을 먼저 본다 — 어떤 입력에서 깨졌나
2. **그 값들의 공통점**을 한 문장으로 말해 본다 — "둘 다 비었다", "순서만 다르다", "길이가 홀수다"
3. **`E` 줄**로 내려가 실제 값이 뭐였는지 확인한다
4. **`>` 줄**의 불변식을 다시 읽는다 — 내가 어떤 경우를 안 생각했나
5. 그 경우를 처리하고 다시 돌린다

### 같은 반례를 다시 재현하기

hypothesis는 한 번 찾은 반례를 `.hypothesis/` 폴더에 기억한다.
**다음 실행에서 그 값을 가장 먼저 다시 시험한다.** 고쳤는지 바로 확인할 수 있다.

```
uv run pytest tests/unit/test_merkle.py -k property --lf
```

`.hypothesis/`는 캐시다. 커밋하지 않고, 지워도 된다.

> **속성 테스트 하나가 예시 테스트 열 개보다 세다.**
> 하지만 실패했을 때 읽기는 더 어렵다. 그래서 이 절이 길다.

## 린터와 타입 검사

테스트만 초록이면 되는 게 아니다. **CI는 린터도 돌린다.** 로컬에서 먼저 확인하는 편이 빠르다.

### ruff — 스타일과 흔한 실수

```
uv run ruff check
```

```
All checks passed!
```

문제가 있으면 파일과 줄 번호, 규칙 코드가 나온다.

```
F401 [*] `hashlib` imported but unused
 --> src/bbschain/core/merkle.py:1:8
  |
1 | import hashlib
  |        ^^^^^^^
help: Remove unused import: `hashlib`

Found 1 error.
[*] 1 fixable with the `--fix` option.
```

**첫 줄이 규칙 코드와 요약**이고, `-->` 줄이 **파일과 위치**다.
`help:` 줄은 어떻게 고치라는 제안이다.
`[*]` 표시가 붙은 것은 자동으로 고칠 수 있다는 뜻이다.

```
uv run ruff check --fix
```

**자동 수정을 돌린 뒤에는 무엇이 바뀌었는지 꼭 확인하라.** 남이 고친 코드를 그냥 받지 마라.

### mypy — 타입 검사

```
uv run mypy src/
```

```
Success: no issues found in 2 source files
```

**`src/`만 검사한다.** `tests/`는 대상이 아니다.
`src/bbschain/core/` 아래는 특히 엄격하게 본다.
타입 표기 없는 함수를 만들면 여기서 걸린다.

### 커밋 전에 한 번에

CI가 돌리는 것과 같은 순서다.

```
uv sync --locked --all-groups
uv run ruff check
uv run pytest
```

**셋이 전부 성공하면 CI도 초록일 가능성이 높다.**
`uv sync --locked`는 `uv.lock`이 `pyproject.toml`과 어긋났는지 먼저 잡아 준다.

## 막혔을 때 확인 순서

| 증상 | 먼저 볼 것 |
|---|---|
| `collected 0 items` | 파일 이름이 `test_`로 시작하나. 함수 이름이 `test`로 시작하나 |
| `ModuleNotFoundError` | → [설정 가이드](phase-0/설정-가이드.md#modulenotfounderror가-났을-때) |
| 큰 박스가 뜨며 "아직 구현이 없다" | → [안내 배너](#아직-구현이-없을-때-뜨는-안내-배너). 에러가 아니다 |
| 실패가 20개라 뭘 볼지 모르겠다 | `-x`를 붙여 하나만 본다 |
| `Failing test case:` 블록이 나왔다 | → [반례 읽는 법](#속성-기반-테스트의-반례-읽는-법) |
| `uv: command not found` | uv가 안 깔렸다. 설치 후 터미널을 새로 연다 |
| `ERROR`인데 원인을 모르겠다 | 테스트 본문이 아니라 import와 준비 코드를 본다 |
