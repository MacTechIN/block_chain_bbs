## 저장소 최상위에 무엇이 있나

터미널에서 저장소 루트로 가서 확인해 보자. 어디가 루트인지 확신이 안 서면 이 명령이 답한다.

```
ls
```

`pyproject.toml`이 보이는 자리가 루트다. **이 문서의 모든 명령은 루트에서 돌린다.**

```
block_chain_bbs/
├─ pyproject.toml        프로젝트 선언서. 이름, 파이썬 버전, 의존성, 도구 설정이 전부 여기
├─ uv.lock               "지금 실제로 깔린 패키지 목록". 손으로 고치지 않는다
├─ README.md             저장소 첫인상
├─ LICENSE               라이선스
├─ .gitignore            커밋하지 말아야 할 것 목록 (*.key, .env 등)
│
├─ src/bbschain/         우리가 만드는 패키지. 본선 코드가 여기 쌓인다
├─ tests/                판정기. 이미 주어져 있다
├─ docs/                 읽는 문서 (튜토리얼·랩·계획서·진행 기록)
├─ workbook/             손을 움직이는 곳 (지금 이 문서가 있는 곳)
│
├─ .github/workflows/    CI 설정. GitHub이 대신 테스트를 돌리는 규칙
└─ .venv/                가상환경. uv가 만든다. 직접 건드리지 않는다
```

`.pytest_cache/`, `.ruff_cache/`, `.mypy_cache/`, `__pycache__/`도 보일 것이다.
전부 **도구가 만든 캐시**다. 지워도 다시 생긴다. 신경 쓰지 마라.

## 내가 만들 파일은 어디에 두나

**`src/bbschain/` 아래다.** 지금은 파일이 두 개뿐이다.

```
src/bbschain/
├─ __init__.py     패키지 표시 + __version__ 선언
└─ cli.py          Phase 0이 자리만 잡아 둔 빈 껍데기 (Lab 1.5에서 채운다)
```

Phase가 진행되면서 폴더가 하나씩 생긴다. **처음부터 다 만들지 않는다.**

| Phase | 여기에 생긴다 |
|---|---|
| 1 | `core/` (블록·해시·체인·머클), `storage/` |
| 2 | `api/`, `explorer/` |
| 3 | `wallet/`, `mempool/` |
| 4 | `consensus/` |
| 5 | `p2p/`, `node.py` |
| 7 | `anchor/` |

전체 최종형은 → [개발계획서 6절](../../docs/01-개발계획서.md#6-코드-구조)

**그럼 파일 이름은 내가 정하나?** 아니다. 대부분 이미 정해져 있다.
`tests/` 아래 테스트가 어떤 모듈을 import하는지 이미 적혀 있기 때문이다.
예를 들어 `tests/unit/test_merkle.py`는 `bbschain.core.merkle`을 찾는다.
그러니 **만들 파일은 `src/bbschain/core/merkle.py`** 다. 다른 이름이면 테스트가 못 찾는다.

무엇을 만들면 되는지 확인하는 가장 빠른 방법은 그 테스트를 한 번 돌려 보는 것이다.
실패 메시지가 모듈 이름과 함수 이름을 그대로 알려 준다
(→ [테스트 실행법 — 안내 배너](../테스트-실행법.md#아직-구현이-없을-때-뜨는-안내-배너)).

**두지 말아야 할 곳도 알아 두자.**

| 이런 파일 | 여기에 |
|---|---|
| 본선 구현 | `src/bbschain/` |
| 아무렇게나 돌려 보는 실험 코드 | `labs/` (아직 없는 폴더. 만들어 써도 된다) |
| 글로 적는 메모 | [`workbook/notes/`](../notes/README.md) |
| 테스트 | 🔴 만들지 않는다. `tests/`는 이미 주어져 있고 **고치지 않는다** |

## pyproject.toml 읽기

**이 파일 하나가 프로젝트의 선언서다.** 파이썬 버전, 깔 패키지, 도구 설정이 전부 여기 있다.
한 절씩 실제 내용을 보며 읽자. 저장소의 `pyproject.toml`을 열어 놓고 같이 봐도 좋다.

### `[project]` — 이 프로젝트가 뭔지

```toml
[project]
name = "bbschain"
version = "0.0.1"
requires-python = ">=3.12"
dependencies = []
```

- `name` — 패키지 이름. `import bbschain`의 그 이름이다
- `requires-python` — 3.12 이상에서만 돈다는 선언
- `dependencies` — **프로그램을 돌리는 데 필요한 패키지.** 지금은 비어 있다.
  Phase 0과 1은 파이썬 표준 라이브러리만 쓴다. FastAPI는 Phase 2에서 들어온다

### `[project.scripts]` — 터미널 명령 만들기

```toml
[project.scripts]
bbschain = "bbschain.cli:main"
```

읽는 법: **"터미널에서 `bbschain`이라고 치면 `bbschain/cli.py`의 `main` 함수를 부른다."**

지금 돌려 봐도 된다.

```
uv run bbschain --help
```

```
bbschain CLI 는 아직 구현되지 않았다. Lab 1.5 (docs/labs/phase-1-chain.md) 를 보라.
이 파일(src/bbschain/cli.py)은 콘솔 스크립트 진입점을 살려 두기 위한 Phase 0 스텁이다.
```

안내만 내고 끝난다. **그게 정상이다.** 이 줄이 가리키는 파일이 아예 없으면 설치가 깨진다.
그래서 Phase 0에서 빈 껍데기를 만들어 둔 것이다.

### `[build-system]`과 `[tool.hatch...]` — 패키지를 어떻게 조립하나

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]
packages = ["src/bbschain"]
```

`hatchling`은 **소스를 설치 가능한 형태로 조립해 주는 도구**다.
마지막 줄이 중요하다. "패키지의 실체는 `src/bbschain` 폴더다"라고 알려 준다.
이 줄이 없으면 `import bbschain`이 실패한다.

### `[dependency-groups]` — 개발할 때만 필요한 것

```toml
[dependency-groups]
dev = [
    "pytest>=8.0",
    "ruff>=0.6",
    "mypy>=1.11",
    "hypothesis>=6.100",
]
```

네 개가 하는 일은 각각 이렇다.

| 패키지 | 하는 일 |
|---|---|
| `pytest` | 테스트를 찾아서 돌리고 결과를 보고한다 |
| `ruff` | 코드 스타일과 흔한 실수를 잡는 린터 |
| `mypy` | 타입 표기가 맞는지 검사한다 |
| `hypothesis` | 값을 자동으로 만들어 가며 테스트한다 (Phase 1부터 쓴다) |

**`dev` 그룹인 이유**: 프로그램을 쓰는 사람에게는 필요 없고, 만드는 사람에게만 필요하다.

### `[tool.ruff]` — 린터 설정

```toml
[tool.ruff]
line-length = 100
target-version = "py312"
src = ["src"]
```

한 줄 100자까지 허용하고, 3.12 기준으로 검사하고, 소스 루트는 `src`라는 뜻이다.

```
uv run ruff check
```

```
All checks passed!
```

### `[tool.mypy]` — 타입 검사 범위

```toml
[tool.mypy]
python_version = "3.12"
files = ["src"]

[[tool.mypy.overrides]]
module = "bbschain.core.*"
disallow_untyped_defs = true
...
```

`files = ["src"]`는 **`src/`만 검사한다**는 뜻이다. `tests/`는 안 본다.

`[[tool.mypy.overrides]]` 블록은 **`core/` 아래만 더 엄격하게** 보겠다는 설정이다.
`disallow_untyped_defs = true`는 "타입 표기 없는 함수를 금지한다"는 뜻이다.
`core/`가 이 프로젝트의 심장이라 거기만 먼저 조인 것이다. 나머지는 Phase가 가면서 조인다.

### `[tool.pytest.ini_options]` — 기본 실행 범위

```toml
[tool.pytest.ini_options]
testpaths = ["tests/test_smoke.py"]
addopts = "-ra"
```

**이 두 줄 때문에 `uv run pytest`가 테스트 2개만 돈다.**
이유와 우회 방법은 → [테스트 실행법](../테스트-실행법.md#이-저장소에만-있는-규칙--왜-2개만-도나)

## uv와 venv가 하는 일

### uv가 뭔가

**`uv`는 파이썬 패키지와 가상환경을 관리하는 도구다.** `pip` + `venv`를 합친 것에 가깝다.
설치가 빠르고, 락 파일을 직접 관리해 준다.

기억할 명령은 사실상 두 개다.

| 명령 | 하는 일 |
|---|---|
| `uv sync` | `pyproject.toml`과 `uv.lock`을 보고 `.venv/`를 그 상태로 맞춘다 |
| `uv run <명령>` | **`.venv/` 안에서** 그 명령을 돌린다 |

### `.venv/`가 뭔가

**이 프로젝트 전용 파이썬 한 벌이다.** 저장소 안의 폴더 하나일 뿐이다.

여기에 `pytest`, `ruff`, `mypy`, `hypothesis`가 깔린다.
컴퓨터 전체에 깔지 않는 이유는 간단하다. **프로젝트마다 필요한 버전이 다르기 때문이다.**
프로젝트 A가 pytest 7을 쓰고 B가 9를 쓴다면, 한 컴퓨터에 하나만 깔아서는 둘 다 못 돌린다.

`.venv/`는 커밋하지 않는다. `.gitignore`에 들어 있다. `uv sync`로 언제든 다시 만든다.

### 왜 꼭 `uv run`을 붙이나

그냥 `pytest`라고 치면 **어느 파이썬이 잡힐지 알 수 없다.** 컴퓨터에 깔린 것일 수도 있다.
그러면 "내 컴퓨터에서는 되는데요"가 시작된다.

직접 비교해 보자.

```
uv run python -c "import sys; print(sys.executable)"
```

```
/home/<너>/…/block_chain_bbs/.venv/bin/python
```

저장소 안의 `.venv`를 가리킨다. `uv run` 없이 돌리면 다른 경로가 나올 것이다.

> `uv run`은 실행 전에 환경이 `pyproject.toml`과 맞는지도 확인한다.
> 의존성을 고쳤을 때 `uv sync`를 잊어도 대체로 알아서 맞춰 준다.

## import는 어느 파일을 찾아가나

Phase 1이 되면 테스트에 이런 줄이 나온다.

```python
from bbschain.core.merkle import merkle_root
```

**이 한 줄이 무엇을 찾는지 왼쪽부터 읽어 보자.**

```
from bbschain . core . merkle  import  merkle_root
     └─┬────┘  └─┬─┘  └─┬───┘         └─┬───────┘
       │         │      │               └─ 그 파일 안의 이름 (함수/클래스/변수)
       │         │      └─ merkle.py 라는 파일
       │         └─ core 라는 폴더
       └─ 패키지 뿌리. 실체는 src/bbschain/
```

결론: **`src/bbschain/core/merkle.py` 안의 `merkle_root`** 를 찾는다.

### "패키지 뿌리가 `src/bbschain/`"이라는 건 누가 정했나

`.venv` 안에 파일이 하나 있다. 직접 열어 봐라.

```
cat .venv/lib/python3.12/site-packages/_editable_impl_bbschain.pth
```

이 저장소 `src/`의 절대경로 한 줄이 들어 있다.
파이썬은 시작할 때 이런 `.pth` 파일을 읽어 그 경로를 탐색 목록에 넣는다.
그래서 `src/` 안의 `bbschain`이 보이게 된다.

**마법이 아니라 파일 한 줄이다.** 이걸 만드는 것이 `uv sync`이고,
이런 설치 방식을 editable install이라고 부른다. 자세한 설명은
→ [튜토리얼 Lab 0.2](../../docs/tutorial/phase-0.md#lab-02--uv-프로젝트와-src-레이아웃)

### 직접 확인해 보기

```
uv run python -c "import bbschain; print(bbschain.__file__)"
```

```
/home/<너>/…/block_chain_bbs/src/bbschain/__init__.py
```

**복사본이 아니라 네가 지금 고치는 그 파일**을 가리킨다.
그래서 코드를 고치면 다음 실행부터 바로 반영된다. 재설치할 필요가 없다.

## 새 모듈을 만들 때 하는 일

Phase 1에서 `bbschain.core.merkle`을 만들어야 한다고 하자. 순서는 이렇다.

**1. 폴더를 만든다** (이미 있으면 건너뛴다)

```
mkdir -p src/bbschain/core
```

**2. `__init__.py`를 만든다**

```
touch src/bbschain/core/__init__.py
```

비어 있어도 된다. 내용은 필요할 때 넣는다.

> **`__init__.py`가 꼭 필요한가?** 없어도 import가 되는 경우가 있다.
> 하지만 **이 프로젝트에서는 항상 만든다.** 이유는 둘이다.
> `__init__.py`가 없는 폴더는 이름 충돌에 약하고, 패키징 도구가 빠뜨릴 수 있다.
> 고민할 거리를 하나 없애는 쪽이 낫다.

**3. 모듈 파일을 만든다**

```
touch src/bbschain/core/merkle.py
```

**4. 바로 import가 되는지 확인한다**

```
uv run python -c "import bbschain.core.merkle; print('ok')"
```

```
ok
```

**`uv sync`를 다시 돌릴 필요는 없다.** editable 설치는 `src/` 안의 파일을 그때그때 읽는다.

다만 예외가 하나 있다. **`pyproject.toml`을 고쳤다면 `uv sync`를 다시 돌린다.**
의존성을 추가했거나 `[project.scripts]`를 바꿨을 때다. 파일 내용이 아니라 **설정**이 바뀐 경우다.

## ModuleNotFoundError가 났을 때

```
ModuleNotFoundError: No module named 'bbschain.core.merkle'
```

**이 에러 하나가 여러 원인을 가린다.** 그래서 순서대로 확인한다.
위에서부터 내려가면 대개 두세 번째에서 잡힌다.

| # | 확인할 것 | 명령 | 이런 결과면 원인이다 |
|---|---|---|---|
| 1 | 명령 앞에 `uv run`을 붙였나 | — | 안 붙였으면 그것부터 고친다 |
| 2 | 저장소 루트에 있나 | `ls pyproject.toml` | 파일이 없다고 나오면 다른 폴더에 있다 |
| 3 | 파일이 실제로 있나. **철자와 위치** | `ls src/bbschain/core/` | 오타, 다른 폴더, 확장자 누락 |
| 4 | 폴더마다 `__init__.py`가 있나 | `ls src/bbschain/core/__init__.py` | `core/`에 없으면 만든다 |
| 5 | `bbschain` 자체는 import되나 | `uv run python -c "import bbschain; print(bbschain.__file__)"` | 여기서 실패하면 6번으로 |
| 6 | 설치 연결이 살아 있나 | `cat .venv/lib/python3.12/site-packages/_editable_impl_bbschain.pth` | 파일이 없으면 `uv sync` |
| 7 | 그래도 안 되면 환경을 새로 만든다 | `rm -rf .venv && uv sync` | 마지막 수단. 안전하다 |

**에러 메시지의 이름을 그대로 읽어라.** `No module named 'bbschain.core'`와
`No module named 'bbschain.core.merkle'`은 다른 말이다.
앞의 것은 **폴더**가 없다는 뜻이고, 뒤의 것은 그 안의 **파일**이 없다는 뜻이다.
